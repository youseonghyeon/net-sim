# 시뮬레이터에서 자주 보는 실패와 원인

통신이 안 될 때 이벤트 로그(하단 서랍)에 남는 문구와 원인, 고치는 법. 실제 네트워크에서도 같은 순서로 의심하면 된다.

## 구성 검사 경고 (타일의 ! 배지, 인스펙터 "구성 검사")

시뮬레이션을 돌리기 전에 설정만 보고 잡는 것. 빨강(오류)은 통신이 확실히 안 되는 것, 노랑(주의)은 될 수도 있지만 의심스러운 것.

| 경고 문구 | 원인 | 고치는 법 |
|---|---|---|
| `DHCP 로 주소는 나가지만 게이트웨이를 알려주지 않아 …` | DHCP 서버 호스트의 "기본 게이트웨이 (옵션 3)" 칸이 비었는데 같은 세그먼트에 라우터가 있다 | 서버 → DHCP 서비스 → 게이트웨이 칸에 그 라우터 인터페이스 주소 |
| `DHCP 가 DNS 서버를 알려주지 않아 …` | "DNS 서버 (옵션 6)" 칸이 비어 있음 | DNS 칸에 내부 DNS 서버·공유기·8.8.8.8 |
| `게이트웨이 … 가 내 서브넷 … 밖` | 호스트 IP/서브넷 마스크와 게이트웨이가 다른 서브넷 | 둘 중 하나를 같은 서브넷으로 |
| `게이트웨이 … 가 같은 세그먼트의 라우터 주소(…)와 다름` | 오타이거나 다른 스위치/VLAN 의 라우터 주소 | 게이트웨이를 안내된 주소로, 또는 케이블을 그 라우터 쪽으로 |
| `이 서브넷엔 게이트웨이 장치가 없음` | 게이트웨이를 설정했지만 세그먼트에 라우터 인터페이스가 없다 | 게이트웨이/NAT/공유기를 연결하거나 게이트웨이 칸 비우기 |
| `if0 에 주소 … 는 있지만 디폴트 라우트(게이트웨이)가 없음` | 게이트웨이/NAT 업링크를 수동으로 두고 게이트웨이 칸을 비움 | if0/outside → 게이트웨이 칸에 위쪽 라우터 주소 |
| `… 뒤 … 로 돌아가는 경로가 없어 응답이 … 에서 버려짐` | 게이트웨이 뒤 게이트웨이인데 위쪽 장치에 스태틱 라우팅이 없다 | 위쪽 장치 스태틱 라우팅에 `<안쪽 서브넷> via <아래 게이트웨이 if0>` (공유기는 스태틱 라우팅이 없으니 게이트웨이/NAT 박스로 교체) |
| `… 와 … 서브넷이 겹침` | 한 장치의 인터페이스/서브 인터페이스 서브넷 중복 | 한쪽 IP/서브넷 마스크를 다른 서브넷으로 |
| `같은 세그먼트에 DHCP 서버가 N개` | 공유기 DHCP 와 호스트 DHCP 서비스가 같은 LAN 에 | 하나만 남기고 끄기 |
| `IP … 가 같은 세그먼트의 … 와 겹침` | 수동 IP 중복(호스트·공유기 LAN·게이트웨이 인터페이스) | 하나를 바꾼다 |
| `IP … 가 이 세그먼트 라우터의 서브넷(…) 밖` / `if0 주소 … 가 위쪽 라우터의 서브넷 … 밖` | 호스트나 업링크 수동 주소가 라우터 서브넷과 다름 → 응답이 돌아오지 못함 | 라우터 서브넷 안의 주소로 |
| `… 의 DHCP 릴레이 대상 … 로 가는 경로가 없음` | 릴레이 서버 주소가 어느 인터페이스 서브넷에도 없고 경로도 없음 | 스태틱 라우팅 추가 또는 릴레이 대상을 인터페이스 서브넷 안 서버로 |
| `포트 포워딩 TCP :443 → …:443 인데 … 가 … 를 열지 않음 (열린 것: TCP 80)` | 포워딩의 안쪽 포트와 서버가 여는 포트가 다름 (흔한 실수: 443 → 443 인데 웹 서버는 80) | 안쪽 포트를 서버가 여는 포트로 맞추거나 서버에서 그 서비스를 켠다. DNS 를 공개하려면 UDP 53 규칙 + 서버의 DNS 서비스 |
| `DHCP 가 DNS 서버로 공유기 자신을 안내하는데 DNS 포워더가 꺼져 있음` | 공유기 DNS 포워더를 끈 채 DHCP 의 DNS 칸을 비움 → 호스트들이 공유기에 묻지만 답이 없다 | 포워더를 켜거나 DHCP 의 DNS 서버 칸에 8.8.8.8 등을 넣고, 호스트에서 DHCP 임대 갱신 |
| `… 의 트렁크 포트 … 에 연결됨 → … 태그를 이해하지 못해 통신 불가` | 호스트/공유기/허브/AP 가 트렁크 포트에 | 스위치 → VLAN → 그 포트를 액세스로 |
| `… 에 VLAN 서브 인터페이스가 있는데 상대 … 가 트렁크가 아님` | 게이트웨이 서브 인터페이스 포트의 상대 스위치 포트가 액세스 | 그 스위치 포트를 트렁크로 |

검사는 확신이 있을 때만 경고한다(오탐보다 미탐). DHCP 로 주소를 받는 인터페이스처럼 주소를 아직 모르는 경우는 조용히 넘어가므로, 배지가 없다고 설정이 다 맞는 건 아니다.

## 주소를 못 받는다 ("IP 미설정", "DHCP 실패")

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `DHCP timeout: … 응답 없음 → 재시도 n/3` 뒤 `DHCP 실패: timeout` | 같은 L2 세그먼트에 DHCP 서버가 없거나 꺼져 있다 | 라우터의 DHCP 서비스를 켜거나 DHCP 서버 호스트를 두고, 호스트 진단에서 **DHCP 임대 갱신** |
| 라우터/서버 쪽 `DHCP 서비스가 꺼져 있음 → 응답하지 않음` | 서버는 Discover 를 받았지만 서비스가 꺼짐 | DHCP 토글 켜기 |
| `임대할 주소 없음 (풀 고갈) (범위 … 모두 사용 중)` | 풀 고갈. 지운 장치의 임대는 Release 로 돌아오지만, 케이블만 뽑은 장치의 임대는 남는다 | 범위를 넓히거나, 안 쓰는 장치를 삭제(Release) |
| `DHCP 설정 오류: 범위 … 가 인터페이스 서브넷 밖` | LAN 주소를 바꿨는데 범위가 옛 서브넷 | 인스펙터에서 범위를 서브넷 안으로. LAN 주소를 바꾸면 범위는 자동으로 따라오지만 직접 고친 값은 검증 오류로 표시된다 |
| `DHCP 서버가 켜져 있지만 내 주소가 고정이 아님` | DHCP 서버 역할 호스트가 자기 주소를 DHCP 로 받으려 함 | 그 호스트의 IP 설정을 **수동**으로 |
| `DHCP Offer … (기본 게이트웨이 옵션 없음)` | DHCP 서버 호스트에 "기본 게이트웨이 (옵션 3)" 가 비어 있음 → 클라이언트는 같은 서브넷 밖으로 못 나감 | 서버의 "기본 게이트웨이 (옵션 3)" 칸에 그 서브넷의 게이트웨이 주소 |
| 주소를 받았는데 옛 서브넷(예: 192.168.0.x) | 라우터 LAN 을 바꾸기 전에 받은 임대 | 호스트에서 **DHCP 임대 갱신** (라우터 쪽 옛 임대는 이미 무효화됨) |
| `주소 충돌: X 는 이미 Y 가 쓰는 주소 (ARP Probe 에 응답) → 이 주소를 쓰지 않음`, 타일에 `… 충돌 · 사용 안 함` | 고정 IP 를 넣을 때 ARP Probe 로 확인했더니 같은 서브넷의 다른 장비가 이미 씀(장비를 복사해 만들면 흔함). 실제 OS 처럼(RFC 5227) 그 주소를 쓰지 않는다 | 다른 주소를 넣는다. 상대가 주소를 바꾸면 자동으로 다시 확인해 쓴다. 두 장비가 동시에 켜지면 둘 다 포기한다 |
| `주소 충돌: … 도 내 IP … 를 씀 → Gratuitous ARP 로 방어` / `… 기록만` | 쓰는 중에 다른 장비가 같은 주소를 주장. 한 번 방어(이웃 ARP 캐시를 내 MAC 으로 되돌림)하고, 10초 안의 재충돌은 기록만 | 한쪽 주소를 바꾼다. 바꾸면 `충돌 해소` 가 뜬다 |
| `DHCP Request 브로드캐스트 (INIT-REBOOT): "전에 쓰던 X 를 계속 써도 되나요?"` → `DHCP Nak 수신: 전에 쓰던 X 는 이 네트워크에서 쓸 수 없음` | 케이블을 다른 네트워크에 다시 꽂았거나 다른 공유기의 AP 로 로밍. 쓰던 주소부터 확인하는 게 실제 동작(RFC 2131) | 정상 동작. 바로 Discover 로 새 주소를 받는다 |
| `DHCP timeout: 전에 쓰던 X 확인에 … 응답 없음 → Discover 부터` (서버 쪽 `INIT-REBOOT: … 임대 기록이 없음 → 응답하지 않음`) | 같은 서브넷이지만 이 클라이언트를 모르는 서버(다른 공유기). RFC 2131 은 이때 서버가 침묵하게 한다 | 정상 동작. 1초 뒤 Discover 로 새 주소를 받는다 |
| 내 요청은 나가는데 **응답이 옆집(다른 장비)으로 감** | IP 가 겹쳤던 동안 이웃의 ARP 캐시에 그 주소 → 다른 장비 MAC 이 남음(stale ARP). 현실에서도 IP 충돌 뒤 흔한 현상 | 주소를 바꾸면 충돌 해소·재확인으로 풀린다. 급하면 그 인터페이스 IP 를 지웠다 다시 넣어 Gratuitous ARP 를 보낸다 |

## ping 이 실패한다

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `ping … 실패: 내 IP 주소가 없음` | 위 표 참조 | 주소부터 |
| `… 는 다른 서브넷인데 게이트웨이 설정 없음 → 드롭` | 호스트에 게이트웨이가 없음 | 수동이면 게이트웨이 입력, 자동이면 DHCP 서버가 게이트웨이를 안내하는지 확인 |
| `ARP timeout: … 응답 없음 → 대기 패킷 드롭` / `Destination Host Unreachable` | 그 IP 를 가진 장치가 같은 세그먼트에 없다. **잘못된 게이트웨이 주소**일 때도 이 문구 | 대상/게이트웨이 주소가 실제 장치 주소인지, 같은 서브넷인지 확인 |
| `목적지 … 는 LAN 안의 주소 → 라우터를 거칠 필요가 없음 → 드롭` (라우터) | 호스트 서브넷 마스크가 잘못돼 같은 LAN 인데 게이트웨이로 보냄 | 호스트 프리픽스(/24 등)를 라우터와 맞춘다 |
| `WAN 에 공인 주소가 없음 → 인터넷으로 보낼 수 없음` | 라우터 wan 포트에 인터넷이 안 붙었거나 WAN DHCP 실패 | wan 포트에 인터넷 노드 연결, WAN 설정 확인 |
| `… 에 주소가 없음 (케이블과 DHCP, 또는 수동 주소를 확인)` (게이트웨이/NAT) | 업링크 인터페이스에 주소 없음 | 업링크(if0/outside) 케이블·설정 확인 |
| `No route … RIP 이웃에게서 이 경로를 배우지 못함` (게이트웨이/NAT, RIP 켬) | 그 네트워크를 가진 라우터까지 RIP 가 이어지지 않음: 중간 라우터가 RIP 를 안 켰거나, 케이블이 끊겼거나, 그 라우터의 인터페이스에 주소가 없음 | 경로상의 라우터마다 RIP 를 켜고, 각 라우터 표 탭의 라우팅 테이블에 `RIP n홉` 줄이 생기는지 본다. 인터넷으로 나가는 경로면 NAT 박스에서 "디폴트 라우트 광고" 를 켠다 |
| `RIP … 수신 — RIP 가 꺼져 있음 → 무시` / `… 이 인터페이스 서브넷 밖 → 무시` | 이웃은 RIP 를 켰는데 나는 꺼져 있음 / 링크 양쪽 주소가 다른 서브넷 | 양쪽 모두 RIP 를 켜고, 라우터끼리 잇는 링크의 두 인터페이스를 같은 서브넷으로 |
| 케이블을 뽑았는데 다른 라우터가 여전히 그쪽으로 보냄 (RIP) | 스위치 너머의 이웃이 사라진 경우: 내 링크는 살아 있어 모른다. 실제 RIP 는 180초 timeout 으로 알아채지만 이 시뮬레이터는 주기 광고가 없다 | 라우터끼리 직접 잇거나, 그 라우터의 RIP 를 껐다 켜서 다시 광고하게 한다 |
| `No route … 스태틱 라우팅을 추가하세요` (NAT 박스) | NAT 박스 뒤에 게이트웨이가 더 있어, 역변환한 응답을 보낼 안쪽 경로를 모름 | NAT 박스 스태틱 라우팅에 `192.168.0.0/16 via <게이트웨이의 업링크 주소>` 처럼 추가 |
| `ping … 실패: Destination Net Unreachable (X)` / TCP `실패 · Destination Net Unreachable (X)` | 장비 X(게이트웨이·NAT·공유기)의 라우팅 테이블에 목적지로 가는 경로가 없음. X 가 ICMP 로 바로 알려 줘 timeout 을 기다리지 않는다 | X 의 스태틱 라우팅·디폴트 라우트(또는 RIP)를 확인. 공유기면 WAN 주소가 있는지 |
| `… 실패: Destination Host Unreachable (X)` | X 까지는 갔지만 목적지(또는 넥스트 홉) 주소에 ARP 로 답하는 장치가 없음: 주소 오타, 꺼진·케이블 빠진 장치 | 목적지 주소와 그 장치의 케이블·IP 를 확인. 포트 포워딩 대상이 없을 때 바깥 클라이언트도 이 통지를 받는다 |
| `… 해석 중단: DNS 서버에 닿지 않음: Destination Port Unreachable (X)` | DNS 서버로 적은 X 가 DNS 서비스를 켜지 않아 UDP 53 이 닫혀 있음 | X 의 서비스에서 DNS 서버를 켜거나, DNS 칸(또는 DHCP 의 DNS 서버 옵션 6)을 실제 DNS 서버로 |
| `사설 주소 … 는 인터넷에서 라우팅되지 않음 → 드롭` (인터넷) | NAT 없이 사설 주소가 밖으로 나감 (게이트웨이만 있고 NAT 없음) | 인터넷 앞에 NAT 박스나 라우터를 둔다 |
| `NAT 테이블에 없는 … → 드롭. 내부에서 시작하지 않은 통신은 들어올 수 없음` | 바깥에서 먼저 시작한 통신 | 정상 동작. NAT 의 성질 |
| `바깥에서 안쪽 주소 … 로 온 패킷 → 드롭` | 바깥에서 사설 주소를 직접 찍음 | 정상 동작 |
| 안에서 한 번 연결한 뒤 바깥의 다른 클라이언트가 같은 공인 포트로 들어옴 (`nat.restore`) | 이 시뮬레이터의 NAT 는 endpoint-independent(full cone) 매핑: 한 번 열린 공인 포트는 상대를 가리지 않는다. 가정용 공유기의 흔한 동작 | 정상. 막으려면 방화벽 인바운드 규칙 + Stateful 검사 |
| `ping … timeout: 2000ms 동안 응답 없음 (Request timed out)` | ARP 는 됐지만 응답이 안 옴: 중간 장치에 경로 없음(No route), 케이블 손실 실험, 상대가 드롭 | 중간 장치(라우터/게이트웨이/NAT)의 로그에서 드롭 문구를 찾는다 |
| `프레임이 스위치 16개를 넘게 돌았음` / `같은 프레임을 … 다시 받음 → L2 루프` | 두 장치 사이 케이블 2개, 스위치 삼각형 등 L2 루프 | 중복 케이블 제거. 실제 네트워크는 STP 가 막는다 |
| `이벤트가 폭주해 일시정지했습니다` (토스트) | 위 루프가 심해 시뮬레이션이 스스로 멈춤 | 루프 케이블을 지우고 재생 |

## traceroute (진단의 "경로" 버튼)

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 마지막 홉 뒤에 `!N` / `!H` 가 붙고 끝남 | 그 홉 장치가 Destination Unreachable 을 돌려줌: `!N` = 경로 없음, `!H` = 목적지 주소에 ARP 응답 없음 (실제 traceroute 와 같은 표기) | `!N` 이면 그 장치의 라우팅을, `!H` 면 목적지 장치와 주소를 확인 |
| `traceroute X 실패: 16 홉 안에 도달하지 못함` (홉이 `*` 로 이어짐) | `*` 가 시작된 다음 장치가 패킷을 드롭 — No route(`ip.no-route`), 방화벽(`fw.deny`), 인터넷이 사설 주소를 드롭 | 마지막으로 응답한 홉의 **다음 장치** 로그를 본다. 스태틱 라우팅·디폴트 라우트, 방화벽 규칙, 대상이 사설 주소인지 확인 |
| `traceroute X 실패: ARP timeout · 응답 없음 (첫 홉 G …)` | 게이트웨이 주소 G 를 가진 장치가 같은 세그먼트에 없음 | 호스트의 게이트웨이 주소와 케이블(스위치 포트)을 확인 |
| `traceroute X 실패: 게이트웨이 없음` | 다른 서브넷인데 호스트에 게이트웨이가 없음 | IP 설정에 게이트웨이를 넣거나 DHCP 서버의 게이트웨이 옵션을 채운다 |
| `… 새 traceroute 시작으로 취소` / `링크 다운` / `주소 변경` | 진행 중에 다시 시작했거나 링크·주소가 바뀜 | 정상. 다시 실행 |
| 2번째 홉부터 `*` 인데 ping 은 됨 (`fw.deny … Time Exceeded`) | 라우터 방화벽이 인바운드 ICMP 를 막고 Stateful 검사가 꺼져 있어 라우터의 오류 통지가 차단됨 | 방화벽의 Stateful 검사를 켜거나 인바운드 ICMP 허용 규칙 추가 |
| `ping X 실패: TTL 초과` (`icmp.ttl-received` "라우팅 루프 의심") | 두 라우터의 스태틱 라우팅·디폴트 라우트가 서로를 가리켜 패킷이 맴돎 | 두 장치의 경로에서 X 로 가는 항목이 서로를 가리키는지 확인하고 한쪽을 고친다 |

## 이름(google.com, web.home)이 안 된다

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `… 찾을 수 없음: DNS 서버가 설정되지 않음` | 호스트에 DNS 가 없음 (수동 설정에서 비웠거나, DHCP 서버가 DNS 를 안내하지 않음) | 수동이면 DNS 칸 입력. 자동이면 DHCP 서버(라우터는 자동으로 자기 주소, 호스트 서버는 "DNS 서버 (옵션 6)" 칸) 확인 |
| `DNS timeout: 서버 … 가 2번 물어도 응답 없음` | DNS 서버 주소가 틀리거나 경로가 없음, 또는 그 호스트의 DNS 서버 서비스가 꺼짐 | 서버 주소 확인, 그 서버로 ping 이 되는지 확인, 서버의 "DNS 서버" 토글 |
| `DNS 응답: … 없는 이름 (NXDOMAIN)` | 서버 레코드에 없고 업스트림 DNS 도 모르는 이름 | 서버 레코드 추가. 공개 이름은 google.com, example.com, naver.com, github.com, cloudflare.com 만 등록돼 있음 |
| `DNS 서버가 업스트림 서버 응답을 받지 못함 (SERVFAIL)` / 라우터 `업스트림 DNS … timeout (응답 없음)` | 라우터 포워더나 DNS 서버가 업스트림 DNS(8.8.8.8)에 못 닿음: 인터넷 미연결, WAN 주소 없음 | 인터넷 노드 연결과 WAN/outside 주소 확인 |
| `DNS 포워더가 꺼져 있음` | 라우터의 DNS 포워더 토글이 꺼짐 | 켜거나 호스트에 8.8.8.8 을 직접 설정 |
| `DNS 질의를 받았지만 DNS 서버 서비스가 꺼져 있음` | 호스트를 DNS 로 지정했는데 그 호스트의 서비스가 꺼짐 | 서비스에서 DNS 서버 켜기 |

## 바깥에서 들어오는 연결 (포트 포워딩)

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `NAT 테이블에 없는 TCP 포트 80 → 드롭 … (포트 포워딩 규칙을 추가하면 열 수 있음)` | 바깥에서 시작한 연결에 규칙이 없음 | 라우터/NAT 박스의 포트 포워딩에 `공인 :80 → 내부 서버:80` 추가 |
| 규칙은 있는데 인터넷 쪽 클라이언트가 `실패` | 내부 서버 주소가 틀리거나 서버의 웹 서비스가 꺼짐, 또는 NAT 박스 뒤 라우터로 가는 스태틱 라우팅 없음 | 규칙의 주소·포트, 서버의 웹 서버 토글, NAT 박스 스태틱 라우팅 확인 |
| `RST 수신 … 그 포트를 듣는 서비스가 없음` (내부 서버) | 포워딩은 됐지만 서버가 그 포트를 안 듣는다 | 서버의 서비스 토글 |

## 방화벽

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `방화벽 차단: 아웃바운드/인바운드 … — 규칙 N (…) → 드롭` | 그 라우터/게이트웨이의 규칙 N 에 걸림 | 규칙을 지우거나 순서를 바꾼다(위가 먼저). 허용 규칙을 차단 규칙보다 위에 |
| `방화벽 차단: … — 일치하는 규칙 없음, 기본 정책 차단` | 기본 정책이 차단인데 허용 규칙이 없다 | 필요한 통신의 허용 규칙 추가(예: 아웃바운드 TCP 80) 또는 기본 정책을 허용으로 |
| 안에서 시작한 ping/TCP 의 **응답**이 `방화벽 차단` | Stateful 검사가 꺼져 있어 응답도 "인바운드" 규칙에 걸림 | Stateful 검사 켜기. 실제 방화벽의 ESTABLISHED 허용과 같다 |
| `… 상 차단이지만, 안에서 시작한 통신의 응답이라 Stateful 검사로 허용` | 정상. 규칙엔 걸리지만 응답이라 통과 | 응답까지 막고 싶으면 Stateful 검사를 끈다 |
| 포트 포워딩은 됐는데 서버에 안 닿음 | `nat.forward.rule` 뒤에 `방화벽 차단 … 인바운드 TCP …:80` | 방화벽에 인바운드 TCP 80 허용 규칙을 차단 규칙 위에 |
| 방화벽 장비(fw) 뒤 서버에 ping 이 `방화벽 차단: 인바운드 ICMP …` | 투명 방화벽의 인바운드 = outside(위) 포트로 들어온 것. 서버를 inside(아래)에 두면 서버로 가는 것이 인바운드 | 규칙 방향을 확인하거나 케이블의 위/아래를 바꾼다 |
| 방화벽 장비가 ping 에 안 잡히고 traceroute 홉에도 없음 | 정상. 투명 방화벽은 IP 가 없다 | 규칙이 도는지는 fw 장치의 로그(`fw.allow`/`fw.deny`)로 본다 |
| 방화벽 장비 뒤(inside)의 호스트가 `DHCP 실패` 이고 fw 로그에 `방화벽 차단: 인바운드 UDP …:67` | 기본 정책 차단인데 DHCP 허용 규칙이 없다. ARP 는 L2 라 통과하지만 DHCP 는 IP(UDP) 라 규칙 대상 | 허용 · 양방향 · UDP · 포트 67 과 68 규칙을 차단 규칙 위에 |
| 방화벽 장비의 한쪽 케이블만 꽂았더니 `… 에 케이블이 없음 → 드롭` | 투명 방화벽은 반대 포트로만 내보낸다 | outside·inside 둘 다 케이블 연결 |
| 게이트웨이에서 서브넷 간 통신이 "인바운드/아웃바운드" 규칙에 안 걸림 | 방향은 업링크(if0/outside/WAN) 기준이라 안쪽 서브넷끼리는 "양방향" 만 해당 | 서브넷 간 규칙은 방향을 "양방향" 으로 하고 출발지/목적지로 구분 |

## 무선 (Wi-Fi)

| 로그 문구 / 화면 | 원인 | 고치는 법 |
|---|---|---|
| 스마트폰에 `무선 연결 없음`, 인스펙터 "SSID … 를 송출하는 AP 나 공유기가 없습니다" | SSID 오타이거나 기지가 없음 | 단말 SSID 와 AP/공유기 SSID 를 맞춘다 (대소문자 구분) |
| "SSID … 의 무선이 꺼져 있습니다" | 공유기 무선 토글이 꺼짐 (기본값 꺼짐) | 공유기 → 무선(Wi-Fi) 켜기. 무선 AP 장치는 기본 켜짐 |
| "전파 범위 밖입니다" | 단말이 기지 중심에서 300px 넘게 떨어짐 (캔버스의 점선 원 밖) | 단말을 원 안으로 끌어오기 |
| "범위 안의 기지 … 에 빈 무선 슬롯이 없습니다" | 기지당 단말 8대 한도(AP·공유기 모두) | 단말을 줄이거나 AP 를 하나 더 두고 범위를 나눈다 |
| `무선 연결 변경: 다른 기지/슬롯으로 옮겨 붙음 → 다시 연결` | 더 가까운 기지로 로밍(끌어서 옮김) | 정상. 새 기지에서 DHCP 로 새로 임대받는다 |
| `무선 연결 실패: … → 다음 변경 때 다시 시도` | 슬롯이 아직 옛 링크에 잡혀 있는 등 일시적 충돌 | 단말을 살짝 옮기거나 SSID 를 다시 입력하면 재시도된다 |
| `무선 연결 끊김 (범위 밖이거나 …)` 뒤 `임대 주소 … 해제` | 끌어서 범위를 벗어남 | 정상. 다시 들어오면 재연결 + DHCP 새 임대 |
| AP 에 붙었는데 주소를 못 받음 | AP 의 eth0 에 케이블이 없음 (AP 는 브리지일 뿐, DHCP 서버가 아님) | AP eth0 을 스위치/공유기에 케이블로 연결 |
| 단말끼리 ping 이 AP 를 거침 (`단말 ↔ 단말 중계`) | 정상. 무선 단말은 서로 직접 통신하지 않고 AP 가 중계한다 | — |
| `전파로 송출 … 다른 단말도 전파는 받지만 암호화되어 읽지 못한다` | 정상. 무선은 같은 채널의 모두에게 닿는다 | — |

## VLAN

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `… 는 트렁크인데 태그 없는 프레임 → 드롭 (상대 포트도 트렁크여야 함)` | 케이블 한쪽만 트렁크 | 양쪽 스위치 포트를 모두 트렁크로, 또는 둘 다 액세스로 |
| `… 는 액세스 포트(VLAN n)인데 VLAN m 태그 프레임 → 드롭` | 트렁크에서 온 태그 프레임이 액세스 포트로 들어옴 | 그 포트를 트렁크로 |
| 호스트 `VLAN n 태그가 달린 프레임 → 호스트는 태그를 이해하지 못해 드롭` | 호스트가 트렁크 포트에 꽂힘 | 호스트 쪽 스위치 포트를 액세스(VLAN 번호)로 |
| 같은 서브넷 주소인데 `ARP timeout` | 두 호스트가 다른 VLAN 포트에 꽂힘 (브로드캐스트 도메인이 다름) | 같은 VLAN 으로 맞추거나, 서브넷을 나누고 게이트웨이로 잇는다 |
| 게이트웨이 `VLAN n 태그 프레임 → 해당 서브 인터페이스 없음 → 드롭` | 트렁크로 들어온 VLAN 에 서브 인터페이스가 없음 | 게이트웨이의 그 인터페이스에 `VLAN n` 서브 인터페이스(주소) 추가 |
| 다른 VLAN 으로 ping 이 `게이트웨이 설정 없음` / `ARP timeout` | 호스트 게이트웨이가 그 VLAN 의 서브 인터페이스 주소가 아님 | 호스트 게이트웨이 = 자기 VLAN 서브 인터페이스 주소 (예: VLAN 10 → 192.168.10.1) |
| 공유기 `LAN 포트는 태그를 이해하지 못해 드롭` | 트렁크 포트를 공유기에 꽂음 | 공유기는 VLAN 미지원. 게이트웨이 장치를 쓰거나 스위치 포트를 액세스로 |
| 트렁크로 오가는데 태그 없는 프레임이 드롭됨 | 이 시뮬레이터에는 네이티브 VLAN(태그 없는 프레임을 VLAN 1 로 취급)이 없다 | 트렁크에는 스위치·게이트웨이 서브 인터페이스만 꽂고, 호스트는 액세스 포트에 |
| 방화벽 규칙에 포트를 넣었는데 ping 이 그대로 통과/차단됨 | 포트는 TCP/UDP 에만 있어 프로토콜 `모든 프로토콜`+포트 규칙은 ICMP 에 일치하지 않는다 | ICMP 를 막으려면 프로토콜 `ICMP(ping)` 규칙을 따로 둔다 |

## 허브

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `허브: 학습 없이 … 모든 포트로 반복 — 모든 장치가 이 프레임을 본다` | 정상. 허브는 MAC 을 배우지 않아 모든 프레임을 모두에게 보낸다 | 스위치로 바꾸면 `MAC 테이블 조회: <MAC> → <포트> 로 전달` 로 바뀐다 |

## TCP 연결이 안 된다 / 끊긴다

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `RST 수신: … 그 포트를 듣는 서비스가 없음 → 연결 거부` | 대상의 서비스(웹 서버 80)가 꺼짐, 또는 포트 번호가 다름 | 대상 장치의 서비스 토글 켜기, 포트 확인 |
| TCP 연결 표에 `실패 · timeout · SYN 에 응답 없음 (재전송 3회)`, 로그 `TCP timeout: SYN 을 3번 다시 보냈지만 SYN-ACK 없음` | 상대가 거부(RST)한 게 아니라 **중간에서 조용히 드롭**됨: 방화벽 차단, NAT 에 포트 포워딩 규칙 없음(`NAT 테이블에 없는 TCP 포트 … → 드롭`), 경로 없음(No route) | 드롭한 장치의 로그(`fw.deny`, `nat.miss`, `ip.no-route`)를 찾아 규칙·포워딩·경로를 고친다 |
| `실패 · timeout · ACK 없음 (재전송 3회)` (연결은 됐다가 중간에) | 데이터 구간에서 손실(케이블 손실률/손실 실험) 또는 도중에 경로가 끊김 | 케이블 손실률을 0 으로, 또는 ping 으로 먼저 경로를 확인 |
| `순서가 어긋난 데이터 … 중간 세그먼트가 손실됨` | 세그먼트 하나가 손실되어 뒤 세그먼트가 먼저 도착 | 정상 복구 과정. 서버가 timeout 후 재전송한다 |
| `종료된 연결로 FIN·ACK 가 다시 옴 → ACK 재전송` | 내 마지막 ACK 이 손실됨 | 정상 복구 과정 |
| `주소 변경` 으로 연결 실패 | 전송 중 IP 모드/주소를 바꿈 | 정상. 다시 연결 |

## 로드밸런서

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 클라이언트가 `받음 200B`, LB 로그 `… → 502 Bad Gateway` (`백엔드가 하나도 없음` / `살아 있는 백엔드가 없음`) | 백엔드 목록이 비었거나, 목록의 백엔드가 모두 거부·timeout 으로 빠져 있음 | 로드밸런서 → 백엔드에 뒤 서버 주소·포트를 넣고, 그 서버들의 웹 서비스가 켜져 있는지 확인. 빠진 백엔드는 10초 뒤 다시 시도된다 |
| `백엔드 X 실패 (연결 거부 (RST)) → 10초 동안 빼고 다음 백엔드로` | 그 서버가 해당 포트를 열지 않음 (웹 서버 꺼짐, 포트 번호 불일치) | 백엔드 서버의 서비스를 켜거나 LB 의 백엔드 포트를 맞춘다. 구성 검사 `lb.backend-closed` 가 미리 알려 준다 |
| `백엔드 X 실패 (timeout · SYN 에 응답 없음 …)` | 백엔드 주소에 장비가 없거나(ARP timeout), 경로·방화벽에서 드롭 | 주소 오타, 케이블, LB 와 백엔드 사이 경로를 확인 |
| 클라이언트 `HTTP 508 Loop Detected`, 구성 검사 `lb.loop` | 로드밸런서끼리 서로를(또는 자기 자신을) 백엔드로 둠 → 요청이 LB 사이를 돈다. 요청마다 거친 LB 수(Via)가 5개가 되면 끊는다 | 백엔드 목록에서 로드밸런서를 빼고 실제 웹 서버를 넣는다 |
| 클라이언트 `실패 · timeout · 응답 없음 (요청은 전달됨, 10초)` | 상대(로드밸런서)가 요청은 받았지만 응답을 못 줌: LB 의 주소가 바뀌거나 링크가 끊겨 요청이 중단됨 | LB 의 주소·케이블을 확인하고 다시 연결. 앞단 LB 에게는 이 경우가 백엔드 실패가 되어 다음 서버로 넘어간다 |
| 백엔드 서버 로그의 상대 주소가 클라이언트가 아니라 LB 주소 | 정상 동작. 리버스 프록시는 LB 가 대신 연결한다 | 실제 서비스는 X-Forwarded-For 헤더로 원래 클라이언트를 알린다 (이 시뮬레이터는 응답의 "응답 …" 표시로 반대 방향만 보여 줌) |

## VPN

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 구성 검사 `VPN 상대 대역이 우리 LAN 과 겹침` | 두 사무실이 같은 사설 대역(예: 둘 다 192.168.0.0/24)을 씀 → 어느 쪽 주소인지 구분할 수 없다 | 한쪽 대역을 바꾼다 (192.168.1.0/24 와 192.168.2.0/24 처럼) |
| `VPN 패킷 수신 … → 풀지 않고 드롭: 안쪽 출발지 … 가 상대 대역이 아님` / 구성 검사 `vpn.one-way` | 상대 장비의 "상대 쪽 사설 대역" 에 우리 LAN 이 없거나, 우리 쪽 목록에 상대 LAN 이 없음 (한쪽만 설정) | 양쪽 VPN 설정을 짝으로: A 의 대역 목록 = B 의 LAN, B 의 대역 목록 = A 의 LAN |
| 구성 검사 `상대 … 가 VPN 을 켜지 않음` / 상대 로그 `UDP 포트 51820 …` | 상대 장비의 VPN 이 꺼짐 | 상대에서도 VPN 을 켜고 이쪽 공인 주소를 상대 주소로 |
| `VPN: 상대 … 로 가는 바깥 경로가 없어 터널로 보낼 수 없음` | 상대 공인 주소로 갈 경로(디폴트 라우트)가 없음 | outside 의 게이트웨이(디폴트 라우트)나 상대 공인 주소를 확인 |
| `IPsec 터널을 맺지 못함: IKE_SA_INIT 응답 없음 (timeout …)` | 상대가 IPsec VPN 을 켜지 않았거나(또는 WireGuard 방식), 상대 공인 주소가 틀렸거나, 상대가 NAT 뒤인데 UDP 500·4500 포워딩이 없음 | 상대 VPN 을 IPsec 으로 켜고 공인 주소 확인. 상대가 NAT 뒤면 그 NAT 에 UDP 500·4500 → VPN 장비 포워딩 |
| `… IKE_AUTH 인증 실패 — 사전 공유 키(PSK)가 다름` / `AUTHENTICATION_FAILED 로 거절`, 구성 검사 `vpn.psk-mismatch` | 양쪽 PSK 가 다름 | 두 장비의 VPN → 사전 공유 키를 똑같이 |
| 구성 검사 `vpn.mode-mismatch` | 한쪽은 WireGuard, 한쪽은 IPsec | 양쪽 방식을 같게 |
| `ESP(IPsec) …: ESP 에는 포트가 없어 NAT 가 … 드롭` | ESP 가 NAT 를 지나려 함 (보통은 NAT 감지로 UDP 4500 을 쓰므로, 방식·설정이 어긋났을 때) | 양쪽 IPsec 설정을 확인. 사이에 NAT 가 있으면 NAT-T(UDP 4500)가 쓰인다 |
| `IPsec ESP 수신 … 드롭: 이 상대와 맺은 IPsec 터널(SA)이 없음` | 설정을 바꿔 터널이 내려간 뒤 상대가 옛 터널로 보냄 | 이쪽에서 한 번 보내면 다시 협상한다 |
| IKE 가 `재전송 2번 뒤 timeout` 인데 상대는 IPsec 을 켰음, 구성 검사 `vpn.natt-closed` | 상대가 NAT 뒤인데 UDP 4500 포워딩이 없음 (NAT 를 감지하면 IKE_AUTH·ESP 가 4500 으로 감) | 상대 NAT 에 UDP 4500 → VPN 장비 포워딩 추가 |
| 상대가 먼저 연 터널이 방화벽에서 `인바운드 ESP … 차단` | 기본 차단 방화벽에 ESP 허용이 없음 | 방화벽 규칙: 인바운드 UDP 500·4500 과 ESP(IPsec) 를 상대 공인 주소에서 허용 |
| traceroute 가 터널 너머 첫 홉에서 `*` | 상대 VPN 장비가 보낸 Time Exceeded 의 출발지(그쪽 연결 구간 주소)가 이쪽 터널 대역에 없어 AllowedIPs·트래픽 셀렉터로 버려짐 — 실제 장비도 같다 | 정상. 필요하면 그 연결 구간도 터널 대역에 추가 |
| 구성 검사 `vpn.shared-peer` / 한쪽 사무실만 되다가 다른 쪽이 보내면 뺏김 | 두 사이트가 같은 상대에 VPN 을 연결. 상대는 터널 하나만 두고 마지막에 받은 출발지로 답하므로, 나중에 보낸 쪽이 응답을 가져간다 (실제 WireGuard 는 키로 구분하지만 여기엔 키가 없다) | 상대 하나에는 한 사이트만 연결. 사이트가 여럿이면 상대 쪽 터널 장비를 사이트마다 둔다 |
| 방화벽을 켜자 상대 사무실에서 먼저 여는 연결만 `방화벽 차단` | 터널로 나가는 것은 아웃바운드, 터널에서 풀려 들어오는 것은 인바운드로 판정한다. "기본 차단 + 아웃바운드 허용" 이면 이쪽이 연 연결의 응답만(Stateful 검사) 들어온다 | 상대 대역(예: 192.168.2.0/24)에서 오는 인바운드 허용 규칙을 추가 |
| VPN 게이트웨이를 NAT 박스 뒤에 두었는데 상대가 보내면 안 닿음 | 앞의 NAT 박스가 UDP 51820 을 안쪽으로 넘기지 않음 | NAT 박스에 포트 포워딩 UDP 51820 → VPN 게이트웨이 주소. 상대의 "상대 공인 주소" 는 NAT 박스의 공인 주소 |
| 상대 공인 주소를 바꿨는데 이쪽 응답이 예전 주소로 감 | 받은 출발지를 기억하는 엔드포인트 로밍 때문. 상대가 다시 보내기 전까지는 마지막으로 받은 주소로 답한다 | 상대 쪽에서 한 번 보내면(ping) 새 주소를 배운다. 이쪽 VPN 설정의 상대 주소를 바꾸면 기억도 지워진다 |
| 한쪽이 공유기 NAT 뒤인데 반대쪽에서 먼저 보내면 안 됨 | NAT 뒤 쪽은 바깥에서 먼저 들어갈 수 없다 (NAT 의 성질) | NAT 뒤 쪽이 먼저 보내면 반대쪽이 그 출발지로 답한다. 또는 NAT 에 UDP 51820 포트 포워딩 |

## 그 밖에

- **시계가 멈춰 있다**: 패킷이 없고 대기 이벤트도 없으면 시계는 일부러 멈춘다. 동작(ping, 케이블 연결)을 하면 다시 흐른다.
- **일시정지 상태에서 아무 일도 없다**: 상단 ▶ 재생 또는 다음 이벤트(→). Space 로 토글.
- **장치가 캔버스 밖에 있다**: 예제를 다시 불러오면 내용에 맞춰 화면을 잡는다. 휠로 이동, ⌘+휠로 확대·축소.
- **케이블이 안 이어진다** ("빈 포트가 없습니다" / "이미 연결되어 있습니다"): 포트 수 한도(호스트 1, 라우터 5, 스위치 8), 같은 두 장치 사이는 케이블 1개만.

## 이중화 (HA)

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 구성 검사 `ha.vrid-mismatch`, 두 장비 타일이 모두 `HA master` | 짝의 그룹 번호(VRID)가 달라 서로를 짝으로 보지 않음 → 같은 가상 주소를 둘 다 주장 | 두 장비의 그룹 번호를 같게 |
| 구성 검사 `ha.vrid-shared`, 한 쌍이 둘 다 `HA backup` | 서로 다른 이중화 쌍이 같은 세그먼트에서 같은 그룹 번호를 씀 → 네 대가 하나의 선출로 묶임 | 쌍마다 다른 그룹 번호(VRID) |
| 구성 검사 `ha.vip-mismatch` | 짝의 가상 주소가 서로 다름 → 넘어가면 호스트가 쓰던 게이트웨이 주소가 사라짐 | 두 장비의 인터페이스별 가상 주소를 똑같이 |
| 구성 검사 `ha.host-real-gw` | 호스트 게이트웨이가 한 장비의 실제 주소 → 그 장비가 죽으면 따라가지 않음 | 호스트 게이트웨이(또는 DHCP 게이트웨이 옵션)를 가상 주소로 |
| 넘어간 뒤 진행 중이던 TCP 가 timeout, 새 master 에 `NAT 테이블에 없는 …`·`방화벽 차단: 인바운드 …` | 세션 동기화가 꺼져 있어 새 master 는 옛 NAT 매핑·방화벽 흐름을 모름 | 두 장비의 이중화 설정에서 세션 동기화(pfsync)를 켠다. 이미 끊긴 연결은 새로 연결 |
| 구성 검사 `ha.sync-mismatch` | 짝 중 한쪽만 세션 동기화를 켬 | 두 장비 모두 켜거나 끄기 |
| 넘어간 뒤 IPsec 이 잠깐 `SA 없음` 드롭 | 새 master 에는 IPsec 터널이 없음 → 다음 패킷에 다시 협상 | 한 번 더 보내면 복구 |
| `이중화: VIP 인터페이스의 링크·주소가 모두 준비되지 않아 backup 으로 대기 (우선순위 0)` | 가상 주소를 둔 인터페이스 중 하나라도 케이블·주소가 없음 (인터페이스 추적) | 케이블과 인터페이스 주소 확인 |

## SSH 세션

| 증상 / 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 세션은 "SSH 세션 열림" 인데 사이 경로가 끊겨 있음 | keepalive 가 없어 조용한 세션은 경로가 끊겨도 모른다 (실제로도 멈춘 SSH 창이 된다) | "연결 해제" 를 눌러 보면 FIN 재전송 끝에 timeout 으로 드러난다. 다시 접속 |
| 이중화가 넘어간 뒤 "연결 해제" 가 `timeout · ACK 없음`, 새 master 에 `방화벽 차단: 인바운드 TCP …` | 새 master 의 Stateful 검사·NAT 테이블에 이 세션이 없음 (세션 동기화 없음) | 새로 접속한다 |
| 클라이언트는 `실패 · 링크 다운` 인데 서버의 TCP 표에는 여전히 `연결됨` | 반쯤 열린 연결: 클라이언트가 사라진 걸 서버는 알 길이 없다 (keepalive 없음) — 실제 서버도 같은 이유로 keepalive·timeout 을 둔다 | 정상 동작. 서버 쪽 연결은 남아 있어도 해가 없다 |
| 구성 검사 `lb.ssh-port` | 로드밸런서가 포트 22 를 받음. 이 로드밸런서는 HTTP 만 나누는 L7 프록시 | 받는 포트를 웹 포트로. SSH 는 서버에 바로 |
| `SSH 키 교환 중` 에서 멈췄다가 `timeout · 응답 없음` | 중간에서 서버 응답이 드롭됨 (방화벽·경로) | 방화벽에서 TCP 22 허용, 경로 확인 |

## 스패닝 트리 (STP)

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `같은 프레임을 … 에서 다시 받음 … L2 루프 감지, 드롭`, 구성 검사 `switch.loop-no-stp` | 스위치끼리 고리로 이었는데 STP 가 꺼진 스위치가 있음 (실제라면 브로드캐스트 폭주) | 고리에 있는 스위치 모두 STP 켜기 |
| `… 는 STP 대체 포트(차단) → 데이터 프레임을 받지 않고 버림` | 정상. 루프를 끊으려고 막은 포트로 들어온 프레임 | 없음. 다른 경로가 끊기면 이 포트가 열린다 |
| 원하지 않는 스위치가 루트 브리지 | 브리지 우선순위가 같으면 MAC 이 작은 쪽이 루트 | 가운데(코어) 스위치의 우선순위를 작게(예: 4096) |

## 원격 접속 VPN

| 증상 / 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 노트북 `원격 접속 실패: IKE_SA_INIT 응답 없음 …`, 구성 검사 `ra.server-off` | 서버 주소가 틀렸거나 그 장비의 원격 접속 VPN 서버가 꺼짐, 또는 UDP 500·4500 이 막힘 | 서버 공인 주소 확인, 서버에서 원격 접속 VPN 켜기 |
| `서버가 인증을 거절 (AUTHENTICATION_FAILED)`, 구성 검사 `ra.psk-mismatch` | 노트북과 서버의 사전 공유 키가 다름 | 둘을 같게 |
| `INTERNAL_ADDRESS_FAILURE` | 가상 주소 풀이 다 찼거나 잘못됨 | 서버의 풀 시작·끝 확인 |
| 연결됐는데 사내 서버 SSH 가 timeout, 회사 방화벽 `방화벽 차단: 인바운드 … 10.99.0.x` | 방화벽이 가상 주소 풀에서 들어오는 것을 막음 (터널에서 풀린 패킷은 인바운드) | 방화벽에 "인바운드 · 출발 10.99.0.0/24 → 사내 대역 허용" |
| 연결됐는데 사내 서버의 응답이 안 옴 (안쪽에 라우터가 더 있음) | 안쪽 라우터가 가상 주소 풀(10.99.0.x)로 가는 경로를 모름 | 안쪽 라우터에 "10.99.0.0/24 → VPN 장비" 스태틱 라우팅 |
| 8.8.8.8 은 되는데 사내 대역만 안 됨 / 반대 | split tunnel: 서버가 알려 준 사내 대역만 터널로 간다 | 서버의 "알려 줄 사내 대역" 에 필요한 대역 추가 |
| 구성 검사 `ra.pool-overlap` | 가상 주소 풀이 사내 대역과 겹침 | 쓰지 않는 대역으로 |
