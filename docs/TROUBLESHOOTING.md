# 시뮬레이터에서 자주 보는 실패와 원인

통신이 안 될 때 이벤트 로그(하단 서랍)에 남는 문구와 원인, 고치는 법. 실제 네트워크에서도 같은 순서로 의심하면 된다.

## 구성 검사 경고 (타일의 ! 배지, 인스펙터 "구성 검사")

시뮬레이션을 돌리기 전에 설정만 보고 잡는 것. 빨강(오류)은 통신이 확실히 안 되는 것, 노랑(주의)은 될 수도 있지만 의심스러운 것.

| 경고 문구 | 원인 | 고치는 법 |
|---|---|---|
| `DHCP 범위 … 가 이 서버의 서브넷 … 밖` / `DHCP 범위의 시작 주소 … 가 끝 주소 … 보다 큼` (`dhcp.range-invalid`, 오류) | DHCP 서버 호스트의 시작·끝 주소가 서버 자신의 IP/서브넷 밖이거나 거꾸로 → 서버가 Discover 에 응답하지 않아(로그 `DHCP 설정 오류`) 단말이 주소를 못 받는다. 릴레이용 추가 풀 요청에도 응답하지 않는다(추가 풀 자체는 서버 서브넷 밖이 정상). 이때는 게이트웨이·DNS 안내 경고를 내지 않는다 | 서버 → DHCP 서비스 → 시작·끝 주소를 서버 서브넷 안으로(거꾸로면 맞바꾸기), 또는 서버 IP/서브넷을 범위에 맞추기 |
| `DHCP 로 주소는 나가지만 게이트웨이를 알려주지 않아 …` | DHCP 서버 호스트의 "기본 게이트웨이 (옵션 3)" 칸이 비었는데 같은 세그먼트에 라우터가 있다 | 서버 → DHCP 서비스 → 게이트웨이 칸에 그 라우터 인터페이스 주소 |
| `DHCP 가 DNS 서버를 알려주지 않아 …` | "DNS 서버 (옵션 6)" 칸이 비어 있음 | DNS 칸에 내부 DNS 서버·공유기·8.8.8.8 |
| `게이트웨이 … 가 내 서브넷 … 밖` | 호스트 IP/서브넷 마스크와 게이트웨이가 다른 서브넷 | 둘 중 하나를 같은 서브넷으로 |
| `게이트웨이 … 가 같은 세그먼트의 라우터 주소(…)와 다름` | 오타이거나 다른 스위치/VLAN 의 라우터 주소. 그 주소의 장비가 없으면 ARP timeout, 라우터가 아닌 장비(다른 호스트 등)의 주소면 ARP 는 되지만 그 장비가 드롭(호스트는 포워딩 안 함) | 게이트웨이를 안내된 주소로, 또는 케이블을 그 라우터 쪽으로 |
| `기본 게이트웨이 옵션(3) … 가 이 세그먼트의 라우터 주소(…)와 다름` / `추가 풀 … 의 기본 게이트웨이 옵션(3) …` (`dhcp.gateway-mismatch`) | DHCP 서버 호스트의 기본 게이트웨이 칸(추가 풀이면 그 풀의 게이트웨이 칸)이 오타·옛 라우터 주소·다른 서브넷 주소·서버 자신의 주소 → 단말은 주소를 받지만 다른 네트워크로 못 나간다(그 주소의 장비가 없으면 ARP timeout, 라우터가 아닌 장비 주소면 그 장비가 드롭). 기본 풀과 추가 풀이 둘 다 틀리면 한 항목에 이어서 적는다 | 그 칸을 세그먼트 라우터 인터페이스 주소(이중화 쌍이면 가상 주소)로 바꾸고, 이미 받은 호스트에서 DHCP 임대 갱신 |
| `서브넷 /16 가 이 세그먼트 라우터 … 의 /24 보다 짧음` / `… 보다 김` (`host.prefix-mismatch`) | 수동 호스트의 IP 는 라우터 서브넷 안인데 프리픽스 길이가 다름. 짧으면 라우터 서브넷 밖 주소도 같은 네트워크로 보고 ARP 로 직접 찾다가 실패, 길면 같은 서브넷의 일부 주소를 게이트웨이로 보냄(공유기는 드롭, 게이트웨이/NAT 박스는 되돌려 보내는 우회). /0 도 잡는다. 게이트웨이 규칙(서브넷 밖·라우터 주소와 다름)에 걸린 호스트는 그쪽을 먼저 고친다 | 호스트 → IP 설정 → 서브넷을 라우터와 같은 길이로 |
| `이 서브넷엔 게이트웨이 장치가 없음` | 게이트웨이를 설정했지만 세그먼트에 라우터 인터페이스가 없다 | 게이트웨이/NAT/공유기를 연결하거나 게이트웨이 칸 비우기 |
| `if0 에 주소 … 는 있지만 디폴트 라우트(게이트웨이)가 없음` | 게이트웨이/NAT 업링크를 수동으로 두고 게이트웨이 칸을 비움 | if0/outside → 게이트웨이 칸에 위쪽 라우터 주소 |
| `… 뒤 … 로 돌아가는 경로가 없어 응답이 … 에서 버려짐` | 게이트웨이 뒤 게이트웨이인데 위쪽 장치에 스태틱 라우팅이 없다 | 위쪽 장치 스태틱 라우팅에 `<안쪽 서브넷> via <아래 게이트웨이 if0>` (공유기는 스태틱 라우팅이 없으니 게이트웨이/NAT 박스로 교체) |
| `… 와 … 서브넷이 겹침` | 한 장치의 인터페이스/서브 인터페이스 서브넷 중복 | 한쪽 IP/서브넷 마스크를 다른 서브넷으로 |
| `같은 세그먼트에 DHCP 서버가 N개` | 공유기 DHCP 와 호스트 DHCP 서비스가 같은 LAN 에 | 하나만 남기고 끄기 |
| `IP … 가 같은 세그먼트의 … 와 겹침` | 수동 IP 중복(호스트·공유기 LAN·게이트웨이 인터페이스) | 하나를 바꾼다 |
| `IP … 가 이 세그먼트 라우터의 서브넷(…) 밖` / `if0 주소 … 가 위쪽 라우터의 서브넷 … 밖` | 호스트나 업링크 수동 주소가 라우터 서브넷과 다름 → 응답이 돌아오지 못함 | 라우터 서브넷 안의 주소로 |
| `… 의 DHCP 릴레이 대상 … 로 가는 경로가 없음` | 릴레이 서버 주소가 어느 인터페이스 서브넷에도 없고 경로도 없음 | 스태틱 라우팅 추가 또는 릴레이 대상을 인터페이스 서브넷 안 서버로 |
| `포트 포워딩 TCP :443 → …:443 인데 … 가 … 를 열지 않음 (열린 것: TCP 80)` | 포워딩의 안쪽 포트와 서버가 여는 포트가 다름 (흔한 실수: 443 → 443 인데 웹 서버는 80) | 안쪽 포트를 서버가 여는 포트로 맞추거나 서버에서 그 서비스를 켠다. DNS 를 공개하려면 UDP 53 규칙 + 서버의 DNS 서비스 |
| `DHCP 가 DNS 서버로 공유기 자신을 안내하는데 DNS 포워더가 꺼져 있음` | 공유기 DNS 포워더를 끈 채 DHCP 의 DNS 칸을 비움 → 호스트들이 공유기에 묻지만 답이 없다 | 포워더를 켜거나 DHCP 의 DNS 서버 칸에 8.8.8.8 등을 넣고, 호스트에서 DHCP 임대 갱신 |
| `… 의 트렁크 포트 … 에 연결됨 → … 태그를 이해하지 못해 통신 불가` | 호스트/공유기/허브/AP 가 트렁크 포트에 | 스위치 → VLAN → 그 포트를 액세스로 |
| `… 에 VLAN 서브 인터페이스가 있는데 상대 … 가 트렁크가 아님` | 게이트웨이 서브 인터페이스 포트의 상대 스위치 포트가 액세스 | 그 스위치 포트를 트렁크로 |

검사는 확신이 있을 때만 경고한다(오탐보다 미탐). DHCP 로 주소를 받는 인터페이스처럼 주소를 아직 모르는 경우는 조용히 넘어가므로, 배지가 없다고 설정이 다 맞는 건 아니다.

## 주소를 못 받는다 ("IP 미설정", "DHCP 실패")

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `DHCP timeout: … 응답 없음 → 재시도 n/3` 뒤 `DHCP 실패: timeout` | 같은 L2 세그먼트에 DHCP 서버가 없거나 꺼져 있다 | 라우터의 DHCP 서비스를 켜거나 DHCP 서버 호스트를 두고, 호스트 진단에서 **DHCP 임대 갱신** |
| 라우터/서버 쪽 `DHCP 서비스가 꺼져 있음 → 응답하지 않음` | 서버는 Discover 를 받았지만 서비스가 꺼짐 | DHCP 토글 켜기 |
| `임대할 주소 없음 (풀 고갈) (범위 … 모두 사용 중)` | 풀 고갈. 지운 장치의 임대는 Release 로 돌아오지만, 케이블만 뽑은 장치의 임대는 남는다 | 범위를 넓히거나, 안 쓰는 장치를 삭제(Release) |
| `DHCP 설정 오류: 범위 … 가 인터페이스 서브넷 밖` | LAN 주소를 바꿨는데 범위가 옛 서브넷 | 인스펙터에서 범위를 서브넷 안으로. LAN 주소를 바꾸면 범위는 자동으로 따라오지만 직접 고친 값은 검증 오류로 표시된다. 호스트 DHCP 서비스는 구성 검사 `dhcp.range-invalid` 가 미리 알려 준다 |
| `DHCP 서버가 켜져 있지만 내 주소가 고정이 아님` | DHCP 서버 역할 호스트가 자기 주소를 DHCP 로 받으려 함 | 그 호스트의 IP 설정을 **수동**으로 |
| `DHCP Offer … (기본 게이트웨이 옵션 없음)` | DHCP 서버 호스트에 "기본 게이트웨이 (옵션 3)" 가 비어 있음 → 클라이언트는 같은 서브넷 밖으로 못 나감 | 서버의 "기본 게이트웨이 (옵션 3)" 칸에 그 서브넷의 게이트웨이 주소 |
| 주소를 받았는데 옛 서브넷(예: 192.168.0.x) | 라우터 LAN 을 바꾸기 전에 받은 임대 | 호스트에서 **DHCP 임대 갱신** (라우터 쪽 옛 임대는 이미 무효화됨) |
| `주소 충돌: X 는 이미 Y 가 쓰는 주소 (ARP Probe 에 응답) → 이 주소를 쓰지 않음`, 타일에 `… 충돌 · 사용 안 함` | 고정 IP 를 넣을 때 ARP Probe 로 확인했더니 같은 서브넷의 다른 장비가 이미 씀(장비를 복사해 만들면 흔함). 실제 OS 처럼(RFC 5227) 그 주소를 쓰지 않는다 | 다른 주소를 넣는다. 상대가 주소를 바꾸면 자동으로 다시 확인해 쓴다. 두 장비가 동시에 켜지면 둘 다 포기한다 |
| `주소 충돌: … 도 내 IP … 를 씀 → Gratuitous ARP 로 방어` / `… 기록만` | 쓰는 중에 다른 장비가 같은 주소를 주장. 한 번 방어(이웃 ARP 캐시를 내 MAC 으로 되돌림)하고, 10초 안의 재충돌은 기록만 | 한쪽 주소를 바꾼다. 바꾸면 `충돌 해소` 가 뜬다 |
| `DHCP Request 브로드캐스트 (INIT-REBOOT): "전에 쓰던 X 를 계속 써도 되나요?"` → `DHCP Nak 수신: 전에 쓰던 X 는 이 네트워크에서 쓸 수 없음` | 케이블을 다른 네트워크에 다시 꽂았거나 다른 공유기의 AP 로 로밍. 쓰던 주소부터 확인하는 게 실제 동작(RFC 2131) | 정상 동작. 바로 Discover 로 새 주소를 받는다 |
| `DHCP timeout: 전에 쓰던 X 확인에 … 응답 없음 → Discover 부터` (서버 쪽 `INIT-REBOOT: … 임대 기록이 없음 → 응답하지 않음`) | 같은 서브넷이지만 이 클라이언트를 모르는 서버(다른 공유기). RFC 2131 은 이때 서버가 침묵하게 한다 | 정상 동작. 1초 뒤 Discover 로 새 주소를 받는다 |
| 내 요청은 나가는데 **응답이 옆집(다른 장비)으로 감** | IP 가 겹쳤던 동안 이웃의 ARP 캐시에 그 주소 → 다른 장비 MAC 이 남음(stale ARP). 현실에서도 IP 충돌 뒤 흔한 현상 | 주소를 바꾸면 충돌 해소·재확인으로 풀린다. 급하면 그 인터페이스 IP 를 지웠다 다시 넣어 Gratuitous ARP 를 보낸다 |

## ping 이 실패한다

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `ping … 실패: 내 IP 주소가 없음` | 위 표 참조 | 주소부터 |
| `… 는 다른 서브넷인데 게이트웨이 설정 없음 → 드롭` | 호스트에 게이트웨이가 없음 | 수동이면 게이트웨이 입력, 자동이면 DHCP 서버가 게이트웨이를 안내하는지 확인 |
| `ARP timeout: … 응답 없음 → 대기 패킷 드롭` / `Destination Host Unreachable` | 그 IP 를 가진 장치가 같은 세그먼트에 없다. **잘못된 게이트웨이 주소**일 때도 이 문구 | 대상/게이트웨이 주소가 실제 장치 주소인지, 같은 서브넷인지 확인 |
| `목적지 … 는 LAN 안의 주소 → 라우터를 거칠 필요가 없음 → 드롭` (라우터) | 호스트 서브넷 마스크가 잘못돼 같은 LAN 인데 게이트웨이로 보냄 | 호스트 프리픽스(/24 등)를 라우터와 맞춘다. 구성 검사 `host.prefix-mismatch` 가 미리 알려 준다 |
| `WAN 에 공인 주소가 없음 → 인터넷으로 보낼 수 없음` | 라우터 wan 포트에 인터넷이 안 붙었거나 WAN DHCP 실패 | wan 포트에 인터넷 노드 연결, WAN 설정 확인 |
| `… 에 주소가 없음 (케이블과 DHCP, 또는 수동 주소를 확인)` (게이트웨이/NAT) | 업링크 인터페이스에 주소 없음 | 업링크(if0/outside) 케이블·설정 확인 |
| `No route … RIP 이웃에게서 이 경로를 배우지 못함` (게이트웨이/NAT, RIP 켬) | 그 네트워크를 가진 라우터까지 RIP 가 이어지지 않음: 중간 라우터가 RIP 를 안 켰거나, 케이블이 끊겼거나, 그 라우터의 인터페이스에 주소가 없음 | 경로상의 라우터마다 RIP 를 켜고, 각 라우터 표 탭의 라우팅 테이블에 `RIP n홉` 줄이 생기는지 본다. 인터넷으로 나가는 경로면 NAT 박스에서 "디폴트 라우트 광고" 를 켠다 |
| `RIP … 수신 — RIP 가 꺼져 있음 → 무시` / `… 이 인터페이스 서브넷 밖 → 무시` | 이웃은 RIP 를 켰는데 나는 꺼져 있음 / 링크 양쪽 주소가 다른 서브넷 | 양쪽 모두 RIP 를 켜고, 라우터끼리 잇는 링크의 두 인터페이스를 같은 서브넷으로 |
| 케이블을 뽑았는데 다른 라우터가 여전히 그쪽으로 보냄 (RIP) | 스위치 너머의 이웃이 사라진 경우: 내 링크는 살아 있어 모른다. 실제 RIP 는 180초 timeout 으로 알아채지만 이 시뮬레이터는 주기 광고가 없다 | 라우터끼리 직접 잇거나, 그 라우터의 RIP 를 껐다 켜서 다시 광고하게 한다 |
| `No route … 스태틱 라우팅을 추가하세요` (NAT 박스) | NAT 박스 뒤에 게이트웨이가 더 있어, 역변환한 응답을 보낼 안쪽 경로를 모름 | NAT 박스 스태틱 라우팅에 `192.168.0.0/16 via <게이트웨이의 업링크 주소>` 처럼 추가 |
| `ping … 실패: Destination Net Unreachable (X)` / TCP `실패 · Destination Net Unreachable (X)` | 장비 X(게이트웨이·NAT·공유기)의 라우팅 테이블에 목적지로 가는 경로가 없음. X 가 ICMP 로 바로 알려 줘 timeout 을 기다리지 않는다 | X 의 스태틱 라우팅·디폴트 라우트(또는 RIP)를 확인. 공유기면 WAN 주소가 있는지 |
| `… 실패: Destination Host Unreachable (X)` | X 까지는 갔지만 목적지(또는 넥스트 홉) 주소에 ARP 로 답하는 장치가 없음: 주소 오타, 꺼진·케이블 빠진 장치 | 목적지 주소와 그 장치의 케이블·IP 를 확인. 포트 포워딩 대상이 없을 때 바깥 클라이언트도 이 통지를 받는다 |
| `… 해석 중단: DNS 서버에 닿지 않음: Destination Port Unreachable (X)` | DNS 서버로 적은 X 가 DNS 서비스를 켜지 않아 UDP 53 이 닫혀 있음 | X 의 서비스에서 DNS 서버를 켜거나, DNS 칸(또는 DHCP 의 DNS 서버 옵션 6)을 실제 DNS 서버로 |
| `사설 주소 … 는 인터넷에서 라우팅되지 않음 → 드롭` (인터넷) | NAT 없이 사설 주소가 밖으로 나감 (게이트웨이만 있고 NAT 없음) | 인터넷 앞에 NAT 박스나 라우터를 둔다 |
| `NAT 테이블에 없는 … → 드롭. 내부에서 시작하지 않은 통신은 들어올 수 없음` | 바깥에서 먼저 시작한 통신 | 정상 동작. NAT 의 성질 |
| `바깥에서 안쪽 주소 … 로 온 패킷 → 드롭` | 바깥에서 사설 주소를 직접 찍음 | 정상 동작 |
| 안에서 한 번 연결한 뒤 바깥의 다른 클라이언트가 같은 공인 포트로 들어옴 (`nat.restore`) | 이 시뮬레이터의 NAT 는 endpoint-independent(full cone) 매핑: 한 번 열린 공인 포트는 상대를 가리지 않는다. 가정용 공유기의 흔한 동작 | 정상. 막으려면 방화벽 인바운드 규칙 + Stateful 검사 |
| `ping … timeout: 2000ms 동안 응답 없음 (Request timed out)` | ARP 는 됐지만 응답이 안 옴: 중간 장치에 경로 없음(No route), 케이블 손실 실험, 상대가 드롭 | 중간 장치(라우터/게이트웨이/NAT)의 로그에서 드롭 문구를 찾는다 |
| `프레임이 스위치 16개를 넘게 돌았음` / `같은 프레임을 … 다시 받음 → L2 루프` | 두 장치 사이 케이블 2개, 스위치 삼각형 등 L2 루프 | 중복 케이블 제거. 실제 네트워크는 STP 가 막는다 |
| `이벤트가 폭주해 일시정지했습니다` (토스트) | 위 루프가 심해 시뮬레이션이 스스로 멈춤 | 루프 케이블을 지우고 재생 |

## traceroute (진단의 "경로" 버튼)

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 마지막 홉 뒤에 `!N` / `!H` 가 붙고 끝남 | 그 홉 장치가 Destination Unreachable 을 돌려줌: `!N` = 경로 없음, `!H` = 목적지 주소에 ARP 응답 없음 (실제 traceroute 와 같은 표기) | `!N` 이면 그 장치의 라우팅을, `!H` 면 목적지 장치와 주소를 확인 |
| `traceroute X 실패: 16 홉 안에 도달하지 못함` (홉이 `*` 로 이어짐) | `*` 가 시작된 다음 장치가 패킷을 드롭 — No route(`ip.no-route`), 방화벽(`fw.deny`), 인터넷이 사설 주소를 드롭 | 마지막으로 응답한 홉의 **다음 장치** 로그를 본다. 스태틱 라우팅·디폴트 라우트, 방화벽 규칙, 대상이 사설 주소인지 확인 |
| `traceroute X 실패: ARP timeout · 응답 없음 (첫 홉 G …)` | 게이트웨이 주소 G 를 가진 장치가 같은 세그먼트에 없음 | 호스트의 게이트웨이 주소와 케이블(스위치 포트)을 확인 |
| `traceroute X 실패: 게이트웨이 없음` | 다른 서브넷인데 호스트에 게이트웨이가 없음 | IP 설정에 게이트웨이를 넣거나 DHCP 서버의 게이트웨이 옵션을 채운다 |
| `… 새 traceroute 시작으로 취소` / `링크 다운` / `주소 변경` | 진행 중에 다시 시작했거나 링크·주소가 바뀜 | 정상. 다시 실행 |
| 2번째 홉부터 `*` 인데 ping 은 됨 (`fw.deny … Time Exceeded`) | 라우터 방화벽이 인바운드 ICMP 를 막고 Stateful 검사가 꺼져 있어 라우터의 오류 통지가 차단됨 | 방화벽의 Stateful 검사를 켜거나 인바운드 ICMP 허용 규칙 추가 |
| `ping X 실패: TTL 초과` (`icmp.ttl-received` "라우팅 루프 의심") | 두 라우터의 스태틱 라우팅·디폴트 라우트가 서로를 가리켜 패킷이 맴돎 | 두 장치의 경로에서 X 로 가는 항목이 서로를 가리키는지 확인하고 한쪽을 고친다 |

## 이름(google.com, web.home)이 안 된다

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `… 찾을 수 없음: DNS 서버가 설정되지 않음` | 호스트에 DNS 가 없음 (수동 설정에서 비웠거나, DHCP 서버가 DNS 를 안내하지 않음) | 수동이면 DNS 칸 입력. 자동이면 DHCP 서버(라우터는 자동으로 자기 주소, 호스트 서버는 "DNS 서버 (옵션 6)" 칸) 확인 |
| `DNS timeout: 서버 … 가 2번 물어도 응답 없음` | DNS 서버 주소가 틀리거나 경로가 없음, 또는 그 호스트의 DNS 서버 서비스가 꺼짐 | 서버 주소 확인, 그 서버로 ping 이 되는지 확인, 서버의 "DNS 서버" 토글 |
| `DNS 응답: … 없는 이름 (NXDOMAIN)` | 서버 레코드에 없고 업스트림 DNS 도 모르는 이름 | 서버 레코드 추가. 공개 이름은 google.com, example.com, naver.com, github.com, cloudflare.com 만 등록돼 있음 |
| `DNS 서버가 업스트림 서버 응답을 받지 못함 (SERVFAIL)` / 라우터 `업스트림 DNS … timeout (응답 없음)` | 라우터 포워더나 DNS 서버가 업스트림 DNS(8.8.8.8)에 못 닿음: 인터넷 미연결, WAN 주소 없음 | 인터넷 노드 연결과 WAN/outside 주소 확인 |
| `DNS 포워더가 꺼져 있음` | 라우터의 DNS 포워더 토글이 꺼짐 | 켜거나 호스트에 8.8.8.8 을 직접 설정 |
| `DNS 질의를 받았지만 DNS 서버 서비스가 꺼져 있음` | 호스트를 DNS 로 지정했는데 그 호스트의 서비스가 꺼짐 | 서비스에서 DNS 서버 켜기 |

## 바깥에서 들어오는 연결 (포트 포워딩)

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `NAT 테이블에 없는 TCP 포트 80 → 드롭 … (포트 포워딩 규칙을 추가하면 열 수 있음)` | 바깥에서 시작한 연결에 규칙이 없음 | 라우터/NAT 박스의 포트 포워딩에 `공인 :80 → 내부 서버:80` 추가 |
| 규칙은 있는데 인터넷 쪽 클라이언트가 `실패` | 내부 서버 주소가 틀리거나 서버의 웹 서비스가 꺼짐, 또는 NAT 박스 뒤 라우터로 가는 스태틱 라우팅 없음 | 규칙의 주소·포트, 서버의 웹 서버 토글, NAT 박스 스태틱 라우팅 확인 |
| `RST 수신 … 그 포트를 듣는 서비스가 없음` (내부 서버) | 포워딩은 됐지만 서버가 그 포트를 안 듣는다 | 서버의 서비스 토글 |

## NAT 종류 · P2P (홀 펀칭) · 헤어핀 NAT

| 증상 / 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `Port-restricted cone NAT: … 매핑은 있지만 안에서 … 먼저 보낸 적이 없음 → 드롭` (Restricted·Symmetric 도 같은 꼴) | 매핑은 있어도 NAT 종류가 "안에서 먼저 보낸 상대" 에게서 온 것만 들인다 | 정상(홀 펀칭 중 처음 몇 개는 이렇게 막힌다). 안에서 그 상대에게 먼저 보내게 하거나 NAT 종류를 full cone 으로 |
| P2P `홀 펀칭 6번 동안 상대에게서 아무것도 들어오지 않음 … → TURN 서버 … 에 릴레이 주소를 요청` → `연결됨 (TURN 릴레이 경유)` | 한쪽이 symmetric NAT(통신사 CGNAT 등) — STUN 이 알려 준 포트가 상대에게는 맞지 않는다 | 정상 동작(릴레이). 직접 잇고 싶으면 반대쪽 NAT 를 full cone 으로 (symmetric ↔ symmetric·port-restricted 는 직접 안 됨) |
| `P2P 연결 못 함: 시그널링 서버에 아직 등록되지 않음` | 주소를 아직 못 받았거나 인터넷에 닿지 않음 | 주소·기본 게이트웨이·공유기 WAN 을 확인하고 잠시 뒤 다시 |
| `시그널링 서버 … 에 등록하지 못함 (응답 없음 3번) … 10초마다 다시 시도` | 인터넷 노드까지 경로가 없음, 또는 사설 주소 그대로 나감(NAT 없음) | 경로와 NAT 확인. 고친 뒤 "+10초" 로 시간을 흘리거나 바로 P2P 연결을 누르면(먼저 등록하고 이어서 연결) 된다 |
| `P2P 연결 실패 (상대 X): X 가 다른 상대와 연결 중이라 거절함 (busy)` | 상대가 이미 다른 사람과 연결돼 있거나 연결하는 중 — 한 번에 한 상대만 | 상대 쪽에서 지금 상대와의 연결을 끝내거나(다른 상대에게 연결) 잠시 뒤 다시 |
| `P2P 연결 실패 (상대 X): 상대 "X" 가 시그널링 서버에 등록돼 있지 않음` | 상대 이름이 틀렸거나 상대의 P2P 앱이 꺼져 있음 | 상대 장치의 서비스 → P2P 앱 이름을 확인 |
| `헤어핀 NAT 꺼짐: 안쪽 … 가 바깥 주소 …:포트 로 접속 → … 드롭` | 포트 포워딩은 바깥에서 온 연결에만 적용된다. 안에서 자기 공인 주소(도메인)로 가면 NAT 가 되돌려 주지 않는다 | 공유기·NAT 박스의 NAT 종류 섹션에서 헤어핀 NAT 를 켜거나, 안에서는 서버의 사설 주소로 접속 |
| 헤어핀으로 접속한 서버가 본 상대 주소가 공유기 LAN 주소 | 헤어핀은 출발지도 장비의 안쪽 주소로 바꾼다 — 그래야 응답이 장비를 거쳐 되돌아간다 | 정상 |

## 방화벽

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `방화벽 차단: 아웃바운드/인바운드 … — 규칙 N (…) → 드롭` | 그 라우터/게이트웨이의 규칙 N 에 걸림 | 규칙을 지우거나 순서를 바꾼다(위가 먼저). 허용 규칙을 차단 규칙보다 위에 |
| `방화벽 차단: … — 일치하는 규칙 없음, 기본 정책 차단` | 기본 정책이 차단인데 허용 규칙이 없다 | 필요한 통신의 허용 규칙 추가(예: 아웃바운드 TCP 80) 또는 기본 정책을 허용으로 |
| 안에서 시작한 ping/TCP 의 **응답**이 `방화벽 차단` | Stateful 검사가 꺼져 있어 응답도 "인바운드" 규칙에 걸림 | Stateful 검사 켜기. 실제 방화벽의 ESTABLISHED 허용과 같다 |
| `… 상 차단이지만, 안에서 시작한 통신의 응답이라 Stateful 검사로 허용` | 정상. 규칙엔 걸리지만 응답이라 통과 | 응답까지 막고 싶으면 Stateful 검사를 끈다 |
| 포트 포워딩은 됐는데 서버에 안 닿음 | `nat.forward.rule` 뒤에 `방화벽 차단 … 인바운드 TCP …:80` | 방화벽에 인바운드 TCP 80 허용 규칙을 차단 규칙 위에 |
| 방화벽 장비(fw) 뒤 서버에 ping 이 `방화벽 차단: 인바운드 ICMP …` | 투명 방화벽의 인바운드 = outside(위) 포트로 들어온 것. 서버를 inside(아래)에 두면 서버로 가는 것이 인바운드 | 규칙 방향을 확인하거나 케이블의 위/아래를 바꾼다 |
| 방화벽 장비가 ping 에 안 잡히고 traceroute 홉에도 없음 | 정상. 투명 방화벽은 IP 가 없다 | 규칙이 도는지는 fw 장치의 로그(`fw.allow`/`fw.deny`)로 본다 |
| 방화벽 장비 뒤(inside)의 호스트가 `DHCP 실패` 이고 fw 로그에 `방화벽 차단: 인바운드 UDP …:67` | 기본 정책 차단인데 DHCP 허용 규칙이 없다. ARP 는 L2 라 통과하지만 DHCP 는 IP(UDP) 라 규칙 대상 | 허용 · 양방향 · UDP · 포트 67 과 68 규칙을 차단 규칙 위에 |
| 방화벽 장비의 한쪽 케이블만 꽂았더니 `… 에 케이블이 없음 → 드롭` | 투명 방화벽은 반대 포트로만 내보낸다 | outside·inside 둘 다 케이블 연결 |
| 게이트웨이에서 서브넷 간 통신이 "인바운드/아웃바운드" 규칙에 안 걸림 | 방향은 업링크(if0/outside/WAN) 기준이라 안쪽 서브넷끼리는 "양방향" 만 해당 | 서브넷 간 규칙은 방향을 "양방향" 으로 하고 출발지/목적지로 구분 |

## 무선 (Wi-Fi)

| 로그 문구 / 화면 | 원인 | 고치는 법 |
|---|---|---|
| 스마트폰에 `무선 연결 없음`, 인스펙터 "SSID … 를 송출하는 AP 나 공유기가 없습니다" | SSID 오타이거나 기지가 없음 | 단말 SSID 와 AP/공유기 SSID 를 맞춘다 (대소문자 구분) |
| "SSID … 의 무선이 꺼져 있습니다" | 공유기 무선 토글이 꺼짐 (기본값 꺼짐) | 공유기 → 무선(Wi-Fi) 켜기. 무선 AP 장치는 기본 켜짐 |
| "전파 범위 밖입니다" | 단말이 기지 중심에서 300px 넘게 떨어짐 (캔버스의 점선 원 밖) | 단말을 원 안으로 끌어오기 |
| "범위 안의 기지 … 에 빈 무선 슬롯이 없습니다" | 기지당 단말 8대 한도(AP·공유기 모두) | 단말을 줄이거나 AP 를 하나 더 두고 범위를 나눈다 |
| `무선 연결 변경: 다른 기지/슬롯으로 옮겨 붙음 → 다시 연결` | 더 가까운 기지로 로밍(끌어서 옮김) | 정상. 새 기지에서 DHCP 로 새로 임대받는다 |
| `무선 연결 실패: … → 다음 변경 때 다시 시도` | 슬롯이 아직 옛 링크에 잡혀 있는 등 일시적 충돌 | 단말을 살짝 옮기거나 SSID 를 다시 입력하면 재시도된다 |
| `무선 연결 끊김 (범위 밖이거나 …)` 뒤 `임대 주소 … 해제` | 끌어서 범위를 벗어남 | 정상. 다시 들어오면 재연결 + DHCP 새 임대 |
| AP 에 붙었는데 주소를 못 받음 | AP 의 eth0 에 케이블이 없음 (AP 는 브리지일 뿐, DHCP 서버가 아님) | AP eth0 을 스위치/공유기에 케이블로 연결 |
| 단말끼리 ping 이 AP 를 거침 (`단말 ↔ 단말 중계`) | 정상. 무선 단말은 서로 직접 통신하지 않고 AP 가 중계한다 | — |
| 노트북 `wlan0 연결됨 → 지금 쓰는 유선(eth0) 가 우선이라 대기`, 캔버스의 회색 점선 | 유선 케이블이 꽂혀 있어 Wi-Fi 는 붙어만 있음 (유선 우선) | 정상. 케이블을 빼면 Wi-Fi 로 넘어간다 |
| 노트북 `eth0 링크 다운` 뒤 `Wi-Fi(wlan0) 로 전환: 다른 NIC 라 MAC 이 … 로 바뀜 → DHCP 로 주소를 새로 받는다`, 주소가 바뀌고 열려 있던 연결은 `링크 다운` 으로 실패 (케이블을 꽂아 돌아올 때는 `NIC 전환`) | NIC 마다 MAC 이 달라 DHCP 서버는 다른 기기로 보고 다른 주소를 준다. 출발지 주소가 바뀌니 TCP 연결은 끊긴다 | 정상. 다시 연결한다 (VPN 은 새 주소로 스스로 다시 붙는다). 케이블을 다시 꽂으면 유선이 쓰던 주소를 INIT-REBOOT 로 되찾는다 |
| 노트북 케이블을 뺐더니 `링크 다운 (다른 NIC 도 연결돼 있지 않음)` | Wi-Fi 가 꺼져 있거나 SSID 기지가 범위 밖 | 노트북 "개요" 탭의 Wi-Fi 를 켜고 SSID 를 맞춘다 |
| `전파로 송출 … 다른 단말도 전파는 받지만 암호화되어 읽지 못한다` | 정상. 무선은 같은 채널의 모두에게 닿는다 | — |

## VLAN

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `… 는 트렁크인데 태그 없는 프레임 → 드롭 (상대 포트도 트렁크여야 함)` | 케이블 한쪽만 트렁크 | 양쪽 스위치 포트를 모두 트렁크로, 또는 둘 다 액세스로 |
| `… 는 액세스 포트(VLAN n)인데 VLAN m 태그 프레임 → 드롭` | 트렁크에서 온 태그 프레임이 액세스 포트로 들어옴 | 그 포트를 트렁크로 |
| 호스트 `VLAN n 태그가 달린 프레임 → 호스트는 태그를 이해하지 못해 드롭` | 호스트가 트렁크 포트에 꽂힘 | 호스트 쪽 스위치 포트를 액세스(VLAN 번호)로 |
| 같은 서브넷 주소인데 `ARP timeout` | 두 호스트가 다른 VLAN 포트에 꽂힘 (브로드캐스트 도메인이 다름) | 같은 VLAN 으로 맞추거나, 서브넷을 나누고 게이트웨이로 잇는다 |
| 게이트웨이 `VLAN n 태그 프레임 → 해당 서브 인터페이스 없음 → 드롭` | 트렁크로 들어온 VLAN 에 서브 인터페이스가 없음 | 게이트웨이의 그 인터페이스에 `VLAN n` 서브 인터페이스(주소) 추가 |
| 다른 VLAN 으로 ping 이 `게이트웨이 설정 없음` / `ARP timeout` | 호스트 게이트웨이가 그 VLAN 의 서브 인터페이스 주소가 아님 | 호스트 게이트웨이 = 자기 VLAN 서브 인터페이스 주소 (예: VLAN 10 → 192.168.10.1) |
| 공유기 `LAN 포트는 태그를 이해하지 못해 드롭` | 트렁크 포트를 공유기에 꽂음 | 공유기는 VLAN 미지원. 게이트웨이 장치를 쓰거나 스위치 포트를 액세스로 |
| 트렁크로 오가는데 태그 없는 프레임이 드롭됨 | 이 시뮬레이터에는 네이티브 VLAN(태그 없는 프레임을 VLAN 1 로 취급)이 없다 | 트렁크에는 스위치·게이트웨이 서브 인터페이스만 꽂고, 호스트는 액세스 포트에 |
| 방화벽 규칙에 포트를 넣었는데 ping 이 그대로 통과/차단됨 | 포트는 TCP/UDP 에만 있어 프로토콜 `모든 프로토콜`+포트 규칙은 ICMP 에 일치하지 않는다 | ICMP 를 막으려면 프로토콜 `ICMP(ping)` 규칙을 따로 둔다 |

## TCP 연결이 안 된다 / 끊긴다

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `RST 수신: … 그 포트를 듣는 서비스가 없음 → 연결 거부` | 대상의 서비스(웹 서버 80)가 꺼짐, 또는 포트 번호가 다름 | 대상 장치의 서비스 토글 켜기, 포트 확인 |
| TCP 연결 표에 `실패 · timeout · SYN 에 응답 없음 (재전송 3회)`, 로그 `TCP timeout: SYN 을 3번 다시 보냈지만 SYN-ACK 없음` | 상대가 거부(RST)한 게 아니라 **중간에서 조용히 드롭**됨: 방화벽 차단, NAT 에 포트 포워딩 규칙 없음(`NAT 테이블에 없는 TCP 포트 … → 드롭`), 경로 없음(No route) | 드롭한 장치의 로그(`fw.deny`, `nat.miss`, `ip.no-route`)를 찾아 규칙·포워딩·경로를 고친다 |
| `실패 · timeout · ACK 없음 (재전송 3회)` (연결은 됐다가 중간에) | 데이터 구간에서 손실(케이블 손실률/손실 실험) 또는 도중에 경로가 끊김 | 케이블 손실률을 0 으로, 또는 ping 으로 먼저 경로를 확인 |
| `순서가 어긋난 데이터 … 중간 세그먼트가 손실됨` | 세그먼트 하나가 손실되어 뒤 세그먼트가 먼저 도착 | 정상 복구 과정. 서버가 timeout 후 재전송한다 |
| `종료된 연결로 FIN·ACK 가 다시 옴 → ACK 재전송` | 내 마지막 ACK 이 손실됨 | 정상 복구 과정 |
| `주소 변경` 으로 연결 실패 | 전송 중 IP 모드/주소를 바꿈 | 정상. 다시 연결 |

## HTTPS (포트 443)

| 문구 | 원인 | 고치는 법 |
|---|---|---|
| 클라이언트 `실패 · 연결 거부 (RST)` (포트 443) | 그 서버가 443 을 열지 않음 | 서버의 서비스에서 HTTPS 서버(TCP 443)를 켠다 |
| 클라이언트 `실패 · TLS 핸드셰이크 실패 · 상대가 TLS 로 답하지 않음` (curl: `wrong version number`) | 443 에서 TLS 가 아니라 평문 HTTP 로 답하는 것이 들음(프록시 포트를 443 으로 둠 등) | 그 포트에 HTTPS 서버가 있는지 확인. 프록시는 보통 3128 |
| 서버 `TLS 가 아닌 평문 요청(…)이 HTTPS 포트 443 으로 옴 → 400 Bad Request` | HTTP 프록시 설정이 이 서버의 443 을 가리켜 CONNECT 가 평문으로 옴 | 그 장치의 HTTP 프록시 주소를 실제 프록시로 고친다 |
| 클라이언트 `실패 · timeout · TLS ServerHello 없음` | ClientHello 는 전달됐는데 서버 쪽 응답이 10초 동안 없음 | 서버·터널 너머 대상까지의 경로를 확인 |
| 서버 `TLS ClientHello 가 평문 포트 80 으로 옴 → … 400 Bad Request`, 클라이언트 `TLS 핸드셰이크 실패` | HTTPS 를 평문 HTTP 포트로 넘김 (L4 로드밸런서 443 → 백엔드 80, 포트 포워딩 443 → 80 등) | 백엔드·포워딩 대상 포트를 443(HTTPS 서버)으로, 또는 L7 로드밸런서가 TLS 를 풀게 한다 |
| 클라이언트 `실패 · 상대가 RST 로 끊음 (응답을 다 받기 전)` | 응답을 끝까지(FIN) 받기 전에 상대가 연결을 끊음 — 프록시 터널이면 프록시와 대상 사이가 끊겨 프록시가 끊은 것 | 상대(또는 터널 너머 대상)까지의 링크·경로 확인 |
| 로드밸런서(L7) 443 인데 백엔드 연결이 평문 80 | 정상 동작. L7 은 TLS 를 풀어(TLS 종료) 요청을 보고, 백엔드에는 백엔드 포트대로 연결한다(80 = 평문, 443 = 다시 암호화). L4 는 TLS 를 풀지 않고 그대로 넘긴다 | 백엔드까지 암호화하려면 백엔드 포트를 443 으로 |

## 로드밸런서

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 클라이언트가 `받음 200B`, LB 로그 `… → 502 Bad Gateway` (`백엔드가 하나도 없음` / `살아 있는 백엔드가 없음`) | 백엔드 목록이 비었거나, 목록의 백엔드가 모두 거부·timeout 으로 빠져 있음 | 로드밸런서 → 백엔드에 뒤 서버 주소·포트를 넣고, 그 서버들의 웹 서비스가 켜져 있는지 확인. 빠진 백엔드는 10초 뒤 다시 시도된다 |
| `백엔드 X 실패 (연결 거부 (RST)) → 10초 동안 빼고 다음 백엔드로` | 그 서버가 해당 포트를 열지 않음 (웹 서버 꺼짐, 포트 번호 불일치) | 백엔드 서버의 서비스를 켜거나 LB 의 백엔드 포트를 맞춘다. 구성 검사 `lb.backend-closed` 가 미리 알려 준다 |
| `백엔드 X 실패 (timeout · SYN 에 응답 없음 …)` | 백엔드 주소에 장비가 없거나(ARP timeout), 경로·방화벽에서 드롭 | 주소 오타, 케이블, LB 와 백엔드 사이 경로를 확인 |
| 로드밸런서 표 `DOWN (헬스 체크: 연결 거부 …)`, 로그 `헬스 체크: 백엔드 X 3번 연속 실패 → DOWN` | 액티브 헬스 체크가 2초마다 연결해 보다 3번 연속 실패 — 그 포트를 닫았거나(RST) 응답이 없음(timeout) | 백엔드 서버의 서비스를 켜면 2번 연속 응답 뒤 UP. 체크는 시간이 흐를 때만 돌므로 요청을 보내거나 "+10초" |
| 백엔드를 껐는데 첫 요청이 그 백엔드에서 실패하고 다음 백엔드로 넘어감 | 액티브 헬스 체크가 꺼져 있으면 패시브만 — 누군가의 요청이 실패해야 뺀다 | 로드밸런서 설정에서 액티브 헬스 체크를 켜고 시간을 흘려보내면 요청 전에 뺀다 |
| 클라이언트 `HTTP 508 Loop Detected`, 구성 검사 `lb.loop` | 로드밸런서끼리 서로를(또는 자기 자신을) 백엔드로 둠 → 요청이 LB 사이를 돈다. 요청마다 거친 LB 수(Via)가 5개가 되면 끊는다 | 백엔드 목록에서 로드밸런서를 빼고 실제 웹 서버를 넣는다 |
| 클라이언트 `실패 · timeout · 응답 없음 (요청은 전달됨, 10초)` | 상대(로드밸런서)가 요청은 받았지만 응답을 못 줌: LB 의 주소가 바뀌거나 링크가 끊겨 요청이 중단됨 | LB 의 주소·케이블을 확인하고 다시 연결. 앞단 LB 에게는 이 경우가 백엔드 실패가 되어 다음 서버로 넘어간다 |
| 클라이언트 `실패 · timeout · 응답이 중간에 멈춤 (…B 받은 뒤 10초)` | 응답을 일부 받다가 10초 동안 더 오지 않음: 상대(또는 그 뒤 서버)가 보내다 끊김 | 상대의 케이블·경로를 확인하고 다시 연결 |
| L4 모드에서 클라이언트 `실패 · 연결 거부 (RST)`, 로드밸런서 `백엔드 … 가 RST 로 거부` | 고른 백엔드가 그 포트를 열지 않음. L4 는 이미 시작한 연결을 다른 백엔드로 옮기지 못한다 (L7 은 대신 다시 보냄) | 백엔드 서비스·포트 확인. 다시 연결하면 빼 둔 백엔드를 건너뛴다 |
| L4 모드에서 첫 연결이 잠깐 늦게 성공, 로드밸런서 `백엔드 … 실패 (SYN 에 응답 없음 …)` | 고른 백엔드가 SYN 에 답하지 않음 (꺼짐·케이블) → 클라이언트의 SYN 재전송 때 다른 백엔드로 옮김 | 죽은 백엔드를 확인. 10초 동안은 건너뛴다 |
| 세션 고정인데 한 서버로만 몰림 | 정상: 같은 출발지 IP 는 계속 같은 백엔드. 클라이언트가 하나이거나, 여러 사람이 NAT·프록시 뒤라 한 주소로 보이면 한 서버만 쓴다 | 사람마다 나누려면 세션 고정을 쿠키로(L7). 쿠키는 브라우저마다라 NAT 뒤에서도 나뉜다 |
| 쿠키 세션 고정인데 요청마다 다른 서버, 구성 검사 `lb.cookie-l4` | L4 주소 변환은 HTTP 를 보지 않아 쿠키를 넣지도 읽지도 못함 | 세션 고정을 출발지 IP 로 바꾸거나 방식을 L7 프록시로 |
| 쿠키 세션 고정인데 `Set-Cookie` 를 또 받고 서버가 바뀜, 로그 `쿠키가 가리키는 … 는 빠져 있거나 없어 다시 고름` | 쿠키의 백엔드가 실패로 빠져 있거나 목록에서 지워짐 | 정상 동작: 다른 백엔드를 골라 새 쿠키를 준다. 그 백엔드를 살리면 새로 오는 브라우저에게 다시 나뉜다 |
| 백엔드 서버 로그의 상대 주소가 클라이언트가 아니라 LB 주소 | 정상 동작. 리버스 프록시는 LB 가 대신 연결한다 | 실제 서비스는 X-Forwarded-For 헤더로 원래 클라이언트를 알린다 (이 시뮬레이터는 응답의 "응답 …" 표시로 반대 방향만 보여 줌) |

## 포워드 프록시

| 문구 | 원인 | 고치는 법 |
|---|---|---|
| 클라이언트 `HTTP 403 Forbidden`, 프록시 `… 는 차단 목록(…)에 있음` | 대상 이름(하위 이름 포함)이나 주소가 프록시의 차단 목록에 있음 | 의도한 차단이면 정상. 아니면 프록시 → 차단 목록에서 뺀다 |
| 클라이언트 `HTTP 503 Service Unavailable`, 프록시 `… 의 이름을 주소로 바꾸지 못함` | 이름은 PC 가 아니라 프록시가 찾는다. 프록시의 DNS 설정이 없거나, 방화벽이 프록시의 DNS 질의를 막음 | 프록시 서버의 DNS(수동이면 DNS 칸)와 방화벽 규칙을 확인 |
| 클라이언트 `HTTP 503 Service Unavailable`, 프록시 `… 에 연결하지 못함 (…)` | 대상이 그 포트를 열지 않음(RST)이거나 경로·방화벽에서 드롭(timeout) | 대상 주소·포트, 프록시에서 대상까지의 경로와 방화벽 규칙을 확인 |
| 클라이언트 `HTTP 400 Bad Request`, 프록시 `대상(절대 URI)이 없음` | HTTP 프록시 설정 없이 프록시 주소:포트로 직접 접속함 | 그 장치의 HTTP 프록시를 켜고, 진단에는 원래 대상(예: example.com:80)을 넣는다 |
| 프록시 설정이 있는데 SSH·ping 이 막힘 | 프록시는 웹(포트 80·443)만 맡는다. 나머지는 직접 나가다 방화벽에 막힌다 | 정상 동작(프록시로만 나가는 사무실). 필요하면 방화벽에 그 트래픽을 허용 |
| HTTPS(443) 인데 프록시 기록에 경로가 없고 `CONNECT 호스트:443` 만 남음 | 정상 동작. HTTPS 는 CONNECT 로 터널만 열고 TLS 는 PC 와 대상이 직접 한다 — 프록시는 이름(CONNECT·SNI)과 길이만 본다 | 경로 단위로 막으려면 실무에서는 TLS 가로채기(SSL 복호화)를 쓴다(이 시뮬레이터에는 없음). 도메인 단위 차단은 차단 목록으로 된다 |
| 클라이언트 `HTTP 503 Service Unavailable`, 프록시 `CONNECT … 에 연결하지 못함`, access.log `NONE/503` | CONNECT 대상이 443 을 열지 않음(RST)이거나 경로·방화벽에서 드롭(timeout) | 대상 주소, 프록시에서 대상까지의 경로와 방화벽 규칙을 확인 |
| 클라이언트 `HTTP 405 Method Not Allowed` (HTTPS) | HTTP 프록시 주소가 프록시가 아니라 일반 웹 서버를 가리킴(CONNECT 를 모름), 또는 L7 로드밸런서(nginx 식은 CONNECT 를 받지 않음)를 가리킴 | 프록시 주소·포트를 맞추고, 프록시 팜 앞의 로드밸런서는 L4 모드로(구성 검사 `proxy.l7-connect`) |
| 클라이언트 `실패 · timeout · 프록시의 CONNECT 응답 없음` | 프록시가 대상에 연결하느라 10초 넘게 답하지 않음 | 프록시에서 대상까지의 경로를 확인 |
| 터널이 열린 뒤 클라이언트 연결이 `상대가 RST 로 끊음`, 프록시 `CONNECT … 터널 반대편 연결 실패` | 프록시와 대상 사이 연결이 끊김(재전송 timeout 등) → 프록시가 클라이언트 쪽도 끊는다 | 프록시에서 대상까지의 링크·경로 확인 |
| 클라이언트 `HTTP 503 Service Unavailable`, 프록시 `… 의 응답이 중간에 끊김 (…B 받음, timeout · 응답이 중간에 멈춤 …)` | 대상(또는 그 뒤의 서버)이 응답을 보내다 끊김. 받은 뒤 10초 동안 더 오지 않으면 포기한다 | 대상 서버·케이블·경로 확인 |
| 프록시 access.log `TCP_MISS_ABORTED/000` | 프록시가 대상에서 받아 오는 동안 클라이언트가 먼저 끊음(클라이언트의 10초 timeout 등) | 대상이 느리거나 멈췄는지 확인 |
| 구성 검사 `proxy.port-clash` | 같은 장비에서 로드밸런서와 프록시가 같은 포트 → 로드밸런서가 먼저 받아 요청 대상을 무시하고 자기 백엔드로 보냄 | 프록시 포트(보통 3128)나 로드밸런서 포트를 바꾼다 |
| 클라이언트 `실패 · 연결 거부 (RST)`, 구성 검사 `proxy.not-running` | HTTP 프록시 주소의 장비가 그 포트에서 프록시를 돌리지 않음(꺼짐·포트 다름) | 프록시 서버의 서비스에서 프록시를 켜거나 HTTP 프록시 포트를 맞춘다(보통 3128) |
| 대상 서버 로그의 상대 주소가 PC 가 아니라 프록시(인터넷 쪽은 공유기 공인 주소) | 정상 동작. 포워드 프록시는 클라이언트를 대신해 연결한다 | 실제 프록시는 X-Forwarded-For 로 원래 주소를 알리기도 한다(이 시뮬레이터에는 없음) |

## VPN

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 구성 검사 `VPN 상대 대역이 우리 LAN 과 겹침` | 두 사무실이 같은 사설 대역(예: 둘 다 192.168.0.0/24)을 씀 → 어느 쪽 주소인지 구분할 수 없다 | 한쪽 대역을 바꾼다 (192.168.1.0/24 와 192.168.2.0/24 처럼) |
| `VPN 패킷 수신 … → 풀지 않고 드롭: 안쪽 출발지 … 가 상대 대역이 아님` / 구성 검사 `vpn.one-way` | 상대 장비의 "상대 쪽 사설 대역" 에 우리 LAN 이 없거나, 우리 쪽 목록에 상대 LAN 이 없음 (한쪽만 설정) | 양쪽 VPN 설정을 짝으로: A 의 대역 목록 = B 의 LAN, B 의 대역 목록 = A 의 LAN |
| 구성 검사 `상대 … 가 VPN 을 켜지 않음` / 상대 로그 `UDP 포트 51820 …` | 상대 장비의 VPN 이 꺼짐 | 상대에서도 VPN 을 켜고 이쪽 공인 주소를 상대 주소로 |
| `VPN: 상대 … 로 가는 바깥 경로가 없어 터널로 보낼 수 없음` | 상대 공인 주소로 갈 경로(디폴트 라우트)가 없음 | outside 의 게이트웨이(디폴트 라우트)나 상대 공인 주소를 확인 |
| `IPsec 터널을 맺지 못함: IKE_SA_INIT 응답 없음 (timeout …)` | 상대가 IPsec VPN 을 켜지 않았거나(또는 WireGuard 방식), 상대 공인 주소가 틀렸거나, 상대가 NAT 뒤인데 UDP 500·4500 포워딩이 없음 | 상대 VPN 을 IPsec 으로 켜고 공인 주소 확인. 상대가 NAT 뒤면 그 NAT 에 UDP 500·4500 → VPN 장비 포워딩 |
| `… IKE_AUTH 인증 실패 — 사전 공유 키(PSK)가 다름` / `AUTHENTICATION_FAILED 로 거절`, 구성 검사 `vpn.psk-mismatch` | 양쪽 PSK 가 다름 | 두 장비의 VPN → 사전 공유 키를 똑같이 |
| 구성 검사 `vpn.mode-mismatch` | 한쪽은 WireGuard, 한쪽은 IPsec | 양쪽 방식을 같게 |
| `ESP(IPsec) …: ESP 에는 포트가 없어 NAT 가 … 드롭` | ESP 가 NAT 를 지나려 함 (보통은 NAT 감지로 UDP 4500 을 쓰므로, 방식·설정이 어긋났을 때) | 양쪽 IPsec 설정을 확인. 사이에 NAT 가 있으면 NAT-T(UDP 4500)가 쓰인다 |
| `IPsec ESP 수신 … 드롭: 이 상대와 맺은 IPsec 터널(SA)이 없음` | 설정을 바꿔 터널이 내려간 뒤 상대가 옛 터널로 보냄 | 이쪽에서 한 번 보내면 다시 협상한다 |
| IKE 가 `재전송 2번 뒤 timeout` 인데 상대는 IPsec 을 켰음, 구성 검사 `vpn.natt-closed` | 상대가 NAT 뒤인데 UDP 4500 포워딩이 없음 (NAT 를 감지하면 IKE_AUTH·ESP 가 4500 으로 감) | 상대 NAT 에 UDP 4500 → VPN 장비 포워딩 추가 |
| 상대가 먼저 연 터널이 방화벽에서 `인바운드 ESP … 차단` | 기본 차단 방화벽에 ESP 허용이 없음 | 방화벽 규칙: 인바운드 UDP 500·4500 과 ESP(IPsec) 를 상대 공인 주소에서 허용 |
| `IPsec DPD: 상대 … 응답 없음 (재전송 2번 뒤 timeout) → … SA 삭제` | 상대 장비가 꺼졌거나 경로가 끊김 (또는 방화벽이 UDP 500·4500 을 막음) | 경로를 고치면 터널로 갈 다음 패킷에 다시 협상한다 |
| `IPsec DPD: 상대 … 가 이 터널을 모른다고 알림 (INVALID_SPI …) → SA 삭제` / 상대 쪽 `… 이쪽에 없는 터널 … 을 확인함` | 상대의 설정이 바뀌거나 재시작해 SA 가 사라짐 | 자동: 다음 패킷에 다시 협상 |
| `IPsec: 연결된 터널(SA) 없음 → DPD 를 보내지 않음` | 아직 터널을 맺지 않았거나 이미 지워짐 | 상대 대역으로 ping 을 한 번 보내 터널을 맺은 뒤 누른다 |
| traceroute 가 터널 너머 첫 홉에서 `*` | 상대 VPN 장비가 보낸 Time Exceeded 의 출발지(그쪽 연결 구간 주소)가 이쪽 터널 대역에 없어 AllowedIPs·트래픽 셀렉터로 버려짐 — 실제 장비도 같다 | 정상. 필요하면 그 연결 구간도 터널 대역에 추가 |
| 구성 검사 `vpn.shared-peer` / 한쪽 사무실만 되다가 다른 쪽이 보내면 뺏김 | 두 사이트가 같은 상대에 VPN 을 연결. 상대는 터널 하나만 두고 마지막에 받은 출발지로 답하므로, 나중에 보낸 쪽이 응답을 가져간다 (실제 WireGuard 는 키로 구분하지만 여기엔 키가 없다) | 상대 하나에는 한 사이트만 연결. 사이트가 여럿이면 상대 쪽 터널 장비를 사이트마다 둔다 |
| 방화벽을 켜자 상대 사무실에서 먼저 여는 연결만 `방화벽 차단` | 터널로 나가는 것은 아웃바운드, 터널에서 풀려 들어오는 것은 인바운드로 판정한다. "기본 차단 + 아웃바운드 허용" 이면 이쪽이 연 연결의 응답만(Stateful 검사) 들어온다 | 상대 대역(예: 192.168.2.0/24)에서 오는 인바운드 허용 규칙을 추가 |
| VPN 게이트웨이를 NAT 박스 뒤에 두었는데 상대가 보내면 안 닿음 | 앞의 NAT 박스가 UDP 51820 을 안쪽으로 넘기지 않음 | NAT 박스에 포트 포워딩 UDP 51820 → VPN 게이트웨이 주소. 상대의 "상대 공인 주소" 는 NAT 박스의 공인 주소 |
| 상대 공인 주소를 바꿨는데 이쪽 응답이 예전 주소로 감 | 받은 출발지를 기억하는 엔드포인트 로밍 때문. 상대가 다시 보내기 전까지는 마지막으로 받은 주소로 답한다 | 상대 쪽에서 한 번 보내면(ping) 새 주소를 배운다. 이쪽 VPN 설정의 상대 주소를 바꾸면 기억도 지워진다 |
| 한쪽이 공유기 NAT 뒤인데 반대쪽에서 먼저 보내면 안 됨 | NAT 뒤 쪽은 바깥에서 먼저 들어갈 수 없다 (NAT 의 성질) | NAT 뒤 쪽이 먼저 보내면 반대쪽이 그 출발지로 답한다. 또는 NAT 에 UDP 51820 포트 포워딩 |

## 그 밖에

- **시계가 멈춰 있다**: 패킷이 없고 대기 이벤트도 없으면 시계는 일부러 멈춘다. 동작(ping, 케이블 연결)을 하면 다시 흐른다.
- **일시정지 상태에서 아무 일도 없다**: 상단 ▶ 재생 또는 다음 이벤트(→). Space 로 토글.
- **장치가 캔버스 밖에 있다**: 예제를 다시 불러오면 내용에 맞춰 화면을 잡는다. 휠로 이동, ⌘+휠로 확대·축소.
- **케이블이 안 이어진다** ("빈 포트가 없습니다" / "이미 연결되어 있습니다"): 포트 수 한도(호스트 1, 라우터 5, 스위치 8), 같은 두 장치 사이는 케이블 1개만.

## 이중화 (HA)

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 구성 검사 `ha.vrid-mismatch`, 두 장비 타일이 모두 `HA master` | 짝의 그룹 번호(VRID)가 달라 서로를 짝으로 보지 않음 → 같은 가상 주소를 둘 다 주장 | 두 장비의 그룹 번호를 같게 |
| 구성 검사 `ha.vrid-shared`, 한 쌍이 둘 다 `HA backup` | 서로 다른 이중화 쌍이 같은 세그먼트에서 같은 그룹 번호를 씀 → 네 대가 하나의 선출로 묶임 | 쌍마다 다른 그룹 번호(VRID) |
| 구성 검사 `ha.vip-mismatch` | 짝의 가상 주소가 서로 다름 → 넘어가면 호스트가 쓰던 게이트웨이 주소가 사라짐 | 두 장비의 인터페이스별 가상 주소를 똑같이 |
| 구성 검사 `ha.host-real-gw` | 호스트 게이트웨이가 한 장비의 실제 주소 → 그 장비가 죽으면 따라가지 않음 | 호스트 게이트웨이(또는 DHCP 게이트웨이 옵션)를 가상 주소로 |
| 넘어간 뒤 진행 중이던 TCP 가 timeout, 새 master 에 `NAT 테이블에 없는 …`·`방화벽 차단: 인바운드 …` | 세션 동기화가 꺼져 있어 새 master 는 옛 NAT 매핑·방화벽 흐름을 모름 | 두 장비의 이중화 설정에서 세션 동기화(pfsync)를 켠다. 이미 끊긴 연결은 새로 연결 |
| 구성 검사 `ha.sync-mismatch` | 짝 중 한쪽만 세션 동기화를 켬 | 두 장비 모두 켜거나 끄기 |
| 넘어간 뒤 IPsec 이 잠깐 `SA 없음` 드롭 | 새 master 에는 IPsec 터널이 없음 → 다음 패킷에 다시 협상 | 한 번 더 보내면 복구 |
| 물러난 장비 `IPsec: 이중화 master 에서 물러남 → 터널(SA …)을 지움` / `원격 접속: 이중화 master 에서 물러남 → 붙어 있던 클라이언트 …의 터널을 지움`, 그 장비에서 DPD 를 누르면 `연결된 터널(SA) 없음` | 정상. IPsec SA 는 세션 동기화로 복사되지 않으므로 물러난 쪽이 비우고 새 master 가 다시 협상한다 (들고 있으면 옛 master 의 DPD 에 상대가 "살아 있음" 으로 답해 헷갈린다) | 없음. 사이트 간은 다음 패킷에, 원격 접속 노트북은 새 master 의 INVALID_SPI 를 받고 다시 접속한다 |
| `이중화: VIP 인터페이스의 링크·주소가 모두 준비되지 않아 backup 으로 대기 (우선순위 0)` | 가상 주소를 둔 인터페이스 중 하나라도 케이블·주소가 없음 (인터페이스 추적) | 케이블과 인터페이스 주소 확인 |
| master 가 말없이 죽었는데(케이블 손실 100% 등 링크는 살아 있음) backup 이 이어받지 않음, ping 계속 실패 | 주기 광고가 꺼져 있으면 master 는 변화가 있을 때만 알리므로, 알리지 못한 고장은 backup 이 모른다. 켜져 있어도 시간이 흘러야 Master_Down(3초 + skew)이 끝난다 | 두 장비의 이중화 설정에서 주기 광고를 켜고, ping 을 몇 번 더 보내거나 위의 "+10초" 로 시간을 흘려보낸다 |
| `이중화: master … 의 광고를 3.6초 동안 못 들음 … 말없이 죽은 것으로 보고 이어받음` | 주기 광고를 켠 backup 이 master 의 광고를 Master_Down 동안 못 들음 → master 가 됨 | 정상 동작. 옛 master 가 다시 들리면 우선순위가 높은 쪽이 되찾는다(preempt) |
| 구성 검사 `ha.advert-mismatch`, 두 장비가 master·backup 을 오감 | 한쪽만 주기 광고를 켬 → 켠 backup 은 광고를 기다리다 master 가 되고, 켜지 않은 master 의 답을 들으면 물러나기를 되풀이 | 두 장비 모두 켜거나 끄기 (실제 VRRP 도 광고 간격이 같아야 한다) |

## SSH 세션

| 증상 / 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 세션은 "SSH 세션 열림" 인데 사이 경로가 끊겨 있음 | keepalive 가 없어 조용한 세션은 경로가 끊겨도 모른다 (실제로도 멈춘 SSH 창이 된다) | "연결 해제" 를 눌러 보면 FIN 재전송 끝에 timeout 으로 드러난다. 다시 접속 |
| 이중화가 넘어간 뒤 "연결 해제" 가 `timeout · ACK 없음`, 새 master 에 `방화벽 차단: 인바운드 TCP …` | 새 master 의 Stateful 검사·NAT 테이블에 이 세션이 없음 (세션 동기화 없음) | 새로 접속한다 |
| 클라이언트는 `실패 · 링크 다운` 인데 서버의 TCP 표에는 여전히 `연결됨` | 반쯤 열린 연결: 클라이언트가 사라진 걸 서버는 알 길이 없다 (keepalive 없음) — 실제 서버도 같은 이유로 keepalive·timeout 을 둔다 | 정상 동작. 서버 쪽 연결은 남아 있어도 해가 없다 |
| 구성 검사 `lb.ssh-port` | 로드밸런서가 포트 22 를 받음. 이 로드밸런서는 HTTP 만 나누는 L7 프록시 | 받는 포트를 웹 포트로. SSH 는 서버에 바로 |
| `SSH 키 교환 중` 에서 멈췄다가 `timeout · 응답 없음` | 중간에서 서버 응답이 드롭됨 (방화벽·경로) | 방화벽에서 TCP 22 허용, 경로 확인 |

## 스패닝 트리 (STP)

| 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| `같은 프레임을 … 에서 다시 받음 … L2 루프 감지, 드롭`, 구성 검사 `switch.loop-no-stp` | 스위치끼리 고리로 이었는데 STP 가 꺼진 스위치가 있음 (실제라면 브로드캐스트 폭주) | 고리에 있는 스위치 모두 STP 켜기 |
| `… 는 STP 대체 포트(차단) → 데이터 프레임을 받지 않고 버림` | 정상. 루프를 끊으려고 막은 포트로 들어온 프레임 | 없음. 다른 경로가 끊기면 이 포트가 열린다 |
| 두 스위치를 VLAN 이 다른 케이블 두 가닥으로 이었더니 한 VLAN 이 통째로 끊김 (JSON 으로 만든 경우) | 이 STP 는 한 인스턴스(802.1D CST)라 VLAN 을 구분하지 않고 두 케이블을 고리로 보고 하나를 막는다 (VLAN 마다 따로 도는 PVST·MST 와 다름) | 두 스위치는 트렁크 한 가닥으로 잇는다 |
| 원하지 않는 스위치가 루트 브리지 | 브리지 우선순위가 같으면 MAC 이 작은 쪽이 루트 | 가운데(코어) 스위치의 우선순위를 작게(예: 4096) |

## 원격 접속 VPN

| 증상 / 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 노트북 `원격 접속 실패: IKE_SA_INIT 응답 없음 …`, 구성 검사 `ra.server-off` | 서버 주소가 틀렸거나 그 장비의 원격 접속 VPN 서버가 꺼짐, 또는 UDP 500·4500 이 막힘 | 서버 공인 주소 확인, 서버에서 원격 접속 VPN 켜기. 서버가 NAT 뒤면 그 NAT 에 UDP 500·4500 → 서버 포워딩 (구성 검사는 UDP 500 포워딩 대상을 서버로 본다) |
| `서버가 인증을 거절 (AUTHENTICATION_FAILED)`, 구성 검사 `ra.psk-mismatch` | 노트북과 서버의 사전 공유 키가 다름 | 둘을 같게 |
| `INTERNAL_ADDRESS_FAILURE` | 가상 주소 풀이 다 찼거나 잘못됨 | 서버의 풀 시작·끝 확인 |
| 연결됐는데 사내 서버 SSH 가 timeout, 회사 방화벽 `방화벽 차단: 인바운드 … 10.99.0.x` | 방화벽이 가상 주소 풀에서 들어오는 것을 막음 (터널에서 풀린 패킷은 인바운드) | 방화벽에 "인바운드 · 출발 10.99.0.0/24 → 사내 대역 허용" |
| 연결됐는데 사내 서버의 응답이 안 옴 (안쪽에 라우터가 더 있음) | 안쪽 라우터가 가상 주소 풀(10.99.0.x)로 가는 경로를 모름 | 안쪽 라우터에 "10.99.0.0/24 → VPN 장비" 스태틱 라우팅 |
| 8.8.8.8 은 되는데 사내 대역만 안 됨 / 반대 | split tunnel: 서버가 알려 준 사내 대역만 터널로 간다 | 서버의 "알려 줄 사내 대역" 에 필요한 대역 추가 |
| `원격 접속: 서버가 이 터널을 모른다고 알림 (INVALID_SPI …) → 다시 접속` | 서버 설정이 바뀌었거나 이중화로 넘어가 서버에 이 클라이언트의 터널이 없음 | 자동으로 다시 접속한다. 그사이 보낸 패킷 하나는 사라진다 |
| 노트북 `원격 접속 실패 …` 뒤로 서버를 고쳤는데도 안 붙음 | 실패하면 스스로 다시 시도하지 않음 | 노트북 설정의 "다시 연결" |
| 노트북 `서버가 계정 인증을 거절 (EAP 실패, AUTHENTICATION_FAILED) — 계정 또는 비밀번호가 틀림`, 서버 `계정 인증 실패 (EAP-MSCHAPv2) — 사용자 … 가 계정 목록에 없음` / `… 의 비밀번호가 다름`, 구성 검사 `ra.account-mismatch` | PSK 는 맞았지만 사용자 계정이 서버 목록에 없거나 비밀번호가 다름 (클라이언트에는 어느 쪽인지 알려 주지 않는다 — 서버 로그에서 확인) | 서버의 "사용자 계정 (EAP)" 에 그 사용자를 넣거나, 노트북의 사용자 이름·비밀번호를 목록과 같게 |
| 노트북 `서버가 사용자 계정 인증(EAP)을 요구하는데 이 노트북에 계정이 없음`, 구성 검사 `ra.no-account` | 서버에 계정 목록이 있어 PSK 만으로는 접속할 수 없음 | 노트북의 원격 접속 VPN 에 사용자 이름·비밀번호 |
| 목록에서 지운 사용자가 여전히 접속돼 있음, 서버 `… 의 세션은 끊지 않음 (다시 붙을 때 인증 실패)` | 인증은 접속할 때 한 번이라 이미 맺은 세션은 그대로 (실무와 같음) | 다시 접속하면 막힌다. 바로 끊으려면 서버의 원격 접속 VPN 을 껐다 켠다(모든 세션이 내려가고 남은 사용자는 다시 접속) |
| 노트북 `원격 접속 끊김: DPD 에 서버 … 응답 없음 (재전송 2번 뒤 timeout) → … SA 삭제` | 서버가 꺼졌거나 경로(케이블·방화벽 UDP 4500)가 끊김 — 조용한 터널은 DPD 를 보내기 전까지 모른다 | 경로를 고친 뒤 "다시 연결" |
| DPD 뒤 `서버가 이 터널을 모른다고 알림 (INVALID_SPI …) → 옛 SA 를 버리고 다시 접속` | 서버 설정이 바뀌었거나 이중화로 넘어가 서버에 이 SA 가 없음 | 자동으로 다시 접속한다 |
| 서버 `이미 답한 IKE_AUTH 를 다시 보냄 (지난 응답이 사라진 것) → 기억해 둔 응답(…)을 그대로 다시 보냄` | 서버의 마지막 IKE_AUTH 응답이 도중에 사라져 노트북이 재전송함 (패킷 손실) | 정상. 노트북은 다시 받은 응답으로 접속(또는 인증 실패)을 끝낸다 |
| 노트북 `서버 … 의 … 응답(SPI …)이 지금 협상(SPI …)의 것이 아님 → 지난 교환의 늦게 온 응답으로 보고 무시` | DPD 를 기다리다 "다시 연결" 하는 등, 지난 협상의 응답이 새 협상 뒤에 도착함 | 정상. 새 협상은 그대로 진행된다 |
| 노트북 `서버 … 에서 온 ESP 의 SPI … 가 지금 터널(SPI …)의 것이 아님 (지난 SA) → 풀지 않고 드롭` | 지난 SA 를 든 장비가 보낸 ESP (지금 터널의 키가 아니라 풀 수 없다) | 계속되면 노트북에서 "다시 연결" |
| 구성 검사 `ra.pool-invalid` | 가상 주소 풀의 시작이 끝보다 크거나 주소가 잘못됨 | 시작 ≤ 끝 인 주소 두 개 |
| 구성 검사 `ra.pool-overlap` | 가상 주소 풀이 사내 대역과 겹침 | 쓰지 않는 대역으로 |
| 원격 접속 노트북 `끊김 · DPD 에 서버 응답 없음`, 사이트 간 `IPsec DPD: 상대 … 응답 없음 … SA 삭제` (누르지 않았는데) | 주기 DPD 를 켜 두었고, 상대에게서 10초 동안 받은 것이 없어 DPD 를 보냈지만 응답이 없음 — 상대가 꺼졌거나 경로가 끊김(케이블 손실 100% 처럼 링크는 살아 있어도) | 경로·상대 장비를 확인한 뒤 원격 접속은 "다시 연결", 사이트 간은 다음 패킷에 다시 협상. 주기 DPD 가 꺼져 있으면 조용한 터널은 상대가 사라져도 모른다 |

## 공유기 VPN (L2TP/IPsec, ipTIME 식)

출장지 노트북이 집 공유기의 VPN 서버에 붙어 집 LAN 주소(할당 IP)를 받는다. IPsec(사전 공유 키) → L2TP 터널·세션 → PPP 계정 인증(CHAP) → 주소(IPCP) 순서로 맺고, 연결되면 모든 트래픽이 집으로 간다(full tunnel).

| 증상 / 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 노트북 `VPN 접속 실패 (L2TP/IPsec): IKE Main Mode 응답 없음 …`, 구성 검사 `ra.server-off` | 서버 주소(공유기 공인 주소)가 틀렸거나 공유기의 VPN 서버가 꺼짐 | 공유기 WAN 주소 확인(실제 가정은 주소가 바뀌어 DDNS 이름으로 접속), 공유기 설정의 "VPN 서버" 켜기 |
| 노트북 `서버가 IPsec 인증을 거절 (AUTHENTICATION-FAILED) — 사전 공유 키가 다름`, 공유기 `… 의 IPsec 인증 실패 — 사전 공유 키가 다름`, 구성 검사 `ra.psk-mismatch` | 노트북과 공유기의 사전 공유 키가 다름 | 둘을 같게 |
| 노트북 `서버가 계정 인증을 거절 (CHAP Failure) — 계정 또는 비밀번호가 틀림`, 공유기 `PPP 계정 인증 실패 (CHAP) — 계정 … 가 목록에 없음` / `… 의 비밀번호가 다름`, 구성 검사 `ra.account-mismatch` | IPsec 은 맺었지만 계정이 공유기 목록에 없거나 비밀번호가 다름 (노트북에는 어느 쪽인지 알려 주지 않는다 — 공유기 로그에서 확인) | 공유기 "VPN 서버 → 계정" 에 넣거나 노트북의 사용자 이름·비밀번호를 같게 |
| 노트북 `서버가 PPP 계정 인증(CHAP)을 요구하는데 계정이 없음`, 구성 검사 `ra.no-account` | L2TP/IPsec 은 사전 공유 키 뒤에 계정 인증을 꼭 거친다 | 노트북 VPN 에 사용자 이름·비밀번호 |
| 노트북 `서버에 줄 주소가 없음 (IPCP Nak)`, 공유기 `할당 IP … 에 줄 주소가 없음`, 구성 검사 `router.vpn-pool` | 할당 IP 가 다 찼거나, 범위가 거꾸로이거나 LAN 대역 밖 | 공유기 "VPN 서버" 의 할당 IP 를 LAN 대역 안·DHCP 범위 밖으로 넉넉히 |
| 구성 검사 `router.vpn-pool` (DHCP 범위와 겹침) | 같은 주소가 VPN 기기와 LAN 기기에 함께 생길 수 있음 | 할당 IP 를 DHCP 범위 밖으로 (예: 192.168.0.50 ~ 59) |
| 구성 검사 `router.vpn-no-users` | 공유기 VPN 서버에 계정이 없어 아무도 접속할 수 없음 | 계정 추가 |
| 구성 검사 `ra.type-mismatch` | 노트북의 VPN 종류가 서버와 다름 (공유기는 L2TP/IPsec, 회사 VPN 장비는 IKEv2) | 노트북 VPN 의 "종류" 를 서버에 맞게 |
| 연결됐는데 집 NAS(192.168.0.x)에만 안 닿음, 노트북 로그에 `vpn.encap` 이 없음 | 출장지 LAN 대역이 집 LAN 대역과 같아(둘 다 192.168.0.0/24) 노트북이 NAS 를 "같은 서브넷" 으로 보고 출장지 LAN 에서 찾는다 | 한쪽 대역을 바꾼다 (보통 집 공유기 LAN 을 192.168.10.0/24 처럼 흔하지 않은 대역으로) |
| 연결 중 해외 사이트가 "한국에서 접속" 으로 봄 | 정상 — full tunnel 이라 인터넷도 집 공유기의 NAT 로 나가 집 공인 주소로 보인다 | 원하지 않으면 VPN 을 끈다 (회사 VPN 의 split tunnel 과의 차이) |
| 공유기 `VPN 서버: … Main Mode 첫 교환 없이 온 인증 → 무시` / `PSK 인증 없이 온 Quick Mode → 무시` | 공유기 설정이 바뀌어(또는 WAN 이 끊겨) 진행 중이던 협상을 잊음 | 노트북에서 "다시 연결" |
| 노트북 `VPN 끊김 (L2TP/IPsec): 공유기가 연결을 끊음 (터널 끊기 (StopCCN))`, 공유기 `… 터널 끊기(StopCCN)를 보내고 세션을 비움` | 공유기 VPN 서버의 설정(사전 공유 키·할당 IP)이 바뀌었거나 VPN 서버를 끔 (계정만 바꾸면 끊지 않는다) | 설정을 확인한 뒤 노트북에서 "다시 연결" |
| 공유기 `모르는 연결(SPI …)의 L2TP/IPsec 패킷 … → INVALID-SPI 로 알림`, 노트북 `공유기가 이 연결을 모른다고 알림 … → 다시 접속` | 공유기가 연결을 잊음 (자동 WAN 이 주소를 잃었다 다시 받음 등) | 자동으로 다시 접속한다. 그사이 보낸 패킷 하나는 사라진다 |
| 공유기 `L2TP/IPsec VPN 협상 요청 (IKE …) → 이 공유기의 VPN 서버가 꺼져 있어 받지 않음` | 노트북이 가리킨 공유기의 VPN 서버가 꺼짐 | 공유기 설정의 "VPN 서버" 켜기. 안쪽 장비가 서버면 UDP 500·4500 포워딩 |
| 공유기 `목적지 … 는 VPN 할당 IP 인데 지금 그 주소로 붙어 있는 VPN 기기가 없음 … → 드롭` | 끊긴 VPN 기기에게 보내려는 LAN 장치 (공유기가 대신 답했던 프록시 ARP 가 그 장치 캐시에 남음) | 정상. 기기가 다시 붙으면 같은 주소를 받아 이어진다 |
| 구성 검사 `router.vpn-pool` (LAN 장치가 고정으로 씀) | 할당 IP 범위의 주소를 LAN 의 수동 장치가 쓰고 있어, 그 주소를 받은 VPN 기기와 충돌 (집 장치의 패킷이 그 장치로 감) | 할당 IP 를 쓰지 않는 주소로, 또는 그 장치의 주소를 바꾸기 |
| 노트북 `IKE … 수신 / ESP 수신 … → 지금 VPN 연결의 것이 아님 (끊었거나 종류를 바꾼 뒤 늦게 온 패킷) → 무시` | VPN 을 끄거나 종류를 바꾼 직후 서버가 보낸 것이 늦게 도착 | 정상 |

## WireGuard (GL.iNet 식 공유기 서버·클라이언트, 노트북·폰 앱)

WireGuard 는 공개 키가 곧 신원이다. 틀리면 "거절" 메시지가 없고 **아무 답도 하지 않는다** — 클라이언트 쪽에는 timeout 만 보이므로 서버 로그와 구성 검사로 원인을 찾는다.

| 증상 / 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 클라이언트 `핸드셰이크 실패 — … 가 3번 모두 응답하지 않음 (timeout)`, 서버 `… Initiation — 보낸 공개 키 … 가 피어 목록에 없음 → 응답 없이 버림`, 구성 검사 `wg.not-registered` | 서버 피어 목록에 이 클라이언트의 공개 키가 없음 | 서버 "WireGuard 서버 → 피어" 에 클라이언트의 "내 공개 키" 를 넣는다 (클라이언트의 "서버 가져오기" 를 쓰면 한 번에) |
| 서버 `… Initiation 을 내 공개 키로 확인할 수 없음 (mac1 불일치 …)`, 구성 검사 `wg.server-key` | 클라이언트에 적은 "서버 공개 키" 가 틀림 (서버가 키를 다시 만들었을 수도) | 클라이언트의 서버 공개 키를 서버 화면의 "내 공개 키" 로 |
| 핸드셰이크는 되는데(연결됨) ping 이 안 됨, 서버 `… 풀린 패킷의 출발지 … 가 그 피어의 AllowedIPs(…) 밖 → 드롭`, 구성 검사 `wg.address-mismatch` | 클라이언트의 "내 터널 주소" 가 서버에 등록된 그 피어의 주소와 다름 (cryptokey routing: 피어마다 쓸 수 있는 출발지가 정해져 있다) | 클라이언트의 터널 주소를 서버 피어의 주소로 |
| 구성 검사 `wg.server-off`, 공유기 `WireGuard 핸드셰이크 … → 이 공유기의 WireGuard 서버가 꺼져 있어 받지 않음` | 가리킨 공유기의 WireGuard 서버가 꺼짐 | 서버 켜기. 서버가 다른 공유기 뒤에 있으면 앞 공유기에 UDP 51820 포워딩 |
| 구성 검사 `wg.port-mismatch` | 클라이언트가 보내는 포트와 서버가 듣는 포트가 다름 | 서버 포트에 맞춘다 |
| 서버 `… 데이터가 모르는 세션 … 로 옴 (이 장비가 재시작·설정 변경으로 세션을 잊음) → 버림` | 서버 설정을 바꿔 세션이 사라졌는데 클라이언트는 옛 세션으로 보냄 (WireGuard 에는 "끊음" 알림이 없다) | 기다리면 클라이언트가 보낸 뒤 15초 동안 답이 없을 때 새로 핸드셰이크한다(시간이 흘러야 — "+10초"). 바로 잇려면 클라이언트에서 "다시 연결" |
| 여행용 공유기 첫 핸드셰이크가 5초 뒤 재시도로 붙음 | 켜질 때 앞 공유기(호텔)가 아직 인터넷 주소를 받기 전이라 첫 Initiation 이 사라짐 | 정상. 타일 배지가 "VPN 연결됨" 이 되면 쓴다 |
| 공유기 `킬 스위치: VPN 이 끊겨 있어 … 를 WAN 으로 내보내지 않음`, 배지 `킬 스위치` | VPN 서버에 닿지 않는 동안 LAN 기기의 인터넷을 막음 (실제 주소가 새지 않게) | 의도한 동작. VPN 을 되살리거나 킬 스위치를 끈다 |
| 공유기 `VPN 이 끊겨 있음 … 킬 스위치가 꺼져 있어 … 를 WAN 으로 바로 내보냄` (vpn.leak) | 킬 스위치가 꺼진 채 VPN 이 끊겨 기기의 트래픽이 VPN 밖으로 나감 | 실제 주소가 드러나면 안 되면 킬 스위치를 켠다 |
| 구성 검사 `wg.dns-outside` | DNS 가 AllowedIPs 밖이라 DNS 질의가 터널로 가지 않음 (사설 주소면 닿지 않고, 공인 주소면 VPN 밖으로 샌다) | AllowedIPs 에 DNS 주소를 넣거나 DNS 를 비운다 |
| 구성 검사 `wg.overlap` / `wg.peer-duplicate` / `wg.no-peers` | 터널 대역이 LAN 과 겹침 / 두 피어의 터널 주소가 같음 / 피어 없음 | 터널을 다른 대역(10.0.0.0/24)으로 / 피어마다 다른 주소 / 피어 추가 |
| 폰에서 8.8.8.8 은 되는데 VPN 을 거치지 않음 | AllowedIPs 를 집 대역만 적은 split tunnel | 전부 터널로 보내려면 AllowedIPs 를 0.0.0.0/0 |
| 노트북 `WireGuard 수신 … → 지금 VPN 연결의 것이 아님 … → 무시`, 공유기 `… 클라이언트가 꺼진 뒤 늦게 온 패킷 → 무시` / `… WireGuard 서버가 꺼져 있음 → 무시` | VPN 을 끄거나 종류를 바꾼 뒤 상대가 보낸 것이 늦게 도착 | 정상 |
| 구성 검사 `wg.no-address`, 공유기 `킬 스위치: VPN 클라이언트에 내 터널 주소가 없어 VPN 을 쓸 수 없음` | 클라이언트의 "내 터널 주소" 가 비었거나 틀림 (킬 스위치가 켜져 있으면 LAN 기기의 인터넷이 막힌다) | 서버 관리자가 정해 준 주소(예: 10.0.0.2/32) |
| 구성 검사 `wg.peer-in-lan` | 피어 터널 주소가 집 LAN 안 → LAN 기기가 그 주소를 같은 서브넷으로 보고 ARP 로 찾아 공유기를 거치지 않음 | 피어 주소를 터널 대역(10.0.0.0/24) 안으로 |
| 구성 검사 `wg.peer-outside` | 피어 터널 주소가 서버 터널 대역 밖 | 터널 대역 안으로 |
| 구성 검사 `wg.peer-key-duplicate` | 두 피어의 공개 키가 같음 — 앞의 피어만 쓰인다 | 중복을 지우거나 그 기기의 공개 키로 |
| LAN 에서 10.0.0.x(피어 없는 터널 주소)로 보냄 → `No route: … WireGuard 터널 대역 … 안이지만 그 주소로 등록된 피어가 없음` | 붙어 있지 않은(등록되지 않은) 터널 주소 | 피어 목록·클라이언트 연결 확인 |

## DDNS (이름으로 집에 접속)

| 증상 / 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 공유기 `DDNS 거절: … 은 다른 기기가 등록한 이름 (badauth)`, 구성 검사 `ddns.name-taken` | 같은 이름을 다른 공유기가 먼저 등록 (이름은 기기마다 하나) | 다른 이름 |
| 구성 검사 `ddns.name-invalid` | 이름에 쓸 수 없는 글자 (영문 소문자·숫자·- 만) | 이름 고치기 (예: myhome) |
| 공유기 `DDNS 갱신 실패: DDNS 서버 … 가 응답하지 않음` | WAN 이 인터넷에 닿지 않음 | WAN·인터넷 연결 확인 (다음 주소 변경·10분 주기 확인 때 다시 시도) |
| `DDNS 등록됨: … (… WAN 주소 … 가 아님: 앞에 NAT 가 있어 그 공인 주소가 등록됨)` | 공유기가 다른 공유기 뒤(이중 NAT)에 있다 | 정상. 밖에서 접속하려면 앞 공유기에 포트 포워딩도 필요 |
| 구성 검사 `wg.name-unknown`, 앱 `서버 이름 … 을(를) 풀지 못함 (없는 이름)` | WireGuard 서버를 DDNS 이름으로 적었는데 그 이름을 등록한 공유기가 없음 | 서버 공유기 → 인터넷 → DDNS 켜기 |
| ISP 가 주소를 바꾼 뒤 폰의 ping 이 실패함 | 폰은 아직 옛 주소로 보낸다 (WireGuard 는 이름을 연결할 때만 푼다) | 시간을 흘리면("+10초") 15초 무응답 → 핸드셰이크 3번 실패 → 이름을 다시 풀어 새 주소로. 바로 하려면 "다시 연결" |
| 다시 풀었는데 `다시 푼 주소도 … 그대로 → 다시 잇지 않음` | DNS 캐시가 아직 옛 주소를 들고 있거나, 주소는 그대로인데 서버가 꺼짐 | DDNS 이름은 TTL 30초 — 잠시 뒤 다시. 서버 상태 확인 |
| 구성 검사 `wg.server-behind-nat` | DDNS 이름의 주인(WireGuard 서버)이 다른 공유기 뒤라 이름이 앞 공유기의 공인 주소를 가리키는데, 앞 공유기에 포워딩이 없음 | 앞 공유기 → 포트 포워딩 UDP 51820 → 서버 공유기의 WAN 주소 |
| `서버 이름 … 을(를) 풀지 못함 … — 전에 쓰던 … 로 계속 시도` / `— 보낼 패킷이 또 생기면 다시 풂` | 이름 풀기가 잠깐 실패 (DNS 장애·이름 미등록) | 저절로 다시 시도한다 (보낼 패킷이 생길 때). 이름·DNS 확인 |
| 나중에 켠 공유기가 `badauth` 에서 안 벗어남 | 먼저 쓰던 공유기가 이름을 내려놓아야 한다 (DDNS 를 끄거나 이름을 바꾸거나 공유기를 치우면 내려놓음) | 내려놓은 뒤 10분 주기 확인이나 WAN 주소 변경 때 등록된다 ("+10초" 로 시간을 흘리거나 이름을 껐다 켜기) |
| 서버 `… 가 3번 모두 응답하지 않음 … 상대 앞 NAT 가 이쪽(바뀐 주소 등)에서 먼저 온 패킷을 막을 수 있다` | 집 서버가 새 주소에서 먼저 다시 잇는 것을 클라이언트 앞의 port-restricted NAT 가 막음 | 정상. 클라이언트가 이름을 다시 풀어 먼저 보내면 이어진다 (full cone NAT 면 서버 쪽 시도로도 이어짐) |

## 멀티 WAN 페일오버 (lan4 = WAN2)

| 증상 / 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 유선 회선에 손실 100%(링크는 살아 있음)인데 한참 WAN2 로 안 넘어감 | 추적 ping 은 5초마다 배경 타이머 — 시간이 흘러야 돈다. 3번 이어 실패해야 끊김 | "+10초" 를 두어 번. 추적 주소가 비어 있으면 이런 장애는 모른다(링크만 봄) |
| `멀티 WAN: … WAN1 에서 WAN2 로 전환` 뒤 SSH·다운로드가 끊김 (서버 `연결 없는 세그먼트 … → RST`) | 새 회선의 공인 주소로 NAT 되어 서버에게는 다른 연결 | 정상 (mwan3 도 같다). 다시 연결 |
| WAN1 이 살아났는데 바로 안 돌아감 | 끊긴 회선은 추적 ping 이 2번 이어 답해야 살아남 | 시간을 흘린다 |
| WAN2 로 넘어간 동안 포트 포워딩으로 들어오는 연결이 안 됨 | WAN2 주소가 다른 장비(핫스팟·LTE) 뒤의 사설 주소라 밖에서 닿지 않음 | 그 장비에도 포워딩이 있어야 한다 |
| 멀티 WAN 을 켠 공유기의 L2TP VPN 서버·IPv6 가 WAN2 로 넘어간 동안 안 됨 | 이 시뮬레이터는 L2TP VPN 서버·IPv6·공유기 자신의 이름 해석을 WAN1 에서만 한다 (WireGuard 는 지금 회선을 따라간다) | 한계 |
| WAN1 으로 되돌아갔는데 WAN2 로 시작한 다운로드는 계속됨 | 정상 — 흐름은 시작한 회선이 살아 있으면 그 회선에 붙는다 (mwan3 conntrack mark) | 끊긴 회선의 흐름만 새 회선으로 넘어가 끊긴다 |
| 구성 검사가 lan4 에 꽂은 장비를 LAN 으로 봄 | 멀티 WAN 이 꺼져 있다 (lan4 는 LAN 포트) | 공유기 → 인터넷 → 멀티 WAN 켜기 |

## AdGuard Home·자녀 보호 (DNS 필터)

| 증상 / 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| ping 실패 `DNS 가 막은 이름 (0.0.0.0)`, 공유기 `… 은(는) … 규칙 … 에 걸림 (AdGuard Home) → … 0.0.0.0 으로 답함` | 정상 — 차단 목록·사용자 규칙·자녀 보호에 걸린 이름 | 막지 않으려면 공유기 → 앱 → AdGuard Home → 예외에 그 이름 |
| 구성 검사 `adguard.bypass`, 그 기기만 광고가 그대로 됨 | DNS 를 8.8.8.8 처럼 직접 적어 공유기를 거치지 않음 | DNS 가로채기 켜기, 또는 그 기기의 DNS 를 공유기 LAN 주소로 |
| 구성 검사 `adguard.dhcp-dns` | DHCP 가 다른 DNS 를 안내해 자동 기기들이 공유기를 거치지 않음 | DHCP 의 DNS 서버 칸을 비우기(공유기 자신) |
| 구성 검사 `adguard.dns-off` | DNS 포워더가 꺼져 있어 거를 질의가 오지 않음 | 네트워크 → DNS 포워더 켜기 |
| 자녀 보호가 그 기기에 안 걸림 | 기기를 주소로 구분하는데 DHCP 로 주소가 바뀜 | 그 기기를 수동 주소로 (실제 공유기는 MAC 으로 고정 할당) |
| 막았는데 한동안 그대로 됨 | 기기 리졸버가 예전 답을 캐시 (60초) | 잠시 뒤, 또는 기기 DNS 캐시 비우기 |

## DPI·VPN 난독화

| 증상 / 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| VPN 이 timeout 으로 실패, 앞 공유기 `DPI 차단: … 는 WireGuard (VPN, WireGuard 모양 …) → 드롭` | 그 망의 DPI 가 VPN 카테고리를 막음 (클라이언트에게는 timeout 으로만 보인다) | 양쪽(클라이언트·서버) 난독화 켜기, 또는 그 망에서 VPN 을 쓰지 않기 |
| 난독화를 켰는데 서버 `… 를 WireGuard 로 알아볼 수 없음 — … 난독화 …`, 구성 검사 `wg.obfuscation-mismatch` | 한쪽만 난독화 | 양쪽 같게 |
| 난독화했는데도 `DPI 차단: … 알 수 없음` | DPI 가 "알 수 없음" 카테고리까지 막음 (엄격한 망) | 그 망에서는 못 지나간다 (실제로는 TCP 443 위장 같은 다른 방법) |
| TCP 연결이 `연결 거부 (RST)` 인데 서버는 켜져 있음, 공유기 `DPI 차단: … → 드롭하고 기기에 RST 를 넣어 연결을 끊음` | DPI 가 그 앱을 막고 RST 를 넣음 (기기는 서버가 거부한 줄 안다) | 공유기 → 앱 → DPI 에서 그 앱·카테고리 풀기 |
| DPI 표에 앱 대신 `HTTPS (이름 모름)` | 이름 없이 주소로 접속했거나(SNI 없음), 기기의 DNS 가 공유기가 아니라 주소를 배우지 못함 | 정상 (DPI 는 보이는 것만 본다) |

## 도커 네트워크 · 포트 공개 (docker -p)

| 증상 / 로그 문구 | 원인 | 고치는 법 |
|---|---|---|
| 맥 터미널에서 컨테이너 주소(172.18.0.x)로 ping 이 timeout, 인터넷 노드 `사설 주소 … 는 인터넷에서 라우팅되지 않음` | 맥의 Docker Desktop 에서 컨테이너는 Linux VM 안에 있어 맥(macOS)에 그 대역 경로가 없다 → 기본 경로로 집 공유기·인터넷까지 나가 버려진다 | 포트 공개로 접속한다(맥의 127.0.0.1:8080). 리눅스에서 도커를 바로 돌리면 호스트가 컨테이너 대역에 직접 붙어 있어 된다 |
| `포트 N 는 127.0.0.1 에만 공개됨 → … 에서는 듣는 프로그램이 없어 RST 로 거부`, 클라이언트 `연결 거부 (RST)` | `-p 127.0.0.1:N:N` 처럼 공개 주소를 하나로 좁혔다 — 그 주소로 온 것만 받는다 | LAN 에서도 받으려면 포트 공개의 받는 주소를 0.0.0.0 으로 |
| `포트 공개 … 대상으로 가는 경로가 없음 → 드롭` | 포트 공개의 대상 주소가 이 장비가 모르는 대역 | 대상 주소를 연결된 브리지 안의 주소로 고치거나 경로를 추가 |
| 컨테이너가 다른 컨테이너 이름을 못 찾음 (`없는 이름`, 공인 DNS 의 NXDOMAIN) | 기본 브리지(docker0)에는 내장 DNS 가 없다 (호스트의 DNS 설정을 그대로 씀) | 사용자 정의 네트워크(br-app)에 같이 붙인다 — 그 네트워크의 내장 DNS 가 컨테이너 이름을 안다 |
| 다른 브리지의 컨테이너로 ping 이 timeout, Docker VM `방화벽 차단` | 서로 다른 도커 네트워크끼리는 같은 호스트여도 막는다 (DOCKER-ISOLATION) | 두 네트워크에 함께 붙인 컨테이너를 거치거나, 같은 네트워크에 둔다 |
| 컨테이너(web)가 본 상대 주소가 클라이언트가 아니라 172.18.0.1 | 포트 공개는 docker-proxy 처럼 장비가 대신 연결을 연다 (FULLNAT) — 대상은 브리지 게이트웨이가 연 연결로 본다 | 정상. 진짜 클라이언트 주소가 필요하면 실제로는 iptables DNAT(userland-proxy 끔)이나 X-Forwarded-For 를 쓴다 |
| 방화벽을 기본 차단으로 두었는데 공개 포트로는 들어온다 | 포트 공개는 장비 자신의 프로세스(docker-proxy)가 받고 대상에게 새로 여는 연결이라, 지나가는 패킷만 검사하는 방화벽을 거치지 않는다 (실제로도 도커가 연 포트는 ufw 규칙을 우회한다) | 막으려면 공개를 지우거나 받는 주소를 127.0.0.1 로 좁힌다 |
| `포트 공개: … 로 넘기려는 패킷의 TTL 이 다함 → 드롭 (공개 규칙이 서로를 가리키는 순환인지 확인)` | 두 장비의 공개 규칙이 서로를 대상으로 가리켜 연결이 끝없이 넘겨진다 | 한쪽 규칙의 대상을 실제 서비스(컨테이너)로 고친다 |
| 게이트웨이 `NAT 켜짐 (MASQUERADE)` / `NAT 꺼짐 → … NAT 매핑 n개 지움` | 게이트웨이 설정의 NAT 토글 | 끄면 위쪽 장비에 안쪽 대역으로 돌아오는 경로(스태틱 라우팅)가 있어야 응답이 돌아온다 |

## IPv6

IPv6 는 장치마다 켜야 오간다(실제 OS 는 기본 켜짐). 켜면 MAC 에서 만든 링크 로컬 주소(fe80::)가 생기고, ARP 대신 NDP 로 이웃의 MAC 을 찾는다. NAT 가 없어 게이트웨이·NAT 박스는 주소를 그대로 넘긴다. 호스트를 자동(SLAAC)으로 두면 게이트웨이의 RA 가 알린 /64 프리픽스 + MAC 에서 만든 인터페이스 ID 로 주소를 스스로 만들고, RA 를 보낸 라우터의 링크 로컬 주소를 기본 게이트웨이로 쓴다.

| 로그·경고 문구 | 원인 | 고치는 법 |
|---|---|---|
| `ping … 실패: IPv6 가 꺼져 있음` / `IPv6 패킷 수신 → 이 장치는 IPv6 가 꺼져 있어 드롭` | 보내는 쪽이나 받는 쪽의 IPv6 가 꺼짐. 꺼진 장치는 NS 멀티캐스트도 걸러 NDP timeout 이 된다 | 그 장치 → 설정 → IPv6 켜기 |
| `ping … 실패: 주소를 DAD 로 확인하는 중` | 켜거나 링크가 살아난 직후 1초 동안은 DAD(중복 확인) 중이라 주소를 못 쓴다 | 1초 뒤 다시 |
| `DAD 실패: … 는 이미 … 가 쓰는 주소` / `DAD 실패: … 도 … 를 동시에 확인하는 중` (`ndp.dad.fail`) / 구성 검사 `ipv6.duplicate` | 같은 IPv6 주소를 두 장치가 씀. 먼저 쓰던 쪽이 NA 로 방어하고 나중에 켠 쪽이 포기한다. 둘이 동시에 켜지면(예제·JSON 불러오기) 서로의 DAD NS 를 받아 둘 다 포기한다 | 한쪽 주소를 바꾸기 |
| `ping … 실패: 링크 다운 — 케이블을 연결하세요` | 케이블이 빠져 IPv6 주소를 쓸 수 없다 (다시 꽂으면 DAD 뒤에 쓴다) | 케이블 연결 |
| `RS 3번에 RA 가 없음 → SLAAC 주소·기본 게이트웨이 없이 링크 로컬만` (`slaac.timeout`) / 타일 `RA 없음 · 링크 로컬만` / 구성 검사 `ipv6.slaac-no-ra` | 호스트는 자동(SLAAC)인데 이 링크의 라우터가 RA 를 보내지 않음(IPv6 꺼짐·RA 광고 꺼짐·라우터 없음) | 게이트웨이 → IPv6 → 그 인터페이스의 RA 광고 켜기, 또는 호스트를 수동으로 |
| `프리픽스 … 는 /64 가 아니라 SLAAC 주소를 만들 수 없음` / 구성 검사 `ipv6.ra-prefix` | RA 로 알린 프리픽스가 /64 가 아님(또는 인터페이스에 주소가 없어 알릴 프리픽스가 없음). SLAAC 는 인터페이스 ID 가 64비트라 /64 에서만 된다 | 게이트웨이 인터페이스 주소를 /64 로 |
| 타일 `RA 받음 · /64 프리픽스 없음` | RA 는 왔지만 알린 프리픽스가 /64 가 아니거나 없다(라우터 인터페이스에 주소가 없음·중복) | 게이트웨이 인터페이스 주소를 /64 로 |
| 라우터 하나를 거뒀는데 SLAAC 주소가 남음 (`… 가 아직 알리고 있음 → SLAAC 주소 유지`) | 정상 — 같은 프리픽스를 다른 라우터도 알리고 있어, 모두 거둬야 주소를 지운다 | |
| 첫 번째 라우터의 케이블만 뺐는데 두 번째 라우터로 안 넘어감 | 시뮬레이터 한계 — 이웃 도달성 확인(NUD)과 주기 RA 가 없어 말없이 사라진 라우터를 모른다. 실제 OS 는 NUD 로 몇 초 안에 넘어간다 | 라우터의 RA 광고를 끄거나 장치를 지우면(거둠 RA) 바로 넘어간다 |
| RA 광고를 끄자 호스트의 주소·게이트웨이가 사라짐 | 정상 — RA 를 끄거나 라우터를 지우면 라우터 수명 0 인 "거둠 RA" 를 보내고, 호스트는 그 라우터를 기본 게이트웨이에서 빼고 프리픽스로 만든 주소를 지운다(이 시뮬레이터는 수명이 흘러 만료되는 대신 거둠 RA 로 바로 반영. 실제 리눅스는 유효 수명 0 을 받아도 주소를 2시간 유지한다 — RFC 4862 5.5.3e, 가짜 RA 로 주소를 지우는 공격을 막으려고). 그 주소로 열려 있던 연결은 끊긴다 | 다시 켜면 곧바로 RA 로 되돌아온다 |
