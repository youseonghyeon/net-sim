# 라우팅·NAT·이중화 — RIP·VRRP·게이트웨이 NAT·포트 공개·NAT 종류·P2P

기능별 구현 상세 (예전 AGENTS.md "시뮬레이션 연결 방식" 에서 옮김 — 2026-10-07). 규칙·공통 메커니즘은 AGENTS.md.

- 동적 라우팅(`nodes/rip.ts`, RIPv2 축소판): `L3Node.rip`(설정 `L3Settings.rip {enabled, defaultRoute}`). 224.0.0.9 / MAC 01:00:5e:00:00:09 멀티캐스트, UDP 520, 메트릭 = 홉 수(16 = 철회). **주기 업데이트·timeout 없음** — 시계가 조용하면 멈추는 구조라 30초 주기 타이머를 넣으면 시계가 끝없이 점프한다. 대신 변화(링크·주소·설정·수신)가 생기면 `kick` → 250ms 뒤 트리거 업데이트(Probe 200ms 뒤라 새 주소로 보냄), 새로 참여한 인터페이스는 Request 도. split horizon + poison reverse, 보내는 인터페이스 자신의 서브넷은 광고 안 함, NAT outside 는 참여 안 함, 경로를 하나라도 잃으면(링크 다운·이웃의 철회) 다음 업데이트에서 모든 인터페이스로 Request 를 보내 대체 경로를 다시 듣는다(주기 업데이트 대신 — 다른 이웃의 16 에 '대답' 하는 방식은 poison reverse 끼리 끝없이 주고받아 금지). 인터페이스 주소가 바뀌거나 서브 인터페이스가 사라지기 직전 `retire` 로 옛 주소에서 전부 철회를 보내고, 서브 인터페이스 번호가 밀리면 `remap`. 장치 제거 시 전부 철회. 수렴 테스트는 삼각형만으로는 부족 — 4대 일렬·백본(스위치 공유)까지 `runToIdle` 이 끝나는지 본다(`tests/rip.test.ts`). 조회는 연결 → 스태틱·RIP 중 긴 마스크(같으면 스태틱) → 스태틱 디폴트 → RIP 디폴트. 한계: 스위치 너머 이웃이 사라진 건 모른다(문서화). 호스트·공유기 WAN·인터넷은 가입하지 않은 멀티캐스트 MAC 을 로그 없이 거른다(`isMulticastMac`). 구성 검사는 양쪽 다 RIP 면 "돌아오는 경로/업링크 디폴트/릴레이 경로" 규칙을 침묵.
- 이중화(`nodes/ha.ts` `Ha`, VRRP 식): `L3Settings.ha {enabled, vrid, priority, vips[]}` (인터페이스별 가상 주소). 장비 단위로 넘어간다(방화벽 HA 처럼 VIP 인터페이스 하나라도 링크·주소가 없으면 우선순위 0 = 인터페이스 추적). master 는 `NetInterface.vip {ip, mac}` 를 켜 가상 주소 ARP 에 가상 MAC(00:00:5e:00:01:VRID)으로 답하고 그 MAC 으로 온 프레임을 받으며, 켤 때 가상 MAC 을 출발지로 Gratuitous ARP(`announceVip`) → 스위치가 새 포트를 배움(호스트 캐시는 그대로). `L3Node.ownIndex`(실제·가상 주소)·`addrOf`(가상 주소 우선: NAT 공인 주소·VPN 터널 끝)를 쓴다. 광고는 VRRP(IP 112, 224.0.0.18, `VrrpPacket`). **주기 광고는 설정 `HaConfig.advert`(기본 꺼짐)** — 켜면 master 가 1초마다(배경 타이머), backup 은 master 광고를 들을 때마다 Master_Down(3초 + skew) 감시를 다시 걸고(배경 타이머) 끝나면 "말없이 죽은 master" 로 보고 이어받는다(케이블 손실 100% 처럼 링크가 살아 있어 물러남 광고가 없는 고장. 케이블을 뽑으면 링크 다운을 알아챈 master 가 남은 링크로 물러남 광고를 보내므로 말없이 죽지 않는다). 감시는 장비 단위(어느 VIP 인터페이스로든 들으면 살아 있음), 물러난 순간부터 건다(새 master 가 첫 광고 전에 죽어도 되찾게). master 의 광고는 출발지 MAC 이 가상 MAC(RFC 5798 7.3 — 스위치가 광고마다 가상 MAC 의 포트를 다시 배워, 둘 다 master 였다가 정리돼도 물러난 쪽 포트로 새지 않는다. 우선순위 0 광고는 실제 MAC). 둘 다 master 였다가 더 높은 쪽 광고를 들은 쪽은 물러나기 전에 세션을 넘겨준다(pfsync `handover` — 받는 쪽은 master 여도 받는다). 광고 설정만 바뀌면 선출을 다시 하지 않는다(넘어가지 않음). 구성 검사 `ha.advert-mismatch`. 꺼져 있으면 변화가 있을 때만 — 시작·링크 복구·설정 변경 때 알리고, master 가 물러날 때(추적 링크 다운·장치 제거·끔·더 높은 쪽 등장) 우선순위 0 광고 → backup 은 skew((256−우선순위)/256 초) 뒤 master. 시작 때는 3초+skew 기다린다. 높은 쪽이 돌아오면 preempt. 광고에 `rid`(VIP 첫 인터페이스의 실제 주소 — 동점 판정을 장비 단위로, 인터페이스마다 엇갈리면 광고가 끝없이 오간다)와 `candidate`(master 가 아닌 후보의 시작 알림 — backup 은 master 광고에만 기다림을 멈춘다, 그래야 높은 쪽이 재시작할 때 master 가 비지 않는다)를 싣는다. 케이블이 새로 이어지면 `NetworkSync` 가 HA master 들을 `poke`(광고 1회) — 갈라졌던 동안 생긴 dual master 정리. DHCP 임대·ARP Probe 끝에서도 `ha.onLinks`. RIP 는 master 가 넥스트 홉으로 가상 주소를 적어 보낸다(`RipEntry.nextHop`, 받는 쪽은 같은 서브넷이면 그 주소를 넥스트 홉으로, 알려 준 이웃은 `RipRoute.from`). 링크 다운을 알아챈 장치가 곧바로 보낸 프레임은 graceful(같은 sync 에서 다른 케이블이 빠져도 전달), 지운 장치의 타이머는 취소(`Network.timersOf`). 세션 동기화(`HaConfig.sync`, pfsync 식 — IP 240, 224.0.0.240, `PfsyncPacket`): master 는 `NatTable.onNew`·`Firewall.onFlow` 로 새 매핑·흐름을 모아(`ha-sync` 타이머 0ms) 가상 주소를 둔 안쪽 인터페이스로 보내고, backup 은 `importEntry`(공인 id 그대로, 이후 할당과 겹치지 않게)·`importFlow` 로 받아 둔다. 새 backup 의 후보 알림을 들은 master 는 전체 복사(bulk). IPsec SA 는 복사하지 않음(넘어가면 재협상) — 그래서 master 에서 물러날 때(`HaHost.onResign`) 사이트 간 SA·협상·기다리던 패킷(`Vpn.dropSa`)과 원격 접속 세션(`RaServer.dropAll`)을 비운다. 들고 있으면 물러난 장비의 DPD 에 상대가 "살아 있음" 으로 답하고, 두 장비가 같은 가상 주소로 협상해 SPI 가 겹친다 — 사이트 간 SPI 씨앗에는 가상 주소로 협상할 때만 실제 주소를 섞는다(`VpnIo.realSource`, 이중화가 아니면 씨앗은 그대로). 동기화가 꺼져 있으면 넘어갈 때 진행 중 연결은 끊김(새 master 의 Stateful 검사가 모르는 흐름). 구성 검사 `ha.sync-mismatch`. 구성 검사 `ha.no-vip`·`ha.vip-outside-subnet`·`ha.vip-mismatch`·`ha.vrid-mismatch`(둘 다 master)·`ha.vrid-shared`(다른 쌍이 같은 번호)·`ha.no-peer`·`ha.host-real-gw`, `vpn.shared-peer` 는 HA 짝을 제외, 게이트웨이 규칙은 가상 주소를 인정(`GwIface.vip`). 타일 배지 `HA master/backup`, 패킷 색 `--pkt-vrrp`. 예제 "방화벽 이중화 (VRRP)".
- 게이트웨이 NAT·포트 공개(2026-10-02, 도커 예제용): 게이트웨이에 `L3Settings.nat {enabled}`(바깥 = if0 고정 — 구성 검사가 if0 을 업링크로 보므로)를 켜면 NAT 박스처럼 MASQUERADE·포트 포워딩·바깥→안쪽 차단을 한다. 노드는 다시 만들지 않고 `L3Node.setNat` 으로 실행 중에 켜고 끈다(`nat`·`outside` 가 바뀜, 포트 포워딩보다 먼저 적용). 구성 검사는 `natOn(d)`(NAT 박스 또는 NAT 를 켠 게이트웨이)로 NAT 장비를 가린다 — 돌아오는 경로 규칙·`subnetsBehind`·포트 포워딩·VPN 포워딩 추적. 포트 공개(`L3Settings.publish [{port, bind, to, toPort}]`, `nodes/publish.ts` `PortPublish`, docker-proxy 식 FULLNAT, TCP 만): 장비 자신의 어느 주소로 와도(bind 0.0.0.0) 또는 그 주소로 온 것만(127.0.0.1 등) 받아 목적지 = 대상, 출발지 = 대상 쪽으로 나가는 내 인터페이스 주소:프록시 포트(61000~)로 바꿔 넘기고, 응답은 되돌린다(`forward(…, natDone)` 로 NAT 를 다시 하지 않음). NAT 역변환·포트 포워딩보다 먼저(VPN·원격 접속 터널로 풀려 온 TCP 도). 같은 포트면 그 주소에 바로 묶인 규칙이 0.0.0.0 보다 먼저. 그 포트가 다른 주소에만 공개돼 있으면 RST(Connection refused). 장비 자신의 프로세스(docker-proxy)가 받고 다시 여는 연결이라 바꾼 패킷은 방화벽(지나가는 패킷 검사)·NAT 를 거치지 않고(`sendPublished` — 실제 도커가 ufw 를 우회하는 모양), TTL 이 다하면 통지 없이 이유를 남기고 드롭(출발지가 나 자신이라 통지가 나에게 돌아오므로 — 공개 규칙 순환). 진행 중인 흐름은 규칙이 바뀌거나 지워져도 끝까지 잇고 새 연결만 규칙을 본다. 양쪽 FIN 뒤 ACK·RST 면 2초(TIME_WAIT), 대상이 SYN·ACK 로 답하지 않은 흐름은 10초 뒤 다음 연결 때 치운다. NAT 는 공개 포트·프록시 포트를 공인 포트로 고르지 않는다(`NatTable.reserved`). 실행 중에 NAT 를 켜면 if0 이 RIP 에서 빠지기 전에 철회(`rip.retire(0)`). 한계: TCP 만, IPv6 없음, 대상 쪽 ICMP 오류는 클라이언트에 전달하지 않음(timeout), 이중화 세션 동기화 대상 아님, 대상이 VPN 너머면 출발지 주소를 고르지 못해 드롭. 트레이스 `port.publish`, 실무 출력 `docker-proxy -proto tcp -host-ip … -container-port …`. 도커 예제(맥 Docker Desktop 구조): macOS = 게이트웨이(if0 집 LAN DHCP · if1 lo 127.0.0.1/8 · if2 vmnet) + NAT + 포트 공개(8080 → VM, 5432 는 127.0.0.1 에만), "맥 터미널" = lo 에 붙은 맥 안의 앱(127.0.0.2/8 — localhost 로 접속하는 쪽), Docker VM = 게이트웨이(vmnet · docker0 · br-app) + NAT + 포트 공개 + 방화벽(DOCKER-ISOLATION), 내장 DNS 는 br-app 의 서버 한 대(실제는 컨테이너마다 127.0.0.11), 기본 브리지 컨테이너는 공인 DNS 라 이름으로 못 찾음.
- NAT 종류·P2P(2026-10-02): `NatTable.type`(RFC 4787 — `full-cone`(기본)·`restricted`(안에서 보낸 적 있는 주소만)·`port-restricted`(주소:포트만)·`symmetric`(상대마다 바깥 포트를 새로 — 매핑 키에 `>상대` 를 붙임, 그 상대만)). 필터링 대상은 `NatEntry.peers`(보낸 상대 "ip"·"ip:port"), 막히면 `nat.miss` details `filtered`. 공유기 `RouterSettings.natType`, 게이트웨이·NAT 박스 `L3Settings.natType`(`natTypeOf` 로 정리). 바꿔도 지금 매핑은 지우지 않고 새 매핑부터 새 방식(`setType`) — 지우면 안쪽 앱이 서버에 알려 둔 바깥 주소(P2P 등록)가 말없이 낡는다. 이중화 세션 동기화는 symmetric 매핑의 상대(`dest`)까지 싣는다. 100.64.0.0/10(CGNAT 공유 주소)은 사설 주소로 본다. P2P 앱(`nodes/p2p.ts` `P2pAgent`, 호스트 `HostSettings.p2p {enabled, name}` — 이름이 비면 장치 이름, UDP 41641): 주소를 얻으면 시그널링 서버(198.51.100.40:8443)에 등록(1.5초·3번) → 사용자 동작 `p2p-connect`(진단 탭 "P2P 연결") → STUN 두 곳(198.51.100.30·31:3478)의 답 포트가 같으면 cone, 다르면 symmetric → offer/answer 로 후보(host·srflx) 교환 → 양쪽 동시 펀칭(200ms × 6, host 후보는 바깥 주소가 같을 때만 — 집집마다 같은 사설 대역이라) → 실패면 제안한 쪽이 TURN(198.51.100.50) 할당 → 시그널링으로 릴레이 주소를 알리면 상대가 그리로 보내 연결(`via: "relay"`). NAT 없는 상대(`nat: none`)는 host 후보로 펀칭. 요청(STUN·offer·Allocate·relay 알림)은 1.5초마다 2번 재전송, 같은 offer 가 다시 오면 answer 를 다시 보낸다. 동시에 서로 제안하면(glare) 이름이 앞선 쪽이 제안 역할, 다른 상대와 연결 중이면 새 제안을 `busy` 로 거절(한 번에 한 상대). 등록 전에 연결하면 먼저 등록하고 이어서 연결, 등록 3번 실패 뒤엔 10초마다 배경 재시도. 끄거나 이름을 바꾸면 `unregister`, 서버는 같은 주소의 옛 이름을 지우고 보낸 이의 연락 주소를 메시지마다 새로 고친다. 다른 상대에 대한 시그널링 오류는 지금 세션을 실패시키지 않는다. 서버들은 인터넷 노드가 흉내(`Internet.p2pServers`, 사설 출발지는 드롭, 미등록 상대는 시그널링 오류). TURN 권한(CreatePermission)·ICE 우선순위·keepalive·연결 후 데이터는 생략. 헤어핀 NAT(`RouterSettings.hairpin`·`L3Settings.hairpin`, 기본 꺼짐): 안에서 내 바깥 주소의 TCP 포워딩 포트로 오면 포트 공개 모듈(`PortPublish`, FULLNAT)로 안쪽 서버에 넘기고 출발지는 이 장비의 안쪽 주소(응답이 장비를 거치게). 꺼져 있으면 `ip.drop` "헤어핀 NAT 꺼짐" 으로 안내(켜져 있던 동안 시작한 흐름은 꺼도 끝까지). NAT 박스·게이트웨이의 헤어핀은 바뀐 목적지로 방화벽 규칙을 거친다(실제 DNAT 의 FORWARD 체인). 포트 공개와 헤어핀은 프록시 포트를 서로 피하고(`PortPublish` 의 `taken`), NAT 공인 포트도 둘 다 피한다. UDP 포워딩은 헤어핀 대상 아님. 한계: 장치를 지울 때 등록 해제를 보내지 않는다(옛 이름으로 연결하면 응답 없음). 예제 "NAT 종류와 홀 펀칭 (P2P·STUN·TURN·헤어핀)"(`tests/p2p.test.ts`).
