# 공통 메커니즘 — 동기화·노드 클래스·NAT·DHCP·IP 충돌·TCP·traceroute

기능별 구현 상세 (예전 AGENTS.md "시뮬레이션 연결 방식" 에서 옮김 — 2026-10-07). 규칙·공통 메커니즘은 AGENTS.md.

- 노드 클래스: `Host`(DhcpClient + 선택적 DhcpServer/DnsServer + DnsResolver + ping + TcpStack), `Switch`, `Hub`(학습 없이 전부 반복), `Router`(LAN 브리지 + DhcpServer + DNS 포워더 + WAN DhcpClient + NatTable/포트 포워딩), `L3Node`(게이트웨이/NAT 박스: 인터페이스 N개, 직접 연결 → 스태틱 라우팅 → 디폴트 라우트, DHCP 릴레이(목적지가 내 주소·브로드캐스트인 DHCP 만 처리하고 나머지는 전달 — 릴레이 경로에 라우터가 더 있어도 됨), NAT 는 outside 에서 + 포트 포워딩. 동적 NAT 매핑은 기본이 상대를 가리지 않는 endpoint-independent(full cone) 방식이라 안에서 연 포트로 바깥 누구든 들어올 수 있다 — 기존 구성의 로그를 바꾸지 않으려고 기본값으로 유지하고, NAT 종류 설정으로 바꾼다(아래 "NAT 종류·P2P"). 바깥에서 사설 주소로 직접 온 패킷은 TCP·UDP·ICMP 모두 드롭), `Internet`(ISP DhcpServer — 가입자마다 /29, 아래 "ISP 대역" + 공인 DNS 8.8.8.8/1.1.1.1 + 공인 서버 대역 ping/TCP 응답 + 외부 클라이언트 198.51.100.7), `FirewallBridge`(`nodes/fwbridge.ts`, 투명 방화벽 장비: 포트 0 outside/1 inside, IP 없음, IPv4 만 `Firewall.check` 후 반대 포트로, ARP 는 통과(DHCP 는 IP 라 규칙 대상). 구성 검사는 양쪽 케이블을 하나로 접어 전선처럼 본다). 공용 모듈: `nodes/dhcp.ts`, `nodes/dns.ts`, `nodes/tcp.ts`, `nodes/nat.ts`, `nodes/firewall.ts`(지나가는 패킷만 검사, 방향은 업링크 기준 in/out, 안쪽끼리는 lan, Stateful 검사는 initiator 패킷만 흐름 등록).
- 루프백: 호스트가 내 주소로 보낸 패킷(IPv4·IPv6)은 네트워크로 나가지 않고 받는데, 보내는 자리에서 바로가 아니라 같은 시각·지금 일 다음에 받는다(0ms timer `loopback` — 리눅스 netif_rx 백로그). 보내는 쪽이 상태를 다 적기 전에 답이 돌아오는 재진입이 없다(LESSONS 4h·4k — 전에는 `onCreated` 같은 우회가 필요했다).
- 이름 해석: `ActionSpec.dst` 는 IP 또는 이름. 호스트가 `looksLikeName` 이면 리졸버로 먼저 해석(캐시 → 설정된 DNS → 실패 사유). DNS 서버 설정은 `NetInterface.dns`(수동 또는 DHCP 옵션). 리졸버는 물은 서버의 주소에서 온 답만 받는다(glibc res_send·nslookup "reply from unexpected source" — 다른 주소의 답은 버리고 timeout 으로 다시 묻는다, `tests/dns-resolver.test.ts`).
- 반복 ping(`ping -c N`, 진단 탭 횟수 선택 1·4·10회): `ActionSpec` ping 의 `count`(없거나 1 이면 예전처럼 한 번, 1~100 으로 자름). `Host.pingRuns`(`PingRun`, 최근 5개)가 실행을 묶고 각 `PingRecord.run` 에 id. `PING_INTERVAL`(1초) 일반 타이머 `ping-next` 로 다음 요청 — 이름은 처음 한 번만 해석하고 그 주소로 반복. 첫 요청도 못 보내면(IP 미설정·이름 해석 실패·IPv6 출발지 없음) `stopped` 로 멈추고 통계 없음. `pingRuns` 는 통계를 남긴(또는 멈춘) 실행만 밀어낸다 — 진행 중인 실행이 보관 수보다 많아도 끝까지 간다. 통계의 대상은 입력한 이름 그대로(리눅스 ping 처럼). 도중에 주소를 잃으면 그 요청만 "IP 미설정" 실패로 세고 계속. 다 보냈고 모두 답·timeout 이 나면 0ms 타이머 `ping-stats` 로 마지막 결과 줄 뒤에 트레이스 `icmp.stats`(보냄·받음·패킷 손실 %·RTT 최소/평균/최대/mdev → 패킷 상세에 리눅스 ping 통계 줄). `finishPing` 은 ctx 를 받아 실행 완료를 확인한다. 테스트 `tests/ping-repeat.test.ts`.
- DNS 조회(nslookup, 진단 탭 "조회"): `ActionSpec` `dns-lookup`(name·qtype A/AAAA·선택 server) → `Host.lookup` → `DnsResolver.lookup`. 실제 nslookup·dig 처럼 캐시를 거치지 않고 매번 묻고 답도 캐시에 넣지 않는다(질의·응답이 매번 캔버스에 지나가게). server 를 주면 그 서버에만(VPN DNS 도 건너뜀), 비우면 설정된 DNS(VPN DNS 포함). 127.0.0.1 은 내 주소(내 DNS 서버 서비스, 루프백). 서버를 지정하지 않은 A 조회는 메시 VPN 의 MagicDNS(100.100.100.100)가 먼저 답한다. 결과는 `Host.lookups`(최근 5개)와 트레이스 `dns.lookup`/`dns.lookup.failed`(details.rcode = NXDOMAIN·SERVFAIL·NODATA·timeout → 패킷 상세의 nslookup 출력). 0.0.0.0·:: 답은 실패가 아니라 `blocked`(DNS 필터가 막은 이름)로 그대로 보여 준다 — 공유기 DNS 와 8.8.8.8 에 물어 비교하는 용도. 한계: 역방향 조회(PTR)·CNAME·MX 없음, 권한 있는 응답(authoritative) 구분 없음. 테스트 `tests/nslookup.test.ts`.
- NAT TCP 매핑은 양쪽 FIN 뒤 마지막 ACK·RST 로 끝난 것으로 표시하고 2초(`NAT_TCP_TIME_WAIT`, L4 로드밸런서와 같은 TIME_WAIT 흉내 — 실제 conntrack 은 120초) 뒤 다음 변환 때 치운다(타이머 없음). ICMP·UDP 매핑은 만료 없음.
- 포트 포워딩은 TCP·UDP(`PortForward.proto`, 없으면 TCP — 예전 저장본 호환). 공유기 WAN 은 UDP 포워딩 규칙이 있는 포트를 DNS 포워더보다 먼저 NAT 역변환으로 넘긴다. 공유기 DHCP 의 DNS 서버 옵션(`RouterSettings.dhcp.dns`, 비우면 공유기 자신 = DNS 포워더). 구성 검사 `nat.forward-closed`(대상이 그 포트를 안 엶, 주소가 여러 사설망에 겹치면 침묵)·`router.dns-off`(자기 자신을 DNS 로 안내하는데 포워더 꺼짐).
- DHCP INIT-REBOOT(RFC 2131 4.3.2): `DhcpClient` 가 마지막 주소를 기억해 `start()`(링크 업·로밍·임대 갱신)에서 Discover 대신 서버 식별자 없는 Request 를 보낸다. 서버는 그 네트워크 주소가 아니거나 남의 임대면 Nak, 내 임대 기록이면 Ack, 기록이 없으면 침묵(클라이언트는 timeout 후 Discover). Nak·실패·Release 면 기억을 지운다.
- IP 충돌(RFC 5227 축소판, `NetInterface`): 고정 주소는 `claim()` — ARP Probe(보낸이 0.0.0.0) 후 200ms 동안 주장하는 장비가 없으면 Gratuitous ARP. 응답이 오면 `conflict.refused` 로 그 주소를 쓰지 않고(송신·ARP 응답 안 함), 충돌 상대가 다른 주소를 알리면 다시 claim. 쓰는 중 충돌은 기록 + Gratuitous ARP 방어(10초에 한 번). 노드는 `"arp-probe"` 타이머에서 `finishProbe` 를 부른다. DHCP 로 받은 주소는 Probe 없이 바로 announce. 타일은 `… 충돌` 경고.
- 진단 자동완성(`model/reach.ts` `probeTargets`): 토폴로지를 복제한 `NetworkSync` 에서 후보마다 ping/TCP·traceroute 를 실제로 돌려 닿는지·홉 수·실패 이유(방화벽/NAT 사설 주소/No route/VLAN/충돌)를 얻고, 출발 호스트 기준 위치(같은 서브넷/다른 서브넷/인터넷/이름)로 묶는다. 화면 시뮬레이션과 무관(복제본). UI 는 `app/TargetPicker.tsx`, 진단 입력값은 장치별로 기억(`diagMemory`).
- 주소 변경 시 정합성: 호스트/라우터/L3 모두 주소가 바뀌면 ARP 캐시·대기열을 비우고 TCP 연결을 정리하며 Gratuitous ARP 를 보낸다. DHCP 서버는 인터페이스/범위 변경 시 범위 밖 임대를 무효화한다.
- 공유기 경로 판단(2026-10-08, `Router.wanRouteProblem`·`defaultRouteProblem`): WAN 회선으로 나가는 패킷은 리눅스처럼 연결된 대역(LAN 이 먼저) → 그 회선의 대역 → 디폴트 라우트 순으로 판단한다. 디폴트 라우트는 넥스트 홉이 내 주소이거나 LAN 대역 안이면 쓰지 못한다 — 공유기 뒤 공유기를 둘 다 192.168.0.1 로 두면 안쪽 공유기 WAN 이 192.168.0.x(게이트웨이 192.168.0.1 = 내 LAN 주소)를 받아 인터넷이 `No route`. 두 곳에서 본다: LAN → 인터넷 전달(`forwardToWan`, NAT 전에 — 매핑을 만들지 않고 Destination Unreachable net)과 WAN 인터페이스의 `outbound` 훅(공유기 자신이 만든 패킷 49곳 전부 — DNS 업스트림·VPN·DDNS·멀티 WAN 추적 ping, 브로드캐스트는 통과). WAN 대역과 LAN 대역이 겹칠 때 목적지가 LAN 대역이기도 하면 LAN 경로가 먼저라 WAN 으로 보내지 않는다. 겹쳐도 넥스트 홉이 LAN 밖이면(예: WAN /16, LAN /24) 정상. 타일 `WAN … · No route`(warn). DHCP 서버는 같은 장비의 다른 인터페이스 주소(공유기 WAN·WAN2, `DhcpServer.ownAddresses`)를 빌려주지 않는다. 구성 검사 `router.wan-lan-overlap`(수동 WAN, 또는 자동 WAN 인데 WAN 세그먼트의 DHCP 서버가 공유기 하나뿐 — ISP·게이트웨이가 끼면 침묵). 한계: 이미 빌려준 주소를 WAN 이 나중에 받는 순서(LAN 기기와 WAN 이 동시에 DHCP)는 막지 못한다(dnsmasq 도 같다 — 대역을 고치면 사라짐), 겹친 상태에서 공유기가 내 주소로 보내는 패킷(리눅스는 자신에게 전달)은 따로 다루지 않는다, 포트 포워딩으로 들어온 연결의 응답이 LAN 대역 상대에게 가는 경우도 위 규칙대로 막힌다(실제도 LAN 으로 가 버린다). 테스트 `tests/router-route.test.ts`.
- **ISP 대역**(2026-10-19, `nodes/internet.ts`): 인터넷 노드는 ISP 대역(`Device.internet.net`, 기본 203.0.113.0/24 — `model/isp.ts`: 직접 입력·"무작위" 공인 /24, /16 ~ /28, 사설·CGNAT·루프백·링크 로컬·IETF 예약·벤치마크·멀티캐스트 대역과 인터넷 노드가 흉내 내는 서버(8.8.8.8·198.51.100.x 등, `simulatedPublicIps`)와 겹치면 기본 대역 + 구성 검사 `isp.net-invalid`)을 가입자마다 /29(`SUBSCRIBER_PREFIX`)로 나눠 준다 — `DhcpServer.perClient`: 대역의 첫 주소 = ISP 게이트웨이, 둘째 = 가입자, 같은 MAC 은 늘 같은 대역(임대 기록), FORCERENEW 로 바꾸면 다른 대역. ISP 게이트웨이는 대역마다 하나(`proxyArp`), 가입자에게 묻는 ARP 의 보낸이도 그 대역의 게이트웨이(`NetInterface.arpSource`). 가입자끼리는 같은 서브넷이 아니라 ISP 라우터를 거친다(`toSubscriber`: TTL -1, `ip.forward` "ISP 라우터: … 가입자 대역 …", Time Exceeded 는 보낸 가입자 대역의 게이트웨이 주소에서 — traceroute 에 ISP 홉). **손으로 적은 공인 주소는 ISP 가 모른다**: 가입자 쪽에서 온 공인 출발지는 ISP 가 그 MAC 에 임대한 주소여야 한다(IP Source Guard = DHCP snooping 바인딩, ISP 대역 밖 손 주소·남의 임대 주소도 드롭, DHCP 제외, 사설 출발지는 기존처럼 "NAT 가 필요" 드롭), 임대하지 않은 ISP 대역 주소로 가는 것은 Destination Net Unreachable(보낸 가입자 대역의 게이트웨이 주소에서), ISP 자신이 만든 것(외부 클라이언트 연결·Tor 출구·흉내 서버의 답)도 그런 주소로는 내보내지 않는다(`unleasedOut`). ISP 게이트웨이의 ARP 응답은 "ISP 게이트웨이 — 가입자 대역 …"(`NetInterface.proxyArpWhy`). 그래서 예제의 고정 공인 WAN 은 모두 자동(DHCP)이고, 상대 주소(VPN 상대·WireGuard 서버 등)는 그 기기가 받는 주소를 적는다(고정 IP 가 필요한 HA 쌍은 앞에 엣지 라우터). 실행 중에 대역을 바꾸면 가입자에게 FORCERENEW → 옛 서버 주소로 온 Request 도 내 것으로 보고(`DhcpServer.formerIds`) Nak → Discover → 새 대역(`Internet.setNet`). 주소 바꾸기는 옛 대역을 피하되 빈 대역이 그것뿐이면 다시 준다(/28). 설정 칸은 칸을 떠나거나 Enter 에 적용(한 글자마다 FORCERENEW 가 가지 않게). 인터넷 노드를 새로 붙이면 임대 기록이 없어 가입자는 WAN 을 다시 꽂거나 임대를 갱신해야 한다(그 사이 Source Guard 드롭 문구가 알려 줌). 설정 탭 "ISP 대역"(`IspNetSection`). 구성 검사: `isp.static-address`(ISP 구간에 손으로 적은 주소, warn), 그리고 앱·`tests/helpers` 의 `L.lint()` 는 ISP 임대(`netSync.leaseHints` — 그 인터페이스가 지금 그 주소를 가질 때만, → `store.ispLeases`, 시뮬레이터가 임대가 바뀔 때 갱신)를 `lintTopology(t, { leased })` 로 넘겨 자동 WAN 도 그 주소의 수동 WAN 처럼 검사한다(VPN 서버·포트 포워딩을 주소로 찾게 — 임대를 모르면 지금처럼 침묵, 지금 수동인 인터페이스는 옛 임대가 남아 있어도 손 주소로 본다). 리뷰 반영(2026-10-19): Tor 를 거치면 손 주소와 통신되던 길, MAC 을 보지 않던 Source Guard, ISP 대역 밖 손 주소, ISP 가 만든 연결이 손 주소로 나가던 것, 프록시 ARP 문구, 대역 변경 뒤 1초 DHCP timeout, /28 에서 주소 바꾸기 뒤 주소 없음, AdGuard 흉내 주소 대역 허용. 생략: 가입자끼리의 L2 격리(같은 통신사 구간 스위치라 손으로 넓은 마스크를 적으면 서로 직접 ARP 된다). 테스트 `tests/isp.test.ts`.
- traceroute: 라우터 계열이 포워딩할 때 TTL 을 줄이고 0 이면 ICMP Time Exceeded(원 패킷 식별 정보 내장)를 들어온 인터페이스 주소로 보낸다. NAT 는 내장 정보로 역변환, 방화벽 Stateful 검사는 원 요청의 응답으로 취급. `Host.traceroute`(ICMP Echo 방식, 홉당 프로브 1개, 1000ms 타임아웃 → `*`, 16 홉). ICMP Destination Unreachable(`IcmpUnreachable`, 코드 net·host·port): 게이트웨이·NAT 박스·공유기는 No route 에 net(!N), 전달하려던 패킷의 ARP 실패에 host(!H), 호스트는 닫힌 UDP 포트에 port(!P) 를 `iface.unreachable()` 로 만들어 보낸 이에게 돌려준다. 받은 호스트는 ping·TCP(`tcp.onUnreachable`, SYN_SENT 만)·DNS(`resolver.onUnreachable`)·traceroute(홉 `flag`) 를 즉시 실패로 끝낸다. Time Exceeded 와 함께 `isIcmpError` 로 묶여 NAT 역변환·방화벽 Stateful(오류 통지 = 응답)을 공유한다. NAT 바깥으로 나가는 통지는 `nat.translate` 로 원래 패킷을 공인 주소로 되돌린다. 방화벽 차단은 여전히 조용한 드롭(실무 기본 DROP) → `*` / timeout.
- TCP 는 학습용 축소판: 누적 ACK, 타임아웃 재전송(RTO 400ms, 3회), 순서 어긋난 세그먼트는 버리고 중복 ACK. 슬라이딩 윈도우·빠른 재전송 없음. 앱은 "GET / 100B → 응답 1000B×3 → 서버 FIN". 포트 22 는 SSH 흉내(`TcpConn.ssh`, `SSH_STEPS` 6개: 버전 교환 → 키 교환 → 인증 뒤 `ssh.open`, 세션을 열어 둔 채 유지, 명령·keepalive 없음). **SSH 점프**(`ssh -J`, 2026-10-19): 진단의 SSH 접속에 "점프 서버" 칸(사용자 동작 `tcp-connect {jump}`) — 클라이언트(`TcpConn.jump` login → wait → up)가 점프 서버 22 에 로그인한 뒤 채널 열기 요청(`SSH_CHANNEL_OPEN`, 세그먼트 `target` = "대상:포트")을 보내고, 점프 서버(`nodes/sshjump.ts` `SshJump`, 서버 서비스 "SSH 점프 허용" `HostSettings.sshJump` = AllowTcpForwarding)가 내 주소로 대상에 relay 연결을 열어 `SSH_CHANNEL_CONFIRM` 뒤 두 연결을 잇는다(프록시 CONNECT 와 같은 모양, 고리 `TcpHost.onChannelOpen`). 클라이언트는 그 채널 위에서 대상과 `SSH_STEPS` 를 처음부터 — 클라이언트 ↔ 점프 서버 구간에서는 바깥 SSH 로 한 번 더 감싼 `SSH_CHANNEL_DATA`(+32B), 점프 서버가 풀어 대상에게. 대상에게는 점프 서버 주소가 클라이언트(내부망 방화벽은 점프 서버의 22 만 들이면 된다). 대상 이름은 점프 서버가 푼다, 점프 서버·대상은 IPv4 만(점프 서버 이름은 듀얼 스택이어도 A 로만 묻는다, IPv6 대상은 `점프 대상은 IPv4 만` 으로 바로 실패). 실패: 점프 꺼짐 `administratively prohibited: open failed`(TCP 스택이 거절), 대상 RST `connect failed: Connection refused`, 대상 쪽 ICMP Unreachable `connect failed: No route to host`, 대상 무응답 `connect failed: Connection timed out`(점프 서버의 SYN 재전송이 클라이언트의 10초 채널 대기보다 먼저 끝남), 이름 못 풂 `Name or service not known`, 이름을 푸는 동안 점프 서버가 주소를 잃음 `Network is unreachable` — 클라이언트는 `ssh.jump.fail` 뒤 RST 로 끊고 이유는 `점프 실패 · …`. 연결 해제(FIN)는 채널 양쪽으로 전파. 점프 서버 표 "SSH 점프 기록 (sshd)", 실무 출력 ssh -v(ProxyJump·`Authenticated to … (via proxy)`)·sshd -d(`server_request_direct_tcpip`)·auth.log(`refused local port forward`·`connect_to … failed`). 구성 검사 `ssh.jump-no-sshd`. 시나리오 테스트는 `tests/fixtures.ts` `separatedJumpTopology`(NCP 예제 + 원격 접속 VPN 재택 노트북·DMZ·점프 서버 — 2026-10-19 까지의 예제), ui-check `ncpwg` 는 dev-1 의 "SSH 점프 허용" 을 켜고 ssh -J dev-1 → dev-2. 리뷰 반영: 서비스 동기화 키(`netSync` `services`)에 `sshJump` 가 빠져 이미 만든 서버에서 토글을 켜도 반영되지 않던 결함. 생략: 여러 단계 점프(-J a,b), PermitOpen, 한 세션의 채널 여러 개, SSH_MSG_DISCONNECT. 사용자 동작 `tcp-close`(`TcpStack.disconnect`, FIN) — 진단 탭의 "SSH 접속"(포트 22)·"연결 해제". 조용한 세션은 경로가 끊겨도 모르고 닫을 때 알게 된다(FIN 재전송 timeout·RST). 인터넷 노드는 80·22·443 을 받는다. 서버 서비스 토글에 SSH(22)·HTTPS(443). **HTTPS**(포트 443, TLS 1.3 축소판): 클라이언트는 원격 포트 443 이면(`relay`·CONNECT 가 아닐 때) ClientHello(SNI = 사용자가 적은 이름, 주소면 없음) → 서버(`TcpStack.tlsPorts` — 호스트는 443 을 들으면서 프록시 포트가 아닐 때, 인터넷 노드)는 ServerHello·인증서·Finished → 클라이언트 Finished + 암호화된 요청(`TcpSegment.tls` "app") → 암호화된 응답·FIN. 서버의 "응답을 이미 보냈나" 는 `bytesSent === tls.sent`(핸드셰이크 바이트 제외). L7 로드밸런서가 443 을 받으면 TLS 를 풀고(TLS 종료) 백엔드 포트대로(443 이면 다시 TLS), L4 는 그대로. TLS 가 아닌 답이면 클라이언트 `tls.fail`(RST), 평문 요청이 TLS 포트로 오면 서버 400, ClientHello 가 평문 포트로 오면(L4·포트 포워딩 443 → 80) 서버 400. 프록시에게 하는 평문 요청(`target`)은 프록시가 443 에서 들어도 TLS 가 아니다. CONNECT 응답·ServerHello 는 응답이 아니라 준비 바이트(`TcpConn.setupReceived`) — LB·프록시가 전달할 응답 크기는 `responseBytes(conn)`. 클라이언트가 응답을 끝까지(FIN) 받기 전에 RST 를 받으면 실패("상대가 RST 로 끊음 (응답을 다 받기 전)", SSH 세션은 종료). 터널 중계는 받은 세그먼트의 헤더 흉내 필드(`RelayPart` — Cookie·Set-Cookie·X-Served-By 등)를 그대로 넘긴다. tcpdump 는 TLS 를 풀지 않고, 패킷 상세는 TLS 층(레코드 번호·SNI, 응용 데이터는 "안 (두 끝만 풂)"). 인증서 검증·세션 재개·ALPN 없음.
