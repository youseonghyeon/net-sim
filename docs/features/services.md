# 서비스·공유기 앱 — 로드밸런서·프록시·DDNS·멀티 WAN·AdGuard·공유기 관리·Samba·SIP

기능별 구현 상세 (예전 AGENTS.md "시뮬레이션 연결 방식" 에서 옮김 — 2026-10-07). 규칙·공통 메커니즘은 AGENTS.md.

- DDNS(`nodes/ddns.ts`, 2026-10-07, Brume 계획 2단계): 공유기 `RouterSettings.ddns {enabled, name}`(이름 앞부분 → `name.glddns.com`, `ddnsHostname`) — `DdnsClient` 가 WAN 주소를 받거나 바뀔 때(`Router.onWanAddress`: DHCP Ack·수동 WAN Probe 끝)·설정 변경·10분마다(배경 타이머) DDNS 서버(인터넷 노드 198.51.100.60, `DdnsMessage` UDP 8245 — 실제는 HTTPS dyndns2)에 갱신, 2초·3번 재전송. 서버(`Internet.ddns` `DdnsService`)는 **요청의 출발지**를 등록(앞에 NAT 가 있으면 그 공인 주소), 이름은 기기(WAN MAC)마다 하나(badauth), 영역 밖이면 notfqdn. 공인 DNS 가 DDNS 이름을 TTL 30초로 답한다 — `DnsMessage.ttl` 을 리졸버·포워더 캐시가 따른다(기본 60초 중 짧은 쪽, 포워더는 남은 TTL 을 넘김). ISP 주소 바꾸기: 사용자 동작 `isp-renumber`(인터넷 노드 진단 "공인 주소 바꾸기") → `DhcpServer.renumber`(임대 삭제 + 그 고객에게 옛 주소를 다시 주지 않음 `avoid`) + DHCP FORCERENEW(RFC 3203, `DhcpOp "forcerenew"` — 클라이언트는 xid 와 상관없이 받아 쓰던 주소로 Request → Nak → Discover). WireGuard 서버를 이름으로: 공유기 클라이언트 `wgClient.server` 가 이름이면 `serverName`(공유기 자신의 `resolver` — WAN 으로 포워더 업스트림에 직접, 응답은 리졸버 포트로 NAT 역변환보다 먼저 받음), 노트북·폰 앱도 `ra.server` 에 이름(`effectiveRaClient`·`endpointName`, 터널 밖 DNS: `DnsResolver.resolve(…, direct)` 로 VPN DNS 를 건너뛰고, 엔드포인트가 없는 동안 DNS 질의는 가로채지 않음). 핸드셰이크가 끝내 실패하면 이름을 다시 푼다(`WgInterface.onFail` → `markResolving`/`setEndpoint`, GL.iNet reresolve) — 같은 주소면 다시 잇지 않는다(`"if-changed"`, 실패 ↔ 다시 풀기 무한 반복 방지). 다시 풀기가 실패하면 전에 쓰던 주소를 되살리고, 주소를 모르는 채 보낼 패킷이 생기면 다시 푼다(`needEndpoint`). DDNS 는 끔·이름 변경·공유기 치움 때 이름을 내려놓는다(`DdnsMessage` op `release`), WAN 주소를 잃으면 기다리던 갱신을 접는다. 구성 검사는 DDNS 이름의 주인이 포워딩하면 따라가고, 주인이 다른 공유기 뒤인데 앞 공유기에 포워딩이 없으면 `wg.server-behind-nat`. `DnsResolver.forget` 으로 캐시를 지우고 묻는다. 구성 검사 `ddns.name-invalid`·`ddns.name-taken`, WireGuard 클라이언트가 DDNS 이름이면 그 이름을 켠 공유기를 서버로 보고 키·등록을 검사(`wg.name-unknown` — glddns.com 이름인데 아무도 등록 안 함). 실무 출력 OpenWrt ddns-scripts·dyndns2 응답. 타일 배지 `DDNS`/`DDNS 실패`. 예제 "주소가 바뀌는 집 (DDNS·WireGuard)"(`exampleDdnsTopology` — 카페 공유기 port-restricted 라 집 서버가 새 주소에서 먼저 잇는 것은 막히고 폰이 이름을 다시 풀어야 함. full cone 이면 서버의 재핸드셰이크 + 로밍으로 이어진다).
- 멀티 WAN 페일오버(`nodes/mwan.ts` `MultiWan`, 2026-10-07, Brume 계획 3단계, mwan3 식): 공유기 `RouterSettings.wan2 {enabled, ipMode, ip, prefix, gateway, track}` — 켜면 **lan4 가 WAN2**(`Router.WAN2_PORT`, `bridgePorts()` 에서 빠짐, 모델 `specOf` 가 포트 이름을 wan2 로, 구성 검사 세그먼트도 lan4 를 따로 끝점으로). WAN2 는 자기 MAC(4번째 옥텟 03)·`wan2Client`(DHCP)·`nat2`(회선마다 공인 주소가 달라 NAT 도 따로, 포트 포워딩·NAT 종류는 둘 다). 나가는 길(`Router.out()`: LAN 전달·DNS 포워더 업스트림·DDNS)은 지금 회선(`mwan.active`), 들어오는 WAN2(`receiveWan2`)는 DHCP·ARP·추적 응답·DNS 포워더 답·DDNS 응답·WireGuard·ping·NAT 역변환·포트 포워딩 — L2TP VPN 서버·IPv6·공유기 자신의 이름 해석(`resolver`)은 WAN1 만(한계). 회선 상태: 링크·주소가 생기면 쓸 수 있음, 링크 다운·주소 잃음은 바로 끊김, 추적(`track`, 기본 8.8.8.8)이 있으면 5초마다(배경 타이머) 회선마다 그 회선으로만 ping(ICMP id `MWAN_ICMP_ID`+0/1, 출발지 = 그 회선 주소) — 직전 ping 무응답이면 실패, 3번 이어 끊김, 끊긴 회선이 2번 이어 답하면 살아남. 살아 있는 첫 회선(WAN1 우선 — 살아나면 되돌아감), 켜질 때 WAN1 이 DHCP 중이면 기다린다(`waiting`). 넘어가면 `mwan.switch` 와 DDNS 갱신, 진행 중 TCP 는 상대가 새 출발지를 모르는 연결로 보고 RST. 단 흐름은 그 흐름이 생긴 회선이 살아 있으면 그 회선에 붙는다(`NatTable.carries` + `Router.outFor`, mwan3 conntrack mark — WAN1 로 되돌아가도 WAN2 로 시작한 연결·WAN2 로 들어온 포트 포워딩의 응답은 WAN2 로, Host Unreachable 통지도 들어온 회선으로). 공유기 WireGuard(클라이언트·서버)는 지금 회선으로 보내고 WAN2 로 온 것도 받는다(출발지가 바뀌면 상대가 로밍으로 따라옴). WAN1 DHCP 가 끝내 실패하면 기다리지 않고 WAN2 로, WAN2 수동 주소도 ARP Probe. 타일 위쪽 줄은 WAN2 를 쓰는 동안 `WAN2 …`(경고 색), 배지 `멀티 WAN`/`WAN2 사용 중`, 표 "멀티 WAN (mwan3 status)"·회선별 NAT 표. 예제 "멀티 WAN 페일오버 (유선 + 휴대폰 핫스팟)"(`exampleMultiWanTopology`, 핫스팟 = 192.168.43.0/24 공유기). 생략: 로드 밸런싱, 회선 3개 이상, 추적 주소 여러 개.
- AdGuard Home·자녀 보호(`nodes/adguard.ts` `Adguard`, 2026-10-07, Brume 계획 4단계): 공유기 `RouterSettings.adguard {enabled, ads, mode zero|nxdomain, custom[], allow[], forceDns, parental[{ip, categories sns|game|video}]}` — 공유기 설정의 새 "앱" 묶음. DNS 포워더 앞의 필터(`DnsServer.filter` 고리: 내 레코드·캐시보다 먼저, 질의마다 쿼리 로그·통계): 예외 → 사용자 규칙 → 광고·추적 목록(`AD_DOMAINS`) → 그 기기의 자녀 보호 카테고리(`PARENTAL_CATEGORIES`) 순, 규칙은 그 이름과 하위 이름(`||x^`). 막으면 업스트림에 묻지 않고 0.0.0.0·::(기본) 또는 NXDOMAIN(`dns.blocked`). 호스트는 0.0.0.0·:: 답을 "DNS 가 막은 이름" 으로 실패시킨다(`Host.resolveName`). DNS 가로채기(`forceDns`): LAN 에서 LAN 밖 DNS(8.8.8.8 등)로 가는 UDP 53 질의를 공유기가 받아(`dns.hijack`, iptables REDIRECT — IPv6 도 `handleLan6` 에서) 원래 서버 주소로 답한다(`DnsServer.answersAt`, IPv6 답도 그 주소에서). 자녀 보호는 IPv4 주소로 정하지만 IPv6 로 물은 기기도 이웃 캐시 → MAC → IPv4(`Router.clientV4`, ARP 캐시 또는 LAN 에서 본 ARP·IPv4 프레임 `lanSeen`)로 알아본다. 프록시 서버의 리졸버도 0.0.0.0·:: 답은 막힌 이름으로 끝낸다. 구성 검사 `adguard.bypass` 는 IPv4 DNS 가 없을 때의 IPv6 DNS 도 보고, DNS 가 공유기에 되묻는 LAN DNS 서버면 침묵한다. 규칙 칸은 치는 동안 원문을 두고 칸을 떠날 때 목록으로(`RuleList`). 새 공개 이름(광고·SNS·게임·동영상)은 인터넷 노드가 `FILTER_ZONE` 으로 답하되 자동완성(`PUBLIC_ZONE`)에는 넣지 않는다. 구성 검사 `lint/adguard.ts`: `adguard.dns-off`·`adguard.dhcp-dns`·`adguard.bypass`(DNS 를 직접 적은 기기, 가로채기 꺼짐). 실무 출력: AdGuard 쿼리 로그 한 줄, iptables REDIRECT. 타일 배지 `AdGuard`, 표 "AdGuard 쿼리 로그"(최근 50). 예제 "광고 차단·자녀 보호 (AdGuard Home)"(`exampleAdguardTopology` — 스마트 TV 는 DNS 8.8.8.8 이라 가로채기를 끄면 우회). 생략: DoH, 목록 갱신, 안전 검색, 시간 예약(벽시계 없음).
- 공유기 관리(`nodes/glinet.ts`, 2026-10-07, Brume 계획 8단계): **관리 접근** `RouterSettings.admin {enabled, remote, allow(쉼표 CIDR), ssh}`(없으면 꺼짐 — 기존 "라우터 자신에게 온 TCP → 듣는 서비스 없음" 그대로) — `RouterAdmin` 이 공유기 자신의 `TcpStack`(80·443 TLS·22 SSH)으로 답한다. SYN 만 검사: WAN 은 `remote` 일 때만(그 포트에 TCP 포트 포워딩이 있으면 포워딩이 먼저), LAN 은 허용 목록, LAN 밖 출발지(VPN)는 remote 일 때만. 답은 받은 주소에서(`ovpnSend` — LAN/WAN/WAN2). 표 "관리 화면 연결". **기기 차단** `RouterSettings.blocked[MAC]`: LAN(IPv4·IPv6)·드롭인에서 인터넷으로 나가는 것을 MAC 으로 드롭(`fw.deny`), LAN·공유기 자신과는 통신. **GoodCloud** `RouterSettings.cloud`: `CloudAgent` 가 클라우드(198.51.100.90:443, UDP 로 줄임)에 register → registered, 25초마다 keepalive(배경 타이머), WAN 주소가 바뀌면 다시 등록. 인터넷 노드 `CloudService` 가 연락 주소(NAT 바깥)를 기억하고, 사용자 동작 `cloud-manage {nodeId: 인터넷, device: MAC}`(인터넷 노드 진단 "GoodCloud 원격 관리")로 그 주소에 manage → 공유기가 status(WAN·기기 수·VPN) — 공유기가 먼저 연 연결이라 포트 포워딩 없이 들어간다, 3초 응답 없으면 timeout. **드롭인 게이트웨이** `RouterSettings.dropIn`: WAN 으로 온 패킷이 내 주소가 아니고 출발지가 WAN 서브넷이면(`dropInForward`) LAN 기기처럼 `forwardToWan`(VPN 클라이언트·DPI·방화벽·NAT), 응답은 NAT 역변환 뒤 목적지가 WAN 서브넷이면 WAN 으로 되돌린다(`toDropInClient`, WireGuard 클라이언트 응답도), 같은 WAN 서브넷 상대는 한 팔로 되돌림(ICMP Redirect 없음). 구성 검사: `host.no-gateway-in-segment` 는 같은 세그먼트의 드롭인 공유기 WAN 주소를 게이트웨이로 인정, `lint/glinet.ts` `admin.remote-open`·`dropin.wan-dhcp`. 배지 `드롭인`·`GoodCloud`. 예제 "드롭인 게이트웨이 (기존 공유기 옆에 꽂기)"(`exampleDropInTopology` — 아이 PC 만 Brume 의 DPI). 리뷰 반영(2026-10-07): 드롭인 기기도 VPN 클라이언트 정책·킬 스위치 대상(`policyApplies`·`fromDropIn`), 드롭인 기기로 보내는 DPI RST·Time Exceeded·DNS 답은 WAN 으로(`insideOf`, `DnsServer.replyVia`), 드롭인 모드의 WAN 쪽 기기는 관리 화면을 LAN 규칙으로. 관리 화면은 VPN 터널(WireGuard·OpenVPN·메시·L2TP)·IPv6 LAN·WAN2·자기 공인 주소(헤어핀 꺼짐이면 포워딩 대신 관리 화면 — OpenWrt DNAT 는 wan 에만)로도 받고 답은 그 길로. 관리 설정이 바뀌어도 열린 세션은 그대로(규칙은 새 연결부터), 끄면 RST. 허용 목록에 쓸 수 있는 항목이 없으면 아무도 허용하지 않음(fail-closed, 구성 검사 `admin.allow-invalid`), IPv6 출발지는 허용 목록이 있으면 거부. 기기 차단은 노트북의 wlan0 MAC 도 함께. GoodCloud 는 멀티 WAN 전환 때 다시 등록하고 WAN2 로도 받는다, 상태의 VPN 칸은 WireGuard·OpenVPN·L2TP 서버·클라이언트·메시를 모두. 구성 검사 `dhcp.gateway-mismatch` 도 드롭인 게이트웨이를 인정. 생략: 관리 화면 로그인, 원격 설정 변경, 드롭인 쪽 기기의 DNS 가로채기·AdGuard(같은 LAN 의 기존 공유기 DNS 로 바로 가는 질의).
- 네트워크 저장소(Samba, 2026-10-07, Brume 계획 9단계): `RouterSettings.samba {enabled, wan}` — 관리 화면과 같은 `RouterAdmin` TcpStack 이 445 를 듣는다(LAN 만, `wan` 이면 인터넷도). TCP 앱 흐름은 HTTP 흉내 그대로이고 포트 445 면 요청·응답 이름만 SMB(`SMB_PORT`·`SMB_REQUEST`, tcpdump `SMB-over-TCP`). 구성 검사 `samba.wan-open`(오류)·`nat.forward-smb`(445·139 포트 포워딩).
- 인터넷 전화·SIP ALG(`nodes/sip.ts`, 2026-10-07, Brume 계획 9단계): 단말 `HostSettings.sip {enabled, user}`(`SipPhone` — 비면 장치 이름의 영문 레이블), UDP payload `SipMessage`(REGISTER·INVITE·ACK·BYE, 응답 180·200·404, Contact, SDP 음성 주소)·`RtpPacket`, 서버 198.51.100.120:5060(인터넷 노드 `SipServer` — 등록 때 Contact 대신 실제로 온 곳(received·rport)을 기억해 거기로 신호를 넘기고, SDP 는 건드리지 않는다). 주소를 얻으면 등록(1.5초·2번), 사용자 동작 `sip-call {nodeId, to}` → INVITE → 180 → 200(SDP) → ACK → 양쪽이 상대 SDP 주소로 RTP 5개(20ms) → 건 쪽이 BYE. 받은 음성이 0 이면 통화 기록에 "상대가 알려 준 음성 주소 … 는 사설 주소". 공유기 `RouterSettings.sipAlg`(기본 꺼짐): `forwardToWan` 의 NAT 변환 뒤 SIP 의 SDP·Contact 가 안쪽 주소면 공인 주소로 고치고(`sipAlgRewrite`), 그 음성 포트를 `NatTable.openPinhole`(가능하면 같은 포트, 필터링 없음)로 미리 연다(`sip.alg`). 한쪽만 켜면 한쪽 통화. 표 "통화 기록"·"SIP 서버 등록". 리뷰 반영: 등록은 60초마다 갱신(배경 타이머 — 공유기 공인 주소가 바뀌어도 서버가 새 주소를 배움), 3번 실패하면 10초마다 다시(요약 "등록 실패"), 걸 때 미등록이면 바로 다시 등록. 이름을 바꾸거나 끄면 옛 이름을 해제(REGISTER Expires 0), 받는 쪽은 To 가 내 이름이 아니면 404, 자기 자신에게 걸면 서버가 486. BYE 는 200 이 없으면 1초씩 2번 다시, 서버는 BYE 의 200 까지 넘긴 뒤 통화를 잊는다, 받은 쪽은 30초 동안 아무것도 오지 않으면 끊는다(RTP timeout 배경 타이머), 링크를 잃으면 통화 끝. ALG 는 통화마다 연 구멍을 기억해 BYE·그 200 이 나갈 때 닫고(`NatTable.closePinhole`, `NatEntry.pinhole`), 방화벽에도 그 음성 포트를 미리 들인다(`Firewall.expects` — RELATED), 같은 공유기 뒤 상대에게는 공인 주소의 ALG 구멍을 안에서 바로 되돌린다(`sipHairpin`, NAT 루프백). DPI 앱 `sip`·`rtp`(기본). 상태 문구는 한국어(`CALL_STATE_LABEL`). 생략: 인증(401)·TCP/TLS·re-INVITE·코덱·STUN/ICE·서버 RTP 중계, 들어오는 SIP 의 ALG(상대 SDP 는 이미 공인), NAT 박스·게이트웨이의 ALG. 예제 "인터넷 전화와 SIP ALG"(`exampleSipTopology`).
- 로드밸런서(`nodes/lb.ts` `LoadBalancer`, 리버스 프록시·L7): 서버의 서비스 토글(`HostSettings.lb`)과 전용 장비(`kind: "lb"`, 호스트 계열·LB 켜진 채 생성)가 같은 모듈을 쓴다. `TcpStack` 의 `TcpHost.onRequest`(요청을 앱이 맡아 ACK 만 하고 나중에 `respond`) / `onFinish`(연결 종료 알림) 고리로 붙는다. LB 가 백엔드로 `connect` 해서 응답을 받으면 같은 크기로 클라이언트에 전달하고 세그먼트에 `origin`(X-Served-By 흉내)을 실어 클라이언트 `TcpConn.servedBy` 에 남긴다(진단 목록 "응답 …"). 분배: 라운드 로빈·최소 연결. 헬스 체크는 **패시브**(거부·timeout 이면 10초 빼고 같은 요청을 다음 백엔드로, 전부 실패면 502)가 기본이고, **액티브**는 설정 `LbConfig.healthCheck`(기본 꺼짐, HAProxy check inter 2s fall 3 rise 2): 2초마다(배경 타이머) 백엔드에 체크 연결(`ConnectOptions.probe` — 맺어지면 `onEstablished` 로 성공 후 FIN, **SYN 재전송 타이머를 걸지 않음**: 일반 타이머를 남기면 죽은 백엔드가 있는 동안 시계가 멈추지 않는다, timeout 은 다음 라운드에 `abandon`. SYN 에 시뮬레이터 내부 표시 `TcpSegment.probe` 를 실어 받은 서버도 그 연결의 재전송을 배경 타이머로 — 돌아오는 길만 끊긴 백엔드의 SYN·ACK 재전송이 라운드마다 쌓여 시계가 멈추지 않던 결함. 체크 연결은 진단 목록·자동완성·LB 자신의 TCP 표에서 뺀다, 체크를 끄면 기다리던 체크 연결을 접는다), 3번 연속 실패면 DOWN(`lb.down` check, HAProxy 로그 줄) 2번 연속 성공이면 UP(`lb.check`), 성공이 이어지는 동안은 조용하다. `isUp` = 패시브로 빠지지 않았고 액티브 DOWN 이 아님. 링크 연결·설정 변경 때 `ensureChecks`. L4 는 체크 연결의 응답을 변환하지 않는다. TCP 임시 포트는 49152~65535 를 돌며 쓰는 중인 포트와 같은 장비의 L4 변환 포트(`TcpStack.reservedPort`)를 건너뛰고, 변환 포트도 쓰는 중인 TCP 포트를 건너뛴다. 호스트의 실제 listen 포트 = 서비스 포트 + LB 포트(`syncListening`). 구성 검사 `lb.no-backend`·`lb.backend-closed`·`lb.loop`(백엔드를 따라가 자기로 돌아옴). 요청은 거친 LB 수를 `via` 로 싣고 5개 이상이면 508 Loop Detected, 뒤에서 온 상태 줄(502·508)과 `servedBy` 는 그대로 전달. LB 의 백엔드 연결은 `connect(…, { onCreated })` 에서 등록한다 — 내 주소로 가는 루프백은 `connect` 안에서 끝까지 동기로 진행되기 때문. TCP 클라이언트는 요청 뒤(또는 마지막으로 받은 뒤 — 받을 때마다 다시 잼) 10초 동안 받은 게 없으면 RST 후 실패(`TCP_READ_TIMEOUT`, HTTP read timeout 흉내, 일부만 받았으면 "응답이 중간에 멈춤"), FIN 을 받으면 끝 — 중간 LB·대상이 끊겨도 영원히 기다리지 않게, LB 에게는 백엔드 실패가 된다. LB·프록시는 상대 FIN 까지 받은 응답만 전달하고 FIN 없이 끊긴 일부 응답은 실패로 본다. 앱이 요청을 맡을 때(`onRequest`) `deferred` 를 먼저 세우고, 루프백으로 응답까지 끝났으면 "받아 오는 대로" ACK 를 따로 보내지 않는다. `transmit` 은 상태를 갱신한 **뒤** 보낸다(루프백 재진입). **점검 항목: TcpStack 에 앱 흐름(LB·프록시·SSH 같은 고리)을 새로 넣으면 "뒤 서버·대상 = 자기 자신" 루프백 테스트를 반드시 하나 둔다** — 세 번 어겼다(`docs/LESSONS.md` 4h·4k). **L4 모드**(`LbConfig.mode: "l4"`, LVS FULLNAT·NLB 식): LB 포트로 온 세그먼트를 TCP 로 받지 않고(`syncListening` 에서 제외) `LoadBalancer.l4` 가 목적지를 백엔드·출발지를 LB:변환 포트(50000~)로 바꿔 넘기고, 돌아오는 것은 반대로(`lb.forward`). 흐름은 SYN 에서 고르고, 양쪽 FIN 뒤 어느 쪽이든 순수 ACK·RST 면 끝난 것으로 표시해 2초(TIME_WAIT) 뒤 다음 SYN 때 치운다(타이머 없음, 최소 연결은 진행 중인 흐름만 셈, 상한 256 은 끝난 흐름부터 내보냄). 끝난 연결의 포트로 SYN 이 오면 새 흐름. 패시브 헬스 체크: SYN·ACK 전에 백엔드 RST, 또는 SYN·ACK 를 못 본 채 SYN 재전송이 오면(무응답) 빼 두고 다시 고른다(고정도 풀림, 연결 시작 전이라 옮겨도 됨). 자기 자신(같은 주소·포트)은 후보에서 빼고, TTL 을 줄여 L4 끼리 순환하면 TTL 로 끝난다. 설정 변경 시 남은 백엔드의 흐름·고정·상태는 유지. HTTP 를 보지 않아 SSH 도 나눈다(`lb.ssh-port` 는 L7 만). **세션 고정**(`sticky`): `"ip"`(두 모드) 출발지 IP → 백엔드 어피니티, 그 백엔드가 빠지면 다시 골라 고정 — NAT·프록시 뒤의 여러 사람은 한 주소라 한 백엔드로 몰린다. `"cookie"`(L7 만, HAProxy `cookie SERVERID insert` 식) 클라이언트가 이 백엔드를 가리키는 쿠키를 안 가져왔으면 첫 응답 세그먼트에 `setCookie`(`SERVERID=주소:포트`)를 싣고, 다음 요청의 `cookie` 로 고른다(가리키는 백엔드가 빠져 있으면 다시 골라 새 쿠키). 쿠키 저장소는 끝 클라이언트의 `TcpStack.cookies`(사이트 = 사용자가 적은 호스트: 이름으로 접속하면 이름(`connect(…, { site })`), 프록시 경유면 대상 호스트, 아니면 주소 — 브라우저처럼 포트는 안 보고 대소문자 무시). 중계 연결(`via` 가 있는 LB·프록시의 연결)은 저장소를 쓰지 않는다. LB 는 받은 쿠키를 백엔드로 넘기지 않고 백엔드의 Set-Cookie 도 전달하지 않는다(LB 체인의 쿠키는 다루지 않음). L4 는 HTTP 를 안 봐 쿠키 고정이 동작하지 않는다(UI 에서 막고 구성 검사 `lb.cookie-l4`). 예전 저장본의 `sticky: true` 는 `normalizeTopology` 가 `"ip"` 로.
- 포워드 프록시(`nodes/proxy.ts` `ForwardProxy`, Squid 식): 서버의 서비스 토글(`HostSettings.proxy {enabled, port 3128, deny[]}`), 클라이언트는 `HostSettings.httpProxy {enabled, server, port}`(http_proxy). 호스트의 TCP 동작이 포트 80 이면(대상이 같은 사무실이어도 — 예외 목록 없음, 내 주소만 직접) 이름도 풀지 않고 프록시로 연결하며 요청에 `target`("호스트:포트", 요청 줄이 절대 URI `GET http://…/`)을 싣는다(`proxy.use`). 프록시는 LB 와 같은 `onRequest`/`onFinish` 고리로 붙어(LB 가 먼저) 대상 이름을 자기 리졸버로 찾고 자기 주소로 연결해(`via`+1, 클라이언트 쿠키 전달) 응답·Set-Cookie 를 돌려준다. 포트 443 이면 CONNECT 터널(`ConnectOptions.method: "CONNECT"`): 요청 줄 `CONNECT 호스트:443`, 프록시는 대상에 중계 연결(`relay` — 스택이 앱 흉내 없이 받은 데이터·FIN 을 `TcpHost.onRelay` 로, 맺어지면 `onEstablished`)을 열고 `200 Connection established`(`CONNECT_ESTABLISHED`) 뒤 두 연결을 잇는다(`tunnels`), 클라이언트는 같은 연결로 대상과 TLS. 한쪽이 닫히면 다른 쪽 FIN, 실패면 RST(`TcpStack.reset`). 기록 `TCP_TUNNEL/200`(URL 자리에 호스트:포트), 연결 실패·이름 실패 `NONE/503`. 프록시 로그에는 SNI 와 길이만 — 요청·응답 문구가 새지 않게 중계 쪽 요약은 `describeData(seg, relay)`. 프록시가 아닌 웹 서버가 CONNECT 를 받으면 405, L7 로드밸런서도 405(nginx 식, 구성 검사 `proxy.l7-connect` — L4 는 연결째 넘겨 된다). 실패는 Squid 처럼: `target` 없음(프록시 포트로 직접 접속) 400, 차단 목록(이름은 하위 이름 포함, 주소는 같을 때 — 이름을 푼 주소도 비교, Squid dst ACL) 403, 이름 못 찾음·연결 실패·응답 중간 끊김 503, 기다리던 클라이언트가 먼저 끊으면 기록만 `TCP_MISS_ABORTED/000`. L7 로드밸런서는 요청 대상(절대 URI)을 백엔드에 그대로 넘긴다(LB 뒤 프록시 팜). 프록시 표 "프록시 요청 (access.log)"(최근 20개, `TCP_MISS/200` 등). 진단 목록은 대상 아래 "프록시 경유", 4xx·5xx 는 실패 색. 부모 프록시·X-Forwarded-For·TLS 가로채기 없음. 구성 검사 `proxy.not-running`(가리킨 수동 주소 장비에 그 포트의 프록시가 없음 — 그 포트의 로드밸런서면 침묵, 웹 서비스면 "그 서버 자신의 응답"), `proxy.port-clash`(같은 장비의 로드밸런서가 프록시 포트를 먼저 받음). 불러올 때 `normalizeTopology` 가 `proxy`·`httpProxy`·`lb.sticky` 를 타입대로 정리. 진단 자동완성은 프록시 경유 연결의 이름을 응답을 만든 서버 주소로 보인다. 예제 "포워드 프록시 (프록시로만 나가는 사무실)" — 공유기 방화벽이 proxy-1 만 내보낸다.
